# 设计文档作为第四类文档

`docs/` 此前在规范里写作「只放三类」：产品文档、技术文档、标准。但实际存在 `docs/设计/` 下 10 份（2903 行）方案文档，其中 [章工作台-产品文档.md](../设计/章工作台-产品文档.md) 有 939 行，比根产品文档（503 行）还长。规范与现状不符，且这些文档不被任何其他文档引用，编码代理无从发现它们。

我们决定把 `docs/设计/` 认定为**第四类文档**，并在 [docs/README.md](../README.md) 登记、在 `pnpm check:docs` 校验状态行。

## 考虑过的替代方案

**并入产品文档与技术文档。** 设计文档的价值恰恰在于记录「当时为什么这样选、否掉了什么」，而规范第 5 节第 2 条要求现状文档不写演变过程。并入等于把两类相反时效的内容塞进一份文件，会让两条规则互相抵消。

**迁到 `.scratch/`（gitignore，不进公开仓库）。** 最省事，但会丢掉未实施的方案：`章工作台-技术设计.md` §2 写着「硬约束（来自 PM 规格，实现时不得偏离）」，那是未来实现的唯一口径来源，删掉就真丢了。这些文档只付出一份索引条目的代价。

**只改规范文字，索引维持粗粒度。** 无法解决「代理发现不了」的问题——那 7 份设计文档当时不在任何索引里，也正是「AI 直接改代码」的机制性原因之一。

## 后果

- 规范 §5 第 1 条改为四类，并写清「三类说现在是怎样，设计说打算变成怎样」的分界。
- 设计文档不受「不写演变过程」约束，它记录的就是权衡过程。
- 设计文档有最低四段（要解决的问题 / 关键取舍与不选什么 / 验收标准 / 待确认）与一行 `> 状态：…`；四段由作者自查，状态行由 `check:docs` 机械校验。
- 设计文档不因实施完成而迁移或改名。仍然有效的现状结论由作者择机并入产品文档或技术文档，原文保留当时的判断。
