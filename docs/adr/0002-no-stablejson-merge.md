# 不做 stableJson 两份合一

`packages/core` 里有两处 `stableJson` 实现，输出等价但各自独立维护。它们参与**指纹**计算——证据身份、审读指纹、润色承接的判定都建立在这个字符串上。

我们决定**保持两份，不合并**。

## 考虑过的替代方案

**合并成一份。** 看起来是明显的重复消除，但两处实现一旦合并，任何一方为了自己场景做的微调都会同时改变另一方的输出，进而改变指纹。指纹变了，存量书仓里所有已记录的指纹就全部失配——审读结果会被判定为 stale，润色承接会作废，已定稿章节的证据身份需要重算。这不是一次重构，是一次数据迁移。

**合并并版本化迁移。** 这是唯一正确的合并路径，也是我们不做它的原因：需要为指纹字段引入版本号、写迁移脚本、并且在迁移期间同时支持新旧两种算法。收益是删掉一份几十行的函数，成本是一次全量数据迁移加一段双算法共存期。这个交换不划算。

## 后果

两份实现之间的等价性由测试保证，不由代码结构保证。改动任一处的输出格式前，先确认另一处是否需要同步，并检查是否有测试覆盖这个等价性。

若将来因为其他原因必须做数据迁移，这项可以一并重做。
