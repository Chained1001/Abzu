# 拆书（teardown）开源实现调研

> 调研日期：2026-09-28。两路并行子代理实地拉取源码核对：oh-story story-long-analyze 全管线、analyze-hit-novel 仓库找回与遗漏项核对。
> 用途：abzu-teardown workflow 文件设计（设计稿 v1.0 之上的可执行层）的参照与校准。

## 一、oh-story story-long-analyze（7.2k★，最重的实现）

读法总纲（SKILL.md 原文）：**"机械边界只解析一次；原文按连续章节块读取一次；同次读取产生逐章事实和跨章观察；聚合阶段复用落盘结果，不重新阅读全文。"**

### 流水线（Stage 0-6）

索引→黄金三章（**停下问用户**）→逐批派 chapter-extractor→结构框架→角色设定关系→报告→文风（按索引定点读 4-6 段）。SKILL.md 本身是"按时刻读"的渐进调度器——每阶段只读该行列出的文件，阶段间只靠落盘产物+进度文件交接。

### 原文隔离协议（六条，缺一不可——最彻底的实现）

1. 派发只照抄计划字段（batch_id/章节范围/行号），不另选不推算
2. 子代理按行号自读原文（原文.txt:L起-L止）
3. 结果只写输出文件
4. 回执一行（`BATCH_WRITTEN`），主会话不 Read 批次输出
5. 提交被拒→错误码原样再派，子代理用 Edit 只改出错处
6. 主会话全程不中转内容

配套：`handoff_cache` 跨批状态交接（别名/未闭合剧情点/悬念/关系/待核五项结构化交接；"隔批不假设接上"）；三档并行度（默认每轮 3 批）；agent 定义 maxTurns 20、权限默认全拒只开读+写缓存。

### 质量门控四层

提交机械校验（情节点数=字数÷200 下限、字段计数整批拒收）→子代理 Grep count 自查（P 行数==标题数==标签数）→Stage 3 量化阈值（置信度≥0.85/覆盖率 85-95%/重叠≤35%）→**合成期事实保真三约束**（错误最大来源是"离原文两跳的聚合层"且"强模型也照样漂移"：硬事实可溯源/缺失写"原文未明确"禁编造/跨指代不串）→语义验收样例（六个合成样例+硬失败清单）。

### 断点续跑

单状态文件 `_progress.md`（HTML 注释受管区）+ 每章 sha256+全源 sha256（原文漂移检测：改动只失效覆盖批次）+ 恢复三条件 + split + **已有摘要永不覆盖**。明令禁止 checkpoint/receipt 文件增殖。

### 交互纪律

问用户的：书名/原文路径、Stage 1 后必停（带推荐选项+默认值）、索引错位三选一、连续失败报告。不问的：批次大小、并行档位、粒度。**作者口径契约**：面向作者"说书不说系统"——禁脚本名/JSON 字段/hash/指标名，编号必须带人话名。

### 短板（Abzu 可做得更好）

无模型分层（几百批全用同一模型）；3 章/25k 批次过小（并行档位 12 本质在为小批次买单）；无独立验证者（事实真伪只有自查）；中文 Markdown 字段面做协议脆弱（同义名即失败）；恢复逻辑集中在 5.7 万字节单体脚本；一次一本。

## 二、analyze-hit-novel（ciel-oliver/analyze-hit-novel，10★，**无 License**）

仓库找回：https://github.com/ciel-oliver/analyze-hit-novel（2026-08 建，skill+四部书 demo）。**无 License——与 webnovel-writer 同等纪律：只借鉴设计思想，不得复制文本。**

### 对账结果

已吸收六项机制全部属实；一处校正：**章节卡实际 14 字段**（我们记 12——漏"状态变化"与"证据"）。打分锚点（剧情 1-5 各级定义/情绪先标类型/描写密度三级）与摘要 100-300 字上限一并补入。

### 遗漏项（值得吸收）

| 机制 | 内容 | Abzu 落点 |
|---|---|---|
| 输入覆盖率三档 | 全文=完整拆／大部分=拆+声明缺失影响／梗概=暂定分析不声称覆盖 | 进场契约 |
| 合并一致性检查 | 分批五步的最后一步：合并后查姓名/时间/动机/秘密/因果矛盾 | 1b 收尾 |
| 冲突矩阵五类+终局对手诊断 | 利益/信念/情感/身份秘密/方法；"高利益+高信念冲突+持续行动力=终局对手候选（诊断线索非定律）" | 深度分析·关系演变 |
| 人物功能三型判断问题 | "删除这个人物，关键事件是否不会发生" | 人物总表·功能列 |
| 原创迁移四层+相似性审计 | 表层/戏剧机制/人物引擎/主题张力；可迁 2-4 层；种子 10 要素+强制相似性再审 | fusion 红线互证 |
| 8 条终检清单 | 完整六维/双时间线齐备/顺序调整有解释/三节奏分开/有向动词/证据置信度/机制非复刻/覆盖率声明 | Stage 收尾门 |

## 四、对 abzu-teardown workflow 设计的净结论

1. **读法总纲照抄**（四句话）作为 workflow 开篇纪律
2. **原文隔离六条协议**全文采纳为派工纪律
3. **机械索引升级**：章节索引.csv 加每章 sha256+全源 sha256+parser 版本——断点续跑地基
4. **拆书进度.md**：单状态文件+受管区+禁止 checkpoint 增殖；原文漂移=只失效覆盖批次
5. **合成期事实保真三约束**进 1d/Stage2 合成步（防"离原文两跳"漂移）
6. **章节卡 12→14 字段校正**；打分锚点补进 schema
7. **handoff_cache 五项交接**进 1b 批次协议
8. **进场三档覆盖率声明**；**8 条终检**进各 Stage 收尾门
9. **作者口径契约**：面向作者说书不说系统（独立小节）
10. **阵容决策（待裁决）**：拆书扫描工——oh-story 用单一 chapter-extractor 且无分层是公认短板；Abzu 方案：新增第 9 代理 teardown-scanner（标准档、批次提取+写缓存+Grep 自查、权限最小化），或技能内嵌任务书不入常驻阵容
11. oh-story 的 3 章/25k 过保守——Abzu 批次取 5-8 章/40k 字符级（强模型时代），但保留"信息密集章 1-2 章/批"的语义分块与处理批次两轴区分
12. 文风.md 的按索引定点取样（不重扫全书）——Stage 3 或正文阶段可选增补
