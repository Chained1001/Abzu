# 架构设计

> 定位：Abzu 的架构层设计——域划分、调用形态、域间衔接与成长路径；触发与交互的通用细则归 `docs/standards/skill资产标准.md`（开发底座），本件只写产品层裁定。
> 依据：迁移自原《触发与交互标准》（入口唯一／机制键／禁互调／调用双层）、原《产物契约标准》（跨域衔接原则）、原《命名标准》（域名纪律）与 `docs/specs/施工机制.md`（运行侧定义），去底座化后重写；§三 与 §四 的条文摘要自存档 `docs/product/总纲.md` §三／§四。

## 一、域清单（域名以本表为准）

| 域 | 域名（skill 名） | 命令 | 覆盖阶段 | 建设状态 |
| --- | --- | --- | --- | --- |
| 大纲域 | `abzu-outline` | `/abzu-outline` | 立项、设定、全书总纲 | **阶段一（规格步）资产已建（088）** |
| 卷纲域 | `abzu-volume` | `/abzu-volume` | 单卷规划与收卷判断 | 未建 |
| 正文域 | `abzu-write` | `/abzu-write` | 章纲与章节撰写 | 未建 |

## 二、调用形态（入口唯一）

1. **入口唯一**：skill 本名即命令——`/abzu-outline`（大纲）／`/abzu-volume`（卷纲）／`/abzu-write`（正文），由宿主斜杠菜单原生补全，无需命令薄代理。
2. **自然语言模糊触发禁止**（机制层）：`SKILL.md` frontmatter 设调用控制键 `disable-model-invocation: true`，保留显式调用与 `/` 菜单可见；键名与语义以宿主官方文档为准。**实测已完成且两处计算方式同批订正**（本处与 `docs/standards/skill资产标准.md` §3）——宿主 Claude Code 2.1.270（2026-09-15）：菜单可见（装后须重载窗口）、模型侧技能名单不含本域（自主触发被抑制）、宿主接受该键而生态参考校验器拒收（本仓保留，仅作规范符合度参考）；键定义的单点权威在 `docs/standards/skill资产标准.md` §3。
3. **双轨缺一不可**：description 触发句是文案层、调用控制键是机制层——只有文案等于靠模型自觉。
4. **域间禁互调**：skill 之间禁止互相调用；跨域只经写入文件文件衔接。
5. **命令薄代理（预留）属 user-invoked 编排层**：只可调用域 skill，域 skill 永不反向调用薄skill 主文件或其他域 skill；启用前不得新增实例。

## 三、域间衔接（唯一接口）

- **域是平行的门，不是管道**：跨域无顺序锁，大纲可反复打磨、随时回改；唯一依赖是文件账本律的产物检查（缺产物＝提示，不拦截）。
- **生产者只写入文件，消费者定义读取**（对应 Pipes and Filters 架构模式与数据耦合：每个 filter 只知输入输出，不知管道中其他 filter；域间只通过写入文件通信，零调用、零预定义消费行为）：跨域只经写入文件衔接，域间**禁互调**——生产者的产物按共享约定写入文件，如何查找与读取由消费方在自己域内定义（通用细则归 `docs/standards/skill资产标准.md` §5）。

大纲域 → 卷纲域的交接清单（定格态）与衔接细则见[书目录契约](书目录契约.md) §3。

## 四、成长路径

### 1. 承载架构（选型理由）

**决定性判定标准：三域共享同一份可变状态**（写作项目的 `基本规格.md`／`创作进度.md`／手稿）——共享资产的归属方式是单 skill 与多 skill 两方案的分水岭。

| 维度 | 单 skill 三域（未采纳） | 多 skill 分立（现行） |
| --- | --- | --- |
| 共享资产 | 一份正本，零机制 | 需跨 skill 同步机制或内嵌副本（副本致不符） |
| 精准入口 | 3 个一行命令薄代理（一次性十分钟） | skill 本名即命令，免费 |
| 上下文 | SKILL.md 薄总控常载 + references 按需读，与多 skill 持平 | 只载命中域 |
| 版本／安装 | 一份版本号、一个目录 | 多份 frontmatter 对齐 |
| 触发 | 一条 description 收敛 | 三域同属写作场景，自然语言互抢，靠直呼纪律压制 |
| 反向迁移 | 拆出容易（先合后拆） | 合并极难 |

早期六域时期实测：合计 188 份 references／约 26,000 行、跨 skill 同步副本 64 组；三域现态未复测。早期为同步副本养字节核对与守卫一节记作沿革出处（前作不作设计依据，纪律见 `docs/standards/运行环境标准.md` §7）——规模躺在磁盘上而非上下文里：渐进披露下，单次会话只进总控 + 当前域 workflow + 两三份方法论。

逃生舱：产出侧域（大纲域／卷纲域／正文域）深度耦合共享状态，不拆。

### 2. 拆分触发器

内容量增长（方法论／知识库／脚本扩充）不构成拆分理由——渐进披露下内容躺磁盘不进上下文；且共享约定随域增加而增值（单副本被更多域摊薄）。拆分由真实需求推动，不预先构建：

- **T1**：运行时组件物化需求出现（hooks／subagent 进书项目，如正文域引入评审 subagent）→ 诞生 `abzu-setup`，届时评估组件重载域是否独立。
- **T2**：外部用户提出选择性安装或市场分发需求 → 先以单插件打包整体 skill，仍不足再拆输入侧。
- **T3**：某域与书目录状态彻底解耦且需独立演进 → 可拆。

T1 补注：`abzu-setup` 只处理硬依赖（物化组件写入文件与依赖预检）；题材偏好、平台选择等软配置不进 setup，由各域工作流首用交互自行采集。共享知识库（题材卡等跨域方法论）由 setup 物化进书项目。
