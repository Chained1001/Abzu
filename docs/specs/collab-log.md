> 定位：规划方/施工方分工协作的逐次登记规格施工记录与协作模板——数据化调优协作流程（模型稳定性/粒度性价比/任务适配）。
> 纪律：每次规格施工完成（核验通过或整改）追加一条；只记录事实与数字，不写过程叙事。每满 10 条施工记录回顾一次 P1 成因分布——同源占比过半（如锚点过时）时上调规格编写核验强度或按机制事故驱动立项自动校验。**审查螺旋止损（三条，2026-09-12 立例）**：全文审硬上限 2 轮、重审只核修复面、窄域审产出照常采信——见「独立审查分身」节。**2026-09-10 补做第 10/20 行欠账**（21 行时随 034 复盘执行）：最大簇=规格层缺陷 9/21≈43%（行号指认见 034 归档规格发现 2），跨 020-025 与 031/032 复现——处置为规格编写协议两条（见「独立审查分身」节）+ 域上线验收清单的断言写法规范（034 改动 5）。**外审惯例**：外审发现先核前提再裁定（033 五项其三前提不成立——黑盒视角是特性，裁定表为范式）。**工序立例**：触发线以上无裁量、无「感觉很小」式逃逸——033/034 未送审即呈作者系旧病复发（2026-09-07 已废裁量制并立同型例），触发线以下豁免不变

## 协作模板

### 规格自审记录模板（各规格「规格自审记录」节按此七项）

1. 锚点：现状锚点逐条现场核验声明（grep/read 实做，无凭记忆）。
2. 清单完备：改动项与依据/裁定逐项对齐，无漏项。
3. 验收可判定：每条断言可机检或走查，且与改动清单不互斥；审改项对照表一行一项不合并（合并后无法逐项核验）；含零命中目标的替换文本须用阿拉伯数字回避汉字自噬。
4. 矛盾检查：规格内部与外部权威无冲突；时序依赖显式声明。
5. 术语：首现术语自带释义或指向权威文件。
6. 节号复核：规格内「某文档 §N」引用逐个现场核对（复盘立例）。
7. 涟漪清单：域建设批须 grep 域上线验收清单本域词 + 列全该域触及的设计文档节（031 漏改场景 7 立例）。
（既有规格自审含「字段生产策略」等专项条目者，接续本七项编号）

### 施工提示词（分身为默认形态；外部窗口为备选）

```
你是施工分身。任务：按规格施工 {规格路径}。你没有 git 写权限，也无需尝试提交；完成后只输出核验请求。

1. 先读 AGENTS.md（宪法）与规格全文，再动手。
2. 严格按规格「文件级改动清单」施工——每条带自由度标记：[A] 逐字执行、[B] 按方向自定实现（不得改变行为）、[C] 按验收标准执行。
3. 偏差分级：P0 阻塞型（规格与现状冲突，继续会做错）→ 立即停下，输出全部改为偏差报告；P1 观察型（不影响施工）→ 继续施工，记入核验请求偏差记录。
4. 规格「禁止事项」为硬边界：禁止触碰清单外文件、禁止运行联网采集。
5. 全部完成后输出【核验请求】——首行摘要（{改动 N 项｜验收 a/b 绿｜P1×n}），整段包在单个代码块里：改动清单逐文件对照规格、验收标准逐条自跑结果、偏差记录（P1）、未决问题。

外部窗口备选形态：作者在另一窗口施工时，首句身份改为「你是施工方」，其余逐字不变（2026-09-11 作者裁定翻回分身默认——审核与施工在规划方会话内闭环；施工方的【核验请求】与规划方的整改提示词由规划方在会话内直接接续）。
```

**分身可续性**：规划方 spawn 施工分身时若预期后续整改，应以**后台** spawn（前台 spawn 的分身结束后不可续，整改只能重新 spawn）；**审查分身一律只读**，不得承接整改或施工。

```
你是独立审查分身（fresh context，评审者与创作者分离）。任务：审查规格 {规格路径} 的成稿质量。你不施工、不修改任何文件，只读只查；完成后只输出审查报告。
```

## 核验协议（规划方执行）

> 判定标准来源：具体断言以各规格「验收标准」节为准（立法在先）；本协议定义核验动作与判定细则。

### 第一步 · 改动面核对（最强一道闸）

- 文件白名单：`git status --short` 必须且仅显示规格清单允许的文件——多出任何一个 = P0，整份打回
- 副作用文件口径：被 `.gitignore` 忽略的临时产物（`.tmp/` 等，红线 2 已辖）不计 P0；untracked 且未忽略的新文件须对应规格预期的新增产物，否则仍 P0
- 改动类型：`git diff` 逐 hunk 审查，只允许规格「文件级改动清单」声明的改动类型；任何逻辑行变动（函数/URL/字符串拼接/流程）= 打回
- [A] 级条目：与规格给出文本 diff 为零，一字之差即偏差
- 未动文件：规格声明"不得触碰"的文件必须零 diff
- 批次扩展：核验后批次若扩展（规划方顺手修正/追加固化），验收断言须在最终工作树复跑一遍并记录
- 机械化入口：预验器的核验比对模式（`--verify <规格路径>`）的改动面比对项（声明集 ↔ 实际改动集双向差集）；工具只作机器比对，判因与裁决仍归本步。

### 第二步 · 验收命令独立重跑（不信施工方报告）

- 规格验收标准的每条命令用规划方自己的会话重跑；施工方自跑结果只作参考
- 退出码不经管道吞掉（宪法反模式 #6）
- 机械化入口：预验器的核验比对模式（`--verify <规格路径>`）的「过程产物三件」与「施工记录表结构」两项——未落过程产物即核验未完成。

### 第三步 · 内容双轨抽查（§3.6）

- 结构轨：由 grep 类断言覆盖
- 内容轨：按下方「审查维度七分」矩阵逐维过（③b 内容质量/④跨文件一致/⑤完整性/⑥规范健康度）——**③b/⑥ 触发线以上由产物审查分身执行**（见「产物审查分身（施工产物审查，默认工序）」节），④/⑤ 由规划方通读对照；触发线以下 ③b 归规划方通读、⑥ 免跑并声明

### 审查维度七分（内容轨的完整检查矩阵）

| 维度 | 审什么 | 检测手段 | 执行者 |
| --- | --- | --- | --- |
| ① 结构合规 | 命名/位置/层级/序号——对照 file-conventions | lint + grep | 命令 |
| ② 格式合规 | 排版/引号/加粗密度/占位符——对照 markdown-style | lint + grep | 命令 |
| ③a 内容残留 | 上游残留/批次号/旧概念词/过时指向 | grep + 通读 | 规划方 |
| ③b 内容质量 | 语义通顺/逻辑自洽/数字一致/事实相符/无断裂截断 | **仅 LLM 语义审**（不可机械自动化） | **产物审查分身**（触发线以上）／规划方通读（触发线以下） |
| ④ 跨文件一致 | 同概念不同文件表述一致（术语/数字/路径） | 通读 + 对照 | 规划方 |
| ⑤ 完整性 | 必备节序齐全/无孤儿字段/引用闭合 | 逐节核对 | 规划方 |
| ⑥ 规范健康度 | 规范条文本身是否被现实违反/是否有条文过时 | **仅 fresh 分身能做**（规划方有确认偏袒） | **产物审查分身**（触发线以上必派；以下免派并声明） |

**③a/③b 分界**：残留是"有没有不该在的"（模式可 grep）；质量是"在的东西对不对、通不通"（需语义理解）。两类检测手段、执行者、可靠度完全不同，必须分开定义。

**③b 不可机械自动化**：语义断裂、逻辑矛盾、数字与规则打架——均需 LLM 语义理解才能发现，grep/lint 无法覆盖。这是 subagent 审查的独占价值所在。（触发线以下的批次由规划方通读、⑥ 免跑，此独占价值相应降级——故「全绿」汇报须声明 ⑥ 未跑）

**维度⑥ 仅 fresh 分身可做**：规划方知道自己"为什么这么写"，看不见自己规范里的过时与矛盾（实证：中央路由退役后 skill-writing 理念层残留——规划方三轮审计未发现，fresh 分身首跑即报）。

### 当批开放项核对（核验结论前必做）

- 当批产生的欠账（搁置项、开放项、候选）须**当批修完**；修不完的写进**当批规格的「开放项」节**——**无落点即核验未完成**（规格随验收归档，由 git 历史承载）。**禁止**把欠账改成台账式清单重建（宪法 §6「不做全域欠账清单」条）：**债跟着主题走，不跟着时间走**——机检／工具类的长期缺口写进 `docs/standards/testing.md` §四 已知缺口，协议／协作／流程类写进本件「已知缺口（协议与协作类）」节，规范文本类写进该主题规范件的「待收口」注，构想与路线进《产品与技术总纲》§五 路线与阶段。
- 当批若触及某长期缺口条目的触发条件（域立项／发布／T1 触发／多域上线），须核对该条目并更新触发条件或结清——否则触发到来时无人观测（该条取代原台账的「冻区解冻」机制；原「销账须记销账依据」同义保留：结清时在当批规格或本件缺口行注依据）
- 反例：036 批审计 F11 发现 AGENTS.md 域状态句过时，仅记于 README Roadmap 一行 checkbox 而未处置，此后 9 批未处理——该反例即本条立例依据

### 结论三态

- 全绿 → 报告通过，请求作者确认提交（pre-commit hook 双保险）
- 有问题 → 出【整改提示词】（问题逐条 + 整改范围 + 禁止扩大）
- 规格自身缺陷 → 【裁决请求】呈作者

### findings 处置与分歧升级阈值

| 级别 | 判定 | 处置 | 谁决 | 实例 |
| --- | --- | --- | --- | --- |
| P0 违规 | 违反规格/宪法红线，继续会做错 | 规划方立即修，commit 时作者确认 | 规划方 | 016 审查 F1：锚点前提与现状不符（013 尾注已存在，外审误报被分身抓出） |
| P1 存疑 | 规格含糊/边界模糊/不影响施工 | 按最合理理解执行 + 标注假设 + 核验请求中申报 | 规划方裁定，作者可推翻 | 015 D1：验收预期 CHANGELOG 命中但清单无此条（规格内部矛盾） |
| P2 建议 | 风格/优化/不影响正确性 | 记录，不阻塞 commit | 规划方 | 016 审查 F6：两处替换文本对同一对象表述不一致 |

**分歧升级**：规划方与施工方对同一 finding 的性质或修法有分歧时 → 升级为【裁决请求】呈作者。**禁止**规划方自行压制施工方的 P0 报告，或施工方擅自将 P0 降级为 P1。

### 边界声明

核验通过 = 按规格改了、语法没坏、文档合规、没越界；**不等于运行时行为验证**——需要联网/真机验证的，归实测阶段（由作者执行）。「全绿」同理**不等于没问题**——仅覆盖已检项与已知模式（宪法 §3.6 扫描只能证伪），汇报全绿时须同时声明已检范围。

### 独立审查分身（规格成稿审查，默认工序）

非平凡规格（改动清单 ≥5 项或含 [B]/[C] 级）成稿后、交作者确认前，规划方**必须** spawn 独立审查分身（fresh context，不经规划方意图污染）通读规格本身——重点核查：锚点真实性、清单完备可执行、验收可判定、内部矛盾。判据核心：评审者与创作者必须为不同上下文，防意图污染与自审偏袒（详见 [agent-design](../standards/agent-design.md) §三）。分身只回报 findings；报告须经规划方复核后采纳（分身也会误报），采纳的修订入规格后才交作者确认。触发线以下的规格（改动清单 <5 项且全部 [A]）豁免送审，随批次照常核验；触发线以上（≥5 项或含 [B]/[C]）一律必须送审，无裁量。断言类检查仍由命令执行。本机制为开发工具链用法，不属 T1 运行时物化（不违 agent-design 的 T1 禁令）。（2026-09-07 改立：原「可选增强、重大时启用」的裁量制被事故证伪——013 中央路由残留规划方三轮自审未发现、fresh 分身首跑即报；015 规格内部矛盾自审漏检、施工分身抓出；「是否重大」由规划方自己裁量等于永不触发，反模式 #9 变体。首例 dogfooding：016 号规格即按新工序先审后施。）

**规格编写协议**（2026-09-10 复盘立例，随触发线一并守）：

- **断言预验强制**：规格送成稿审查前必跑 `python scripts/check_spec_assertions.py <规格路径>`，预验摘要（含 SKIP 项）附入规格自审记录——工具系 020-025 断言自噬守卫化产物，032 两发自斥复发的根因即未跑。**另：静态自检阶段**（自噬预警 + 计数实跑重算）一并跑——其「计数不符」退出 1、「基线漂移」与「自噬预警」只呈报，动态阶段仍恒 0；**该阶段另含检查 C／D**（[A] 项「替换为」侧文本逐字落实核对、规格写作四类机械检查），二者亦非阻断、不影响退出码；细则以本协议条为单点权威，脚本头注只记契约要点。立例依据：047 初稿 §二.5 行内替换句复述断言 token 致预测 2 与到位 1 互斥（§八 已记修法）。
- **节号复核**：规格内一切「某文档 §N」引用，写时现场 grep 该节标题半句核对——锚点节号失准三发（归档规格 031/032 审查记录）均为凭印象所致。
- **计数必须实跑**：规格中任何数字（行数/条数/命中数/改动项数）必须用 `wc -l` / `grep -c` 实数，禁止目视估计——039 五轮审查计数错 ≥5 发，全部是 AI 用眼睛做算术（2026-09-11 立例）。
- **断言字面比对**：验收断言的 grep token 写完后必须在替换文本中 `grep` 确认：①token 在替换文本中存在 ②token 不会因替换文本自身的内容被意外命中（如替换文本含「其余七组」→grep「七组」又命中——汉字数字回避：替换文本中与零命中目标同字面的汉字数字改用阿拉伯数字）（2026-09-11 立例，039 断言互斥 ≥8 发）。
- **替换范围显式限定**：「整段替换」「整行替换」指令必须写明「只替换 XX 括注和 XX 句，其余原样保留」——不限定则 [A] 级施工会删掉不该删的既有内容（039 改动 2 差点删六项产物要素，两轮审查才拦住）（2026-09-11 立例）。

**审查螺旋止损**（2026-09-12 立例；承 2026-09-11「B' 路径」并放宽其触发条件）：

- **全文审硬上限 2 轮**：同一规格的全文审最多 2 轮（初稿一轮、修订后一轮）；第 3 轮起只允许「微修已知项 + 呈作者」，不得再开全文审。规格前提失效时走**作废重出**（移入 archive 并标废，有效内容另批重新锚定后重出），不在失效前提上反复续修。
- **重审只核修复面**：P0 ≥2 后的重审只核「原 P0 修复项 + 其直接影响面」，**不重开全文审**。窄域审仍须逐条实跑自证（附命令输出），其结论与全文审等效——不因「只核了 diff」而重开全文审求心安。
- **触发条件**：本条适用于**任意 P0 族**（不限计数／断言互斥／范围失控三类）——原「B' 路径」的窄触发条件在实践中不敷用（046 批七个 P0 跨形态闸、退出码、锚文本、计数多类）。

（立例依据：039 六轮 58f、046 四稿、043/044 一审 23f 后整稿重写；047 窄域复审 8 次工具调用即抓出 2 处新问题——窄域审的判别力已实证。）

审查是兜底不是替代——规划方对初稿质量负首要责任（铁律自审）；审查 findings 中 P0 ≥2 时，修订后须重新送审一次再交作者确认——该次重审按上方「审查螺旋止损」条只核修复面，不重开全文审。（2026-09-07 外审立例：防「反正有分身审查」的初稿放水。）

### 产物审查分身（施工产物审查，默认工序）

触发线**同规格成稿审查**（见「独立审查分身（规格成稿审查，默认工序）」节，不另立数值真源）——施工完成、规划方核验三步中的第一步·改动面核对、第二步·验收命令独立重跑走完之后，规划方**必须** spawn 产物审查分身（fresh context，未参与本批规划与施工）审产物的 ③b 内容质量与 ⑥ 规范健康度。判据核心同前：规划方看不见自己规范里的过时与矛盾（维度⑥ 实证见「审查维度七分」节）。分身只回报 findings；报告须经规划方复核后采纳（分身也会误报）。**触发线以下**（即规格成稿审查的豁免侧）免派：③b 由规划方通读，**⑥ 免跑——但汇报「全绿」时须显式声明 ⑥ 未跑**（承「边界声明」节）。**分身不复用**：同一批次的独立审查分身（规格成稿审查）与产物审查分身必须为两个独立 fresh 分身——对象不同（规格 vs 产物）、时点不同（施工前 vs 施工后），复用会把施工期上下文带进产物审查。**修复后复审**：产物审查 findings 中 P0 ≥2 时，规划方完成修订（自改或经【整改提示词】回施工方）后须重新派分身复审一次（对称「审查是兜底不是替代」段对规格侧的规定）——P0 ≥2 的产物一经修订，原审查的覆盖声明即失效。**报告落点**：审查报告由规划方转述入当批核验结论、逐条追加到当批规格「审查记录」节，并在施工登记行「结果」列记 findings 数。断言类检查仍由命令执行。本机制为开发工具链用法，不属 T1 运行时物化（不违 agent-design 的 T1 禁令）。
