# 协作日志（collab-log）

> **定位**：规划方/施工方分工协作的逐次登记与模板七件套——数据化调优协作流程（模型稳定性/粒度性价比/任务适配）。
> **纪律**：每次规格施工完成（核验通过或整改）追加一条；只记录事实与数字，不写过程叙事。每满 10 条施工记录回顾一次 P1 成因分布——同源占比过半（如锚点过时）时上调规格编写核验强度或按机制事故驱动立项自动校验。

## 协作模板

### 施工提示词（分身为默认形态；外部窗口为备选）

```
你是施工分身。任务：按规格施工 {规格路径}。你没有 git 写权限，也无需尝试提交；完成后只输出核验请求。

1. 先读 AGENTS.md（宪法）与规格全文，再动手。
2. 严格按规格「文件级改动清单」施工——每条带自由度标记：[A] 逐字执行、[B] 按方向自定实现（不得改变行为）、[C] 按验收标准执行。
3. 偏差分级：P0 阻塞型（规格与现状冲突，继续会做错）→ 立即停下，输出全部改为偏差报告；P1 观察型（不影响施工）→ 继续施工，记入核验请求偏差记录。
4. 规格「禁止事项」为硬边界：禁止触碰清单外文件、禁止运行联网采集。
5. 全部完成后输出【核验请求】——首行摘要（{改动 N 项｜验收 a/b 绿｜P1×n}），整段包在单个代码块里：改动清单逐文件对照规格、验收标准逐条自跑结果、偏差记录（P1）、未决问题。

外部窗口备选形态：作者在另一窗口施工时，首句身份改为「你是施工方」，其余逐字不变。
```

### 核验请求（施工方产出）

```
【核验请求】
- 摘要：{改动 N 项｜验收 a/b 绿｜P1×n}
- 规格文件：{规格路径}
- 改动清单：逐文件对照规格改动清单
- 自核验结果：验收标准逐条 + 实际执行命令与输出摘要
- 偏差记录：P1 观察型偏差（如有）
- 未决问题：需规划方裁决的点（如有）
```

### 整改提示词（核验未通过时）

```
你是施工方。上一轮施工未通过核验。
- 核验结论：{逐条列出问题}
- 整改范围：{只允许改这些文件/这些点，其余维持原状}
- 整改后重新输出【核验请求】
- 禁止扩大整改范围，禁止"顺手"改其他东西
```

### 裁决请求（呈作者拍板）

```
【裁决请求】
- 背景：{一段话说明分歧/冲突}
- 选项 A：{描述 + 代价 + 收益}
- 选项 B：{描述 + 代价 + 收益}
- 我的建议：{选 X，理由}
- 请你拍板
```

### 独立审查分身提示词（规格成稿审查用）

```
你是独立审查分身（fresh context，评审者与创作者分离）。任务：审查规格 {规格路径} 的成稿质量。你不施工、不修改任何文件，只读只查；完成后只输出审查报告。

1. 先读 AGENTS.md（宪法）与规格全文，再开始审查。
2. 重点四查：① 现状锚点真实性——规格引用的行号、原文、计数逐一到仓库实文核对；② 改动清单完备可执行——落位与自由度标注、[A] 文本自足无歧义；③ 验收标准可判定——每条能跑命令或 grep 断言，重点核对断言与规格 [A] 文本不互斥、断言对象实存、计数正确（断言自噬防护，宪法 §3.8 铁律④）；④ 内部矛盾——条款之间、与宪法既有条文之间。
3. findings 分级：P0（照做会做错）/ P1（存疑需复核）/ P2（建议）。
4. 输出【审查报告】——首行摘要（{对象}｜findings 共 N：P0:a P1:b P2:c｜结论），整段包在单个代码块里：逐条 findings（文件:位置｜级别｜问题 + 原文引用）、自核验声明（findings 逐条对源核实）、结论（通过 / 修订后通过 / 裁决建议）。
```

首例：016 号规格成稿审查（9 findings：1 P0 / 3 P1 / 5 P2，修订后通过）。

## 核验协议（规划方执行）

> 判定标准来源：具体断言以各规格「验收标准」节为准（立法在先）；本协议定义核验动作与判定细则。

### 第一步 · 改动面核对（最强一道闸）

- 文件白名单：`git status --short` 必须且仅显示规格清单允许的文件——多出任何一个 = P0，整份打回
- 副作用文件口径：被 `.gitignore` 忽略的临时产物（`.tmp/` 等，红线 2 已辖）不计 P0；untracked 且未忽略的新文件须对应规格预期的新增产物，否则仍 P0
- 改动类型：`git diff` 逐 hunk 审查，只允许规格「文件级改动清单」声明的改动类型；任何逻辑行变动（函数/URL/字符串拼接/流程）= 打回
- [A] 级条目：与规格给出文本 diff 为零，一字之差即偏差
- 未动文件：规格声明"不得触碰"的文件必须零 diff
- 批次扩展：核验后批次若扩展（规划方顺手修正/追加固化），验收断言须在最终工作树复跑一遍并记录

### 第二步 · 验收命令独立重跑（不信施工方报告）

- 规格验收标准的每条命令用规划方自己的会话重跑；施工方自跑结果只作参考
- 退出码不经管道吞掉（宪法反模式 #6）

### 第三步 · 内容双轨抽查（§3.6）

- 结构轨：由 grep 类断言覆盖
- 内容轨：按下方「审查维度七分」矩阵逐维过（③b 内容质量/④跨文件一致/⑤完整性/⑥规范健康度），可由独立审查分身执行

### 审查维度七分（内容轨的完整检查矩阵）

| 维度 | 审什么 | 检测手段 | 执行者 |
| --- | --- | --- | --- |
| ① 结构合规 | 命名/位置/层级/序号——对照 file-conventions | lint + grep | 命令 |
| ② 格式合规 | 排版/引号/加粗密度/占位符——对照 markdown-style | lint + grep | 命令 |
| ③a 内容残留 | 上游残留/批次号/旧概念词/过时指向 | grep + 通读 | 规划方 |
| ③b 内容质量 | 语义通顺/逻辑自洽/数字一致/事实相符/无断裂截断 | **仅 LLM 语义审**（不可机械自动化） | 分身或规划方通读 |
| ④ 跨文件一致 | 同概念不同文件表述一致（术语/数字/路径） | 通读 + 对照 | 规划方 |
| ⑤ 完整性 | 必备节序齐全/无孤儿字段/引用闭合 | 逐节核对 | 规划方 |
| ⑥ 规范健康度 | 规范条文本身是否被现实违反/是否有条文过时 | **仅 fresh 分身能做**（规划方有确认偏袒） | 分身 |

**③a/③b 分界**：残留是"有没有不该在的"（模式可 grep）；质量是"在的东西对不对、通不通"（需语义理解）。两类检测手段、执行者、可靠度完全不同，必须分开定义。

**③b 不可机械自动化**：语义断裂、逻辑矛盾、数字与规则打架——均需 LLM 语义理解才能发现，grep/lint 无法覆盖。这是 subagent 审查的独占价值所在。

**维度⑥ 仅 fresh 分身可做**：规划方知道自己"为什么这么写"，看不见自己规范里的过时与矛盾（实证：中央路由退役后 skill-writing 理念层残留——规划方三轮审计未发现，fresh 分身首跑即报）。

### 结论三态

- 全绿 → 报告通过，请求作者确认提交（pre-commit hook 双保险）
- 有问题 → 出【整改提示词】（问题逐条 + 整改范围 + 禁止扩大）
- 规格自身缺陷 → 【裁决请求】呈作者

### findings 处置与分歧升级阈值

| 级别 | 判定 | 处置 | 谁决 | 实例 |
| --- | --- | --- | --- | --- |
| P0 违规 | 违反规格/宪法红线，继续会做错 | 规划方立即修，commit 时作者确认 | 规划方 | 016 审查 F1：锚点前提与现状不符（013 尾注已存在，外审误报被分身抓出） |
| P1 存疑 | 规格含糊/边界模糊/不影响施工 | 按最合理理解执行 + 标注假设 + 核验请求中申报 | 规划方裁定，作者可推翻 | 015 D1：验收预期 CHANGELOG 命中但清单无此条（规格内部矛盾） |
| P2 建议 | 风格/优化/不影响正确性 | 记录，不阻塞 commit | 规划方 | 016 审查 F6：两处替换文本对同一对象表述不一致 |

**分歧升级**：规划方与施工方对同一 finding 的性质或修法有分歧时 → 升级为【裁决请求】呈作者。**禁止**规划方自行压制施工方的 P0 报告，或施工方擅自将 P0 降级为 P1。

### 边界声明

核验通过 = 按规格改了、语法没坏、文档合规、没越界；**不等于运行时行为验证**——需要联网/真机验证的，归实测阶段（由作者执行）。「全绿」同理**不等于没问题**——仅覆盖已检项与已知模式（宪法 §3.6 扫描只能证伪），汇报全绿时须同时声明已检范围。

### 独立审查分身（规格成稿审查，默认工序）

非平凡规格（改动清单 ≥5 项或含 [B]/[C] 级）成稿后、交作者确认前，规划方**必须** spawn 独立审查分身（fresh context，不经规划方意图污染）通读规格本身——重点核查：锚点真实性、清单完备可执行、验收可判定、内部矛盾。判据核心：评审者与创作者必须为不同上下文，防意图污染与自审偏袒（详见 [agent-design](../standards/agent-design.md) §二）。分身只回报 findings；报告须经规划方复核后采纳（分身也会误报），采纳的修订入规格后才交作者确认。触发线以下的规格（改动清单 <5 项且全部 [A]）豁免送审，随批次照常核验；触发线以上（≥5 项或含 [B]/[C]）一律必须送审，无裁量。断言类检查仍由命令执行。本机制为开发工具链用法，不属 T1 运行时物化（不违 agent-design 的 T1 禁令）。（2026-09-07 改立：原「可选增强、重大时启用」的裁量制被事故证伪——013 中央路由残留规划方三轮自审未发现、fresh 分身首跑即报；015 规格内部矛盾自审漏检、施工分身抓出；「是否重大」由规划方自己裁量等于永不触发，反模式 #9 变体。首例 dogfooding：016 号规格即按新工序先审后施。）

审查是兜底不是替代——规划方对初稿质量负首要责任（铁律自审）；审查 findings 中 P0 ≥2 时，修订后须重新送审一次再交作者确认。（2026-09-07 外审立例：防「反正有分身审查」的初稿放水。）
