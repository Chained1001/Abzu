# 施工机制

> 定位：开发批次的流程纪律——工作方式、核验、机器检查、审查、提交；协作与流程类规则的单点权威。
> 适用范围：**开发侧**——读者是开发者与开发用的 AI 工具，本件不随产品安装分发；产品运行在 Claude Code 上（`/{skill 名}`），与本文无关。

**四步总览**：准备（§一 定角色、§二 AI 建议＋作者拍板）→ 执行（改）→ 自查（§三 核验／§四 机器检查／§五 审查）→ 归档（§七 提交）；偏差走 §六。

## 一、角色与职责

- **作者**：裁决位——提交确认（红线 1）、重大分歧裁决、治理微调的会话内逐项确认。
- **执行 AI**：默认规划与施工合一，在作者的主会话内完成勘察、改动、自查与呈报。
- **审查位**：独立上下文的只读审计，按风险触发（§五）；不承接整改、不复用施工上下文。

**实跑批式纪律**：断言与检查一律批式——一个脚本一次跑完一次输出（每行三列：命令／实测／期望），禁逐条单跑。

## 二、工作方式

**每次动手前，AI 先呈报建议，作者拍板**：

```
任务下达 → AI 评估（改动量＋涉及面）→ 呈报建议（「建议直接干」或「建议先写方案」＋理由）
→ 作者裁定 → 执行
```

AI 的建议依据：

| 情况 | 建议方向 |
| --- | --- |
| 改动小、涉及面窄（≤5 件、不动核心规则） | 建议直接干 |
| 改动大（>5 件）或动核心规则／架构／检查器／`AGENTS.md` | 建议先写方案 |
| 介于两者之间 | 呈两种选择的利弊，由作者定 |

作者可随时 override AI 的建议（「直接干」或「先写方案」）——作者有最高裁定权。

**直接干**：改 → `check.sh` 全绿 → git commit → 呈报。

**方案先行**：AI 写方案（现状位置／改动清单／验收断言——三要素缺一不成）→ 作者确认 → 执行 → `check.sh` 全绿 → commit。方案可在会话内呈报或落 `docs/specs/` 文件（验收后移入 `archive/`）。

**断言写法七条**：①写进方案前实际跑一遍；②计数禁目视估计；③断言与替换文本不互斥；④替换范围写明「只替换 XX」；⑤一条断言一条命令一个期望值；⑥等价性断言排除本批改动件；⑦扫描类断言排除方案本身。

**触检查脚本／标准条文／`AGENTS.md` 的批次**：另做 §四 同步更新核对。

**真机试跑**：仅当改动**用户可观测行为**时必跑。

## 三、核验与登记

**核验**（每批收尾）：

1. `git diff` 逐块对照任务范围——范围外文件＝先呈报，不得顺手带入。
2. `bash scripts/check.sh` 全绿。

**修订工具律**：仓内批量文本修订一律经 `scripts/patch_file.py`（四段式：匹配校验 → lint 检查 → 写盘 → 回读核验）；禁手写长串匹配临时脚本；宿主 Edit 工具不受此辖，但改前 `grep` 取原文。

**登记**：`CHANGELOG` 只落**用户可感知的变更**（skill 新功能、行为变化、bug 修复、破坏性修改）；内部治理改动不进 CHANGELOG，git commit message 即为记录。

**踩坑记录**：修完错后在[《施工问题记录》](施工问题记录.md)加一行；沉淀由作者发起。

## 四、机器检查

- 段序与段现状以 `scripts/check.sh` 头注为准（`# [N]`＝已实现、`# TODO: [N]`＝待建）。
- 何时必须跑：改任何文件后必须全绿（pre-commit 自动执行）。有红先判因再改。
- **红起点**：已实现段判为失败＝红；「未建设」不计红；候选类发现不算失败。
- 守卫纪律：零外部依赖、不跑 LLM、不联网；**禁止改断言、改数字、删检查来变绿**。
- 边界声明：全绿不等于运行时行为已验证——扫描只能证伪不能证真。
- **改检查项时同步两处**：① `check.sh` 头注 ② 被改工具的 docstring。（其余三处——AGENTS §七、标准件 §三 表、已知限制注释——改完顺手核，不强制。）

## 五、审查（按风险分级）

**默认（直接干）**：无前置审查；作者看 diff 即审查。

**事后审计（按风险触发）**：触规则／结构／契约、动标准条文、或 >10 件的大改动——派一个只读 subagent 看 diff 与守卫输出，报告 ≤500 字符。审计不循环——发现问题→修→复审只看修复面（上限一轮）；分歧升级作者。

**方案先行批**：方案确认前作者自审（或派成稿审查）＋施工后事后审计。

## 六、偏差处理

| 级别 | 判定 | 处置 |
| --- | --- | --- |
| P0 阻塞 | 与现状冲突、或违反红线，继续会做错 | 立即停手，呈报作者裁定后重做 |
| P1 观察 | 含糊、边界模糊，不影响执行 | 按最合理理解执行＋标注假设＋申报 |
| P2 建议 | 风格／优化，不影响正确性 | 记录，不阻塞 |

分歧升级：执行 AI 与审查位有分歧时呈作者；禁止压制 P0 或擅自降级。

## 七、提交

- **git 默认只读**（红线 1）：每次 commit／push／tag 须作者单独确认；AI 不自建分支。
- 提交前：`check.sh` 全绿（pre-commit 自动执行）。
- `git add` 逐路径（**禁 `git add -A`**）；未跟踪件先 `git add` 再 commit；提交后 `git show --stat` 复核。
- 提交信息：`type(scope): 主题`；type ∈ {feat, fix, docs, chore, test}。
- 方案先行的件验收后移入 `docs/specs/archive/`（原则只读，移动不留副本）。
