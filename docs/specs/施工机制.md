# 施工机制

> 定位：开发批次的流程纪律——三种工作模式、subagent 规则、核验、机器检查、提交、模板；协作与流程类规则的单点权威。
> 适用范围：**开发侧**——读者是开发者与开发用的 AI 工具，本件不随产品安装分发；产品运行在 Claude Code 上（`/{skill 名}`），与本文无关。
> 依据：早期版本 `AGENTS.md` 与协作模板全套条文（逐条迁移并通用化）；2026-09-17 效率重构——三模式制立为默认组织方式。

## 一、角色与职责

- **作者**：裁决位——模式拍板、规格确认、提交确认（红线 1）、重大分歧裁决。
- **执行 AI**：主会话内的执行者——勘察、定模式、改动、自查、派发 subagent、呈报。
- **审查位**：独立上下文的只读审计，不承接整改、不复用执行上下文。

**实跑批式纪律**：断言与检查一律批式——一个脚本一次跑完一次输出（每行三列：命令／实测／期望），禁逐条单跑。

## 二、三种工作模式

**每次动手前，AI 先定模式并呈报，作者拍板**。模式取机械值，不取自述。

| 模式 | 触发判定标准（按改动清单实算） | 审查位 | 相对成本 | 适用 |
| --- | --- | --- | --- | --- |
| **简单** | 件数 ≤3 ∧ 不触规则／检查器／`AGENTS.md` | 0 | 1× | 错别字、格式、单点修正 |
| **标准** | 件数 4–10 ∨ 触规则／检查器／`AGENTS.md` | 1（事后审计） | 2–3× | 常规批、条文修订 |
| **全量** | 件数 ＞10 ∨ 跨域 ∨ 作者指定 | 2（成稿审查＋产物审查） | 5–8× | 大重构、跨域改造、高风险 |

**判定标准说明**：

- 「触规则」＝改标准件条文或 `AGENTS.md`；「触检查器」＝改 `scripts/check*.py`／`check.sh`。
- 跨域＝一批内改动横跨两个及以上域（如治理＋产品）。
- 作者可随时改模式（「这批按全量走」「直接改就行」）——作者有最高裁定权。
- **批内混装按最重项定模式**：一批内只要有一项不满足低模式条件，全批按高模式走，不得拆项规避。

## 三、各模式流程

### 1. 简单模式（0 个 subagent）

```
AI 定模式并呈报 → 作者拍板 → 改 → check.sh 全绿 → git commit → 呈报
```

- 不写规格、不派审查位；作者看 diff 即审查。
- 触发条件为「≤3 件 ∧ 不触核心」时，AI 无须呈报利弊，直接报「建议简单模式」即可。

### 2. 标准模式（1 个 subagent）

```
AI 定模式并呈报 → 作者拍板
  → AI 写规格（三要素）→ 作者确认
  → 改 → check.sh 全绿
  → 派 1 个事后审计 subagent → 按其结论修（若有）
  → git commit → 呈报
```

- 规格可在会话内呈报，也可落 `docs/specs/` 文件（验收后移入 `archive/`）。
- 事后审计只看 `git diff` 与守卫输出，不看创作过程。

### 3. 全量模式（2 个 subagent，依次派）

```
AI 定模式并呈报 → 作者拍板
  → AI 写规格（三要素＋自审五条）
  → 派 1 个成稿审查 subagent（审规格本身）→ 按结论修规格
  → 作者确认
  → 改 → check.sh 全绿
  → 派 1 个产物审查 subagent（审产物）
  → 按其结论修 → git commit → 呈报
```

- 两个审查位**依次**派（成稿审查在前、产物审查在后），不得并行——后者的对象是前者确认过的规格所产出的产物。
- 若产物审查发现 P0 ≥ 2，修订后**只跑修复面复审**（不重开全文审），复审上限一轮。
- 作者不在场时的施工：另派施工 subagent（见 §四），此时共 3 个 subagent。

## 四、Subagent 规则

**判定标准核心**：评审者与创作者必须是**不同上下文**。执行 AI 知道自己为什么这么写，看不见自己规范里的过时与矛盾——独立上下文审查是唯一能抓出这类问题的手段。

### 1. 三种角色

| 角色 | 何时派 | 做什么 | 权限 |
| --- | --- | --- | --- |
| **施工** | 仅全量模式、且作者不在场时 | 按规格施工并自核 | 只读规格与相关文件；**不得 git 提交** |
| **成稿审查** | 全量模式：规格成稿、作者确认前 | 审规格本身——位置真实性、改动清单完备、断言可判定、内部矛盾 | 只读；不得承接整改 |
| **产物审查** | 标准／全量模式：改动完成、提交前 | 审产物——diff 与守卫输出 | 只读；不得承接整改 |

### 2. 派发规则

- **一次只派一个**：每个模式的审查位逐个派，不并行；全量模式按 §三 顺序（成稿审查 → 产物审查）。
- **一律后台 spawn**：后台可续（补修直接对同一 agent 续发指令，无须重派）、不阻塞主会话。
- **不复用**：同一批的两个审查位必须是两个独立上下文——复用会把前段上下文带进后段。
- **只读约束**：审查位不改任何文件；发现的问题由执行 AI 改，不由审查位改。
- **回报点约定**：派发时约定回报点，执行 AI 主动取回报（后台不等于不管）。

### 3. 开工说明格式（派发时写给 subagent，固定四项）

1. **任务与对象**：审什么、对象文件清单（按「文件:节」点名，未点名的节不读）。
2. **只读纪律**：不得修改任何文件；不得执行有副作用的命令。
3. **输出格式**：按 §九 的审查报告模板。
4. **成本记录**：回报中给出本轮工具往返数。

### 4. 回报格式

按 §九 模板。执行 AI 复核回报（subagent 也会误报）后转述入呈报，并登记当批成本。

## 五、核验与登记

**核验**（每批收尾）：

1. `git diff` 逐块对照任务范围——范围外文件＝先呈报，不得顺手带入。
2. `bash scripts/check.sh` 全绿。
3. 标准／全量模式加第三步：审查位结论逐条处置（P0 必修、P1 逐条表态、P2 可记录）。

**修订工具律**：仓内批量文本修订一律经 `scripts/patch_file.py`（四段式：匹配校验 → lint 检查 → 写盘 → 回读核验）；禁手写长串匹配临时脚本；宿主 Edit 工具不受此辖，但改前 `grep` 取原文。

**登记**：`CHANGELOG` 只落**用户可感知的变更**（skill 新功能、行为变化、bug 修复、破坏性修改）；内部治理改动不进 `CHANGELOG`，git commit message 即为记录。条目限长 ≤400 字符（`check_content` `[3]` 段脚本检查）。

**踩坑记录**：修完错后在[《施工问题记录》](施工问题记录.md)加一行；总结由作者发起。

**条文立法**：新增／修改规范条文须至少附一个正例或反例；无实例者标「预立法，随首批实例校准」并附关联实例判定标准；本批触及的标准件内预立法标记逐条核，判定标准命中即同批校准或删除标记。

**成本记录**：全量模式与标准模式在呈报中给出工具往返数与周期时长（量级即可），供跨批比较。

## 六、机器检查

- 段序与段现状以 `scripts/check.sh` 头注为准（`# [N]`＝已实现、`# TODO: [N]`＝待建）。
- 何时必须跑：改任何文件后必须全绿（pre-commit 自动执行）。有红先判因再改。
- **红起点**：已实现段判为失败＝红；「未建设」不计红；候选类发现不算失败。
- 守卫纪律：零外部依赖、不跑 LLM、不联网；**禁止改断言、改数字、删检查来变绿**。
- 边界声明：全绿不等于运行时行为已验证——扫描只能证伪不能证真。
- **改检查项时同步两处**：① `check.sh` 头注 ② 被改工具的 docstring。（其余面——`AGENTS.md` §七、标准件 §三 表、脚本自身注释——改完顺手核，不强制。）

## 七、偏差处理

| 级别 | 判定 | 处置 |
| --- | --- | --- |
| P0 阻塞 | 与现状冲突、或违反红线，继续会做错 | 立即停手，呈报作者裁定后重做 |
| P1 观察 | 含糊、边界模糊，不影响执行 | 按最合理理解执行＋标注假设＋申报 |
| P2 建议 | 风格／优化，不影响正确性 | 记录，不阻塞 |

- **停手边界**：审查位与执行 AI 对同一问题分歧时，升级呈作者；禁止压制 P0 报告或擅自降级。
- **不循环**：同一对象全文审上限 2 轮；第 3 轮起只允许微修已知项＋呈作者。
- **失败回滚**：验收不通过不得改断言求绿；规格前提失效走作废重出（移入 `archive/` 并标 `-已作废`）。

## 八、提交

- **git 默认只读**（红线 1）：每次 commit／push／tag 须作者单独确认；AI 不自建分支。
- 提交前：`check.sh` 全绿（pre-commit 自动执行）。
- `git add` 逐路径（**禁 `git add -A`**）；未跟踪件先 `git add` 再 commit；提交后 `git show --stat` 复核。
- 提交信息：`type(scope): 主题`；type ∈ {feat, fix, docs, chore, test}。
- 规格验收后移入 `docs/specs/archive/`（原则只读，移动不留副本）。

## 九、模板

### 1. 规格模板（三要素，标准／全量模式用）

```markdown
# {NNN}-{YYYY-MM-DD}-{中文主题}

> 模式：{标准／全量}
> 必读输入：{本批需要读的既有文件与节}；不涉业务写「无」

## 一、现状位置（现场核过）

- {文件}:{行}：现文「{原文}」；实测计数 {N}（命令：{grep -c 类命令}）。

## 二、改动清单

| # | 文件:位置 | 改动（现状 → 目标） | 依据／裁定 |
| --- | --- | --- | --- |
| 1 | {路径}:{行} | {现状} → {目标} | {理由} |

## 三、验收断言

1. `{可直接执行的命令}` → 期望 {值}。
2. {人工试跑型}：{做法} → 判定标准 {判定标准}。
3. 过程产物：规格移入 `archive/`；`CHANGELOG` 条目已落（仅用户可感知变更）。

## 四、规格自审（五条）

1. 位置现场核过：{命令与输出摘要}
2. 断言实跑过：{命令与输出摘要}
3. 禁改文件已写明：{清单}
4. 范围与期望同源：{范围}
5. 自述有守卫：{逐句指认结果}
```

**断言写法七条**：①写进规格前实际跑一遍；②计数禁目视估计，行数＝换行符次数；③断言与替换文本不互斥；④替换范围写明「只替换 XX」；⑤一条断言一条命令一个期望值；⑥等价性断言排除本批改动件；⑦扫描类断言排除规格本身。

### 2. 审查报告模板（审查位产出，四段）

```markdown
结论行：发现的问题 共 N：P0:a P1:b P2:c

逐条：文件:行｜问题｜实测命令与输出摘要（一行）
观察项（不计入 N）：…
已读文件清单：件:节｜工具往返数：{N}
```

- 计数类发现须附实测命令与输出；未附者只作观察项。
- 总字符 ≤2,000；细节一律给指针、不复制原文。

### 3. 核验请求模板（施工位产出）

```markdown
【核验请求】
- 摘要：{改动 N 项｜验收 a/b 绿｜P1×n}
- 规格文件：{规格路径}
- 改动清单：逐文件对照规格
- 自核验结果：验收断言逐条＋实际执行命令与输出摘要
- 本轮工具往返数：{N}
- 偏差记录：P1 观察型偏差（如有）
- 未决问题：需作者裁决的点（如有）
```
