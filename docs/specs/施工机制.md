# 施工机制

> 定位：开发批次的流程纪律——三种工作模式、subagent 规则、核验、机器检查、提交、模板；协作与流程类规则的单点权威。
> 适用范围：**开发侧**——读者是开发者与开发用的 AI 工具，本件不随产品安装分发；产品运行在 Claude Code 上（`/{skill 名}`），与本文无关。
> 依据：早期版本 `AGENTS.md` 与协作模板全套条文（逐条迁移并通用化）；2026-09-17 效率重构——三模式制立为默认组织方式。

## 一、角色与职责

- **作者**：裁决位——模式拍板、规格确认、提交确认（红线 1）、重大分歧裁决。
- **执行 AI**：主会话内的执行者——勘察、定模式、改动、自查、派发 subagent、呈报。
- **审查位**：独立上下文的只读审计，不承接整改、不复用执行上下文。

**实跑批式纪律**：断言与检查一律批式——一个脚本一次跑完一次输出（每行三列：命令／实测／期望），禁逐条单跑。

## 二、三种工作模式

**每次动手前，AI 先定模式并呈报，作者拍板**。模式取机械值，不取自述。

| 模式 | 触发判定标准（按改动清单实算） | 审查位 | 相对成本 | 适用 |
| --- | --- | --- | --- | --- |
| **简单** | 件数 ≤3 ∧ 不触规则／检查器／`AGENTS.md` | 0 | 1× | 错别字、格式、单点修正 |
| **标准** | 件数 4–10 ∨ 触规则／检查器／`AGENTS.md` | 1（事后审计） | 2–3× | 常规批、条文修订 |
| **全量** | 件数 ＞10 ∨ 跨域 ∨ 作者指定 | 2（成稿审查＋产物审查） | 5–8× | 大重构、跨域改造、高风险 |

**判定标准说明**：

- 「触规则」＝改标准件条文或 `AGENTS.md`；「触检查器」＝改 `scripts/check*.py`／`check.sh`。
- 跨域＝一批内改动横跨两个及以上域（如治理＋产品）。
- 作者可随时改模式（「这批按全量走」「直接改就行」）——作者有最高裁定权。
- **批内混装按最重项定模式**：一批内只要有一项不满足低模式条件，全批按高模式走，不得拆项规避。
- **「件数」定义**：改动清单的条目数（每行一项，形如「文件:位置」）；同一文件同一节的多处改动算一项；新增或删除文件各按一项计。
- **风险升级信号**（命中任一即建议升一档，即使件数够低）：① 触红线 ② 跨域 ③ 涉数据迁移或不可逆操作 ④ 改用户可观测行为（须真机试跑）⑤ 引外部依赖或联网 ⑥ 改守卫脚本自身。
- **成本起点**：`1×` ＝ 简单模式（做 → 全绿 → 呈报）；其余倍数是相对它的量级估计，供跨批比较。

### 定模式呈报（固定四项，用弹窗请作者拍板）

动手前用 `AskUserQuestion` 弹窗呈报，四项缺一不可：

1. **任务**：一句话说清本批做什么。
2. **模式评估**：件数｜是否触检查脚本｜是否触规则面｜是否跨域。
3. **建议模式 ＋ 理由**：机械判定标准能算出就照实算；**机械判定标准兜不住时（如件数少但风险高）须明说「判定标准不适用」并给出建议与依据**，不得默默按最低模式走。
4. **三个选项**：简单／标准／全量，各带审查位数与相对成本。

**弹窗形态**：`AskUserQuestion`——header 固定「工作模式」；三选项的 description 写「审查位 N｜成本 X×｜**约 N 次工具调用／M token 量级**｜适用场景」；有明确建议时该选项标「（推荐）」并置于首位。作者可选「其他」自定（如「先只做一半」）。

**成本量级怎么估**：按改动清单条数与目标件体量粗算——简单模式约 5–15 次调用／十万级 token；标准模式约 30–50 次／百万级；全量模式约 80–120 次／三百万级（计算方式：单次审查位实测约 0.4–1.1M token）。**目的是让作者据绝对量级判断「这批值不值得走全量」**，不是精确预算。

## 三、各模式流程

> 图例：`【你】`＝需要作者出手的节点；其余节点由执行 AI 完成。**提交一律排在「呈报」之后**——`git commit` 须你单独确认（红线 1）。

### 1. 简单模式（0 个 subagent，你出手 2 次）

```
AI 定模式并呈报（弹窗）
  ↓ 【你】拍板模式
改
  ↓
check.sh 全绿
  ↓
呈报改动与结果
  ↓ 【你】确认提交
git commit
```

- 不写规格、不派审查位；作者看 diff 即审查。

### 2. 标准模式（1 个 subagent，你出手 3 次）

```
AI 定模式并呈报（弹窗）
  ↓ 【你】拍板模式
AI 写规格（三要素＋自审五条）
  ↓ 【你】确认规格
改
  ↓
check.sh 全绿
  ↓
派 1 个事后审计 subagent
  ↓
按其结论修（若有）
  ↓
呈报改动、结果与审计结论
  ↓ 【你】确认提交
git commit
```

- 规格可在会话内呈报，也可落 `docs/specs/` 文件（归档见 §八）。
- 事后审计只看 `git diff` 与守卫输出，不看创作过程。

### 3. 全量模式（2 个 subagent 依次派，你出手 3 次）

```
AI 定模式并呈报（弹窗）
  ↓ 【你】拍板模式
AI 写规格（三要素＋自审五条）
  ↓
派 1 个成稿审查 subagent（审规格本身）
  ↓
按结论修规格
  ↓ 【你】确认规格
改
  ↓
check.sh 全绿
  ↓
派 1 个产物审查 subagent（审产物）
  ↓
按其结论修
  ↓
呈报改动、结果与两个审查结论
  ↓ 【你】确认提交
git commit
```

- 两个审查位**依次**派（成稿审查在前、产物审查在后），不得并行——后者的对象是前者确认过的规格所产出的产物。
- 若产物审查发现 P0 ≥ 2，修订后**只跑修复面复审**（不重开全文审），复审上限一轮。
- **作者不在场时**（授权机制）：模式拍板与规格确认两项须**事前授权**——作者事先指定模式、事先放行规格草案；**提交不可授权**——施工 subagent 只执行到「改动完成＋自核」，执行 AI 呈报后等你回来确认提交。此时共 3 个 subagent（施工＋成稿审查＋产物审查）。

### 4. 审查后的闭环（标准／全量通用）

审查位给出结论后：

1. 按结论修——P0 必修、P1 逐条表态、P2 可记录。
2. **任何修改后重跑 `check.sh` 全绿**（审查后的修改同样是改动，不得跳过）。
3. **P0 的修复由原审查位做修复面复审**（上限一轮，逐条实跑自证）；P1／P2 的修复不强制复审。
4. 复审通过后再呈报，并请你确认提交。

## 四、Subagent 规则

**判定标准核心**：评审者与创作者必须是**不同上下文**。执行 AI 知道自己为什么这么写，看不见自己规范里的过时与矛盾——独立上下文审查是唯一能抓出这类问题的手段。

### 1. 三种角色

| 角色 | 何时派 | 做什么 | 权限 |
| --- | --- | --- | --- |
| **施工** | 仅全量模式、且作者不在场时 | 按规格施工并自核 | 可读规格与相关文件；**仅可写规格改动清单内的文件**；不得 git 提交、不得自建分支、不得改断言或守卫脚本 |
| **成稿审查** | 全量模式：规格成稿、作者确认前 | 审规格本身——位置真实性、改动清单完备、断言可判定、内部矛盾 | 只读；不得承接整改 |
| **产物审查** | 标准／全量模式：改动完成、提交前 | 审产物——diff 与守卫输出 | 只读；不得承接整改 |

### 2. 派发规则

- **一次只派一个**：每个模式的审查位逐个派，不并行；全量模式按 §三 顺序（成稿审查 → 产物审查）。
- **一律后台 spawn**：后台可续（补修直接对同一 agent 续发指令，无须重派）、不阻塞主会话。
- **不复用**：同一批的两个审查位必须是两个独立上下文——复用会把前段上下文带进后段。
- **只读约束**：审查位不改任何文件；发现的问题由执行 AI 改，不由审查位改。
- **回报点约定**：派发时约定回报点，执行 AI 主动取回报（后台不等于不管）。

### 3. 开工说明格式（派发时写给 subagent）

**审查位版（固定四项）**：

1. **任务与对象**：审什么、对象文件清单（按「文件:节」点名，未点名的节不读）。**点名面 ≤ 10 万字符**（引 `check_content.py` 既有的 `109` 批实测：点名面上限 ≈10.7 万字符/实例）；超限须先收窄点名节。
2. **只读纪律**：不得修改任何文件；不得执行有副作用的命令。
3. **输出格式**：按 §九 的审查报告模板。
4. **成本记录**：回报中给出本轮工具往返数。

**施工位版（固定五项）**：

1. **规格路径 ＋ 必读「文件:节」清单**（点名面 ≤ 10 万字符；超限须先收窄）。
2. **可写范围**：仅规格改动清单内的文件；清单外须先呈报，不得顺手带入。
3. **禁止**：不得 git 提交、不得自建分支、不得改断言、不得改守卫脚本。
4. **纪律**：P0 停手申报（禁改断言、禁改期望）；P1 继续并申报；实跑批式。
5. **回报格式**：按 §九 的核验请求模板，整段包在代码块。

### 4. 回报格式

按 §九 模板。执行 AI 复核回报（subagent 也会误报）后转述入呈报，并登记当批成本。

## 五、核验与登记

**核验**（每批收尾）：

1. `git diff` 逐块对照任务范围——范围外文件＝先呈报，不得顺手带入。
2. `bash scripts/check.sh` 全绿。
3. 标准／全量模式加第三步：审查位结论逐条处置（P0 必修、P1 逐条表态、P2 可记录）。

**修订工具律**：仓内**批量**文本修订一律经 `scripts/patch_file.py`（四段式：匹配校验 → lint 检查 → 写盘 → 回读核验）；禁手写长串匹配临时脚本。**「批量」的判定标准**：同一文件多处改动 ∨ 涉及多文件（≥2 件）∨ 同一文件改动 ≥5 处。此范围内**宿主 Edit 工具亦须满足四段式语义**（改前取原文、改后回读核验）。一次一处、单文件单点的修正不受此辖。

**登记**：`CHANGELOG` 只落**用户可感知的变更**（skill 新功能、行为变化、bug 修复、破坏性修改）；内部治理改动不进 `CHANGELOG`，git commit message 即为记录。条目限长 ≤400 **字符**（非字节；`check_content` `[3]` 段脚本检查）。

**踩坑记录**：修完错后在[《施工问题记录》](施工问题记录.md)加一行；总结由作者发起。

**条文立法**：新增／修改规范条文须至少附一个正例或反例；无实例者标「预立法，随首批实例校准」并附关联实例判定标准；本批触及的标准件内预立法标记逐条核，判定标准命中即同批校准或删除标记。

**自洽回扫**：写或改一条规则、一个状态句、一处阈值后，**回扫三处**——① 本文中描述同一事实的其他段落 ② 引用该规则的其他文件 ③ 执行该规则的检查器。三处与本文一致才算写完；不一致即「自相矛盾」，属必修。

> 事故族（反复发生）：**陈述不实**（规格与呈报里写了未核的行号／未算的复算值／不存在的写入位置——两批审查位合计抓到 9 处）｜**删符号未查消费链**（删常量或函数前未追其消费方，致守卫崩或静默失效）｜**权限与职责矛盾**（施工位写「只读」而职责是施工）｜**定位与内容矛盾**（清单写「只记未总结的」而表里有已总结行）｜**守卫与条文脱节**（检查器执行 400 字符阈值而条文已无该阈值）｜**两件规则互斥**（`AGENTS` 要求落 `CHANGELOG` 而 `施工机制` 规定内部治理不落）｜**引用悬空**（指针指向已不存在的节）。共性：改一处后没回扫它牵连的其他表述。

**成本记录**：全量模式与标准模式在呈报中给出工具往返数与周期时长（量级即可），供跨批比较。

## 六、机器检查

- 段序与段现状以 `scripts/check.sh` 头注为准（`# [N]`＝已实现、`# TODO: [N]`＝待建）。
- 何时必须跑：改任何文件后必须全绿（pre-commit 自动执行）。有红先判因再改。
- **红起点**：已实现段判为失败＝红；「未建设」不计红；候选类发现不算失败。
- 守卫纪律：零外部依赖、不跑 LLM、不联网；**禁止改断言、改数字、删检查来变绿**。
- 边界声明：全绿不等于运行时行为已验证——扫描只能证伪不能证真。
- **改检查项时同步三处**：① `check.sh` 头注 ② 被改工具的 docstring ③ **该脚本自身的「已知限制」段**（若有新增限制须同批回填）。其余面——`AGENTS.md` §七、标准件 §三 表——改完顺手核，不强制。

## 七、偏差处理

| 级别 | 判定 | 处置 |
| --- | --- | --- |
| P0 阻塞 | 与现状冲突、或违反红线，继续会做错 | 立即停手，呈报作者裁定后重做 |
| P1 观察 | 含糊、边界模糊，不影响执行 | 按最合理理解执行＋标注假设＋申报 |
| P2 建议 | 风格／优化，不影响正确性 | 记录，不阻塞 |

- **停手边界**：审查位与执行 AI 对同一问题分歧时，升级呈作者；禁止压制 P0 报告或擅自降级。
- **不循环**：同一对象全文审上限 2 轮；第 3 轮起只允许微修已知项＋呈作者。
- **失败回滚**：验收不通过不得改断言求绿；规格前提失效走作废重出（移入 `archive/` 并标 `-已作废`）。

## 八、提交

- **git 默认只读**（红线 1）：每次 commit／push／tag 须作者单独确认；AI 不自建分支。
- 提交前：`check.sh` 全绿（pre-commit 自动执行）。
- `git add` 逐路径（**禁 `git add -A`**）；未跟踪件先 `git add` 再 commit；提交后 `git show --stat` 复核。
- 提交信息：`type(scope): 主题`；type ∈ {feat, fix, docs, chore, test}。
- 规格验收后移入 `docs/specs/archive/`（原则只读，移动不留副本）。

## 九、模板

### 1. 规格模板（三要素，标准／全量模式用）

```markdown
# {NNN}-{YYYY-MM-DD}-{中文主题}

> 模式：{标准／全量}
> 必读输入：{本批需要读的既有文件与节}；不涉业务写「无」

## 一、现状位置（现场核过）

- {文件}:{行}：现文「{原文}」；实测计数 {N}（命令：{grep -c 类命令}）。
- 新增文件写「新增：{路径}（当前不存在）」；删除文件写「删除：{路径}（现文见 git）」。

## 二、改动清单

| # | 文件:位置 | 改动（现状 → 目标） | 依据／裁定 |
| --- | --- | --- | --- |
| 1 | {路径}:{行} | {现状} → {目标} | {理由} |

## 三、验收断言

1. `{可直接执行的命令}` → 期望 {值}。
2. {人工试跑型}：{做法} → 判定标准 {判定标准}。
3. 过程产物：规格移入 `archive/`；`CHANGELOG` 条目已落（仅用户可感知变更）。

## 四、规格自审（五条）

1. **位置／计数／写入位置三件现场核过**：{命令与输出摘要}——位置（行号与引文）、计数（每个数字实跑）、写入位置（点名的节／件／条目须实存）。
2. 断言实跑过：{命令与输出摘要}
3. 禁改文件已写明：{清单}
4. 范围与期望同源：{范围}
5. 自述有守卫：{逐句指认结果}
```

**断言写法七条**：①写进规格前实际跑一遍；②计数禁目视估计，行数＝换行符出现次数（与 `wc -l` 一致；末行无换行符时该行不计——断言须用 `wc -l` 同计算方式）；③断言与替换文本不互斥；④替换范围写明「只替换 XX」；⑤一条断言一条命令一个期望值；⑥等价性断言排除本批改动件；⑦扫描类断言排除规格本身。

### 2. 审查报告模板（审查位产出，四段）

```markdown
结论行：发现的问题 共 N：P0:a P1:b P2:c

逐条：文件:行｜问题｜实测命令与输出摘要（一行）
观察项（不计入 N）：…
已读文件清单：件:节｜工具往返数：{N}
```

- 计数类发现须附实测命令与输出；未附者只作观察项。
- 总字符 ≤2,000；细节一律给指针、不复制原文。

### 3. 核验请求模板（施工位产出）

```markdown
【核验请求】
- 摘要：{改动 N 项｜验收 a/b 绿｜P1×n}
```
