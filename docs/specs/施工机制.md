# 施工机制

> 定位：开发时用的流程纪律——角色、规格流程、核验、审查、止损与模板；协作与流程类规则的单点权威。
> 适用范围：**开发侧**——读者是开发者与开发用的 AI 工具，本件不随产品安装分发；产品运行在 Claude Code 上（`/{skill 名}`），与本文无关（开发／运行分野见根 [`AGENTS.md`](../../AGENTS.md) 头注）。
> 依据：旧仓 AGENTS.md §3（开发节奏与分工协作）与协作模板全套条文（来源件已随 rebuild 作废，条文逐条迁移）；来源件为多域时期内容，已通用化改写，协作模板收敛为三份。

## 一、角色与职责

协作三角色。触发条件：任何非平凡改动（§二 分流表的「标准」「重」两行）都按本节配角色。

- **规划方**（持全局上下文）：勘察现状、写规格、派生施工交底、spawn 审查分身、执行核验三步、统一提交。对规格初稿质量负首要责任——审查是兜底不是替代。
- **施工方**：只按规格施工；**无 git 写权限**，也无需尝试提交。默认形态＝规划方 spawn 的施工分身；备选形态＝作者在外部窗口施工（此时作者即施工执行者）。交付物只有一份【核验请求】（§八 模板）。
- **作者**：纯裁决位——规格确认、提交确认两处出手，重大分歧拍板（升级路径见 §六）。

分身纪律（触发条件：规划方 spawn 任一分身时逐条核对）：

- 规格获作者确认后由规划方主动 spawn 施工分身，不退回作者粘贴中转、不经外部窗口。
- 预期后续整改的施工分身必须后台 spawn——前台分身结束后不可续，整改只能重新 spawn。
- 审查分身一律只读，不得承接整改或施工。
- 发送指令前核对目标 id 的角色与可续性（反模式 #11：旧仓 044 批整改指令误发复审分身）。

## 二、规格流程（判定表与三条路径分流）

三条路径分流表。触发条件：动手改任何文件前先定路径；不确定属哪条时取较重的一条。

| 路径 | 触发条件 | 流程 |
| --- | --- | --- |
| 轻 | 单文件且 < 5 行纯措辞／格式 | 直接改 → `bash scripts/check.sh` 全绿 → `CHANGELOG` 一行 |
| 标准 | 跨文件、或增删文件、或改规则 | 勘验现状 → 写规格 → 独立审查（成稿）→ 施工 → 核验 → 请求提交 |
| 重 | 动 `skills/`、改域内流程／规则／产物契约、架构级 | 标准路径 + 产物审查 + 真机走查（真机走查仅当本批改动用户可观测行为时必跑；纯治理／底座改动不跑，豁免理由写进规格） |

- 判据来源是规格写作标准 §1 判定表：「标准」行即该表 ✅ 各行（新增／删除／重命名文件、跨文件改动 ≥ 2 文件、新增或修改规范条目、架构／流程／规则变更、外审与外部参考研究驱动的修改）；「轻」行即该表 ❌ 各行（单文件错别字／格式修正 < 5 行、复盘驱动的治理微调 ≤ 3 文件，后者豁免条件缺一不可，且另需作者会话内逐项确认——归入「轻」不免除该确认）。
- **产品层纯文档内容批**（写／改 `docs/product/` 的叙述与设计正文，不动契约字段与规则）按**标准路径**走，产物审查降为**单维核对**（见 §五）——定级判据是「改的是**叙述**还是**规则**」，不是「改了几个文件」。（实例：059／060／061 三批均为改标准／规则／结构 → 双维全审；「单维核对」一侧尚无实例，属预立法，随首批产品层内容批校准。）
- 重路径的真机走查做法与记录落点见测试与验收标准 §3，走查记录落当批规格。

规格三要素（缺一不成规格）：现状锚点／文件级改动清单／验收断言。命名与归档位置见命名标准 §2；自由度与深度分级见规格写作标准 §3。

规格自审三条（规格「规格自审」节按此写；缺任一条不得产出施工交底）：

1. 锚点现场核过——规格引用的行号、原文、计数逐条现场 `grep`／read 确认，不凭对话记忆。（反例：旧仓 014 批 3 处现状事实过时，施工时才暴露。）
2. 断言实跑过——每条验收断言写进规格前实际跑一遍（计数用 `wc -l`／`grep -c` 实数，禁目视估计），并核对断言 token 与自家「替换为」侧文本不互斥。（反例：旧仓 020／021／022 三发连击——断言吞替换文本、断言对象与计数错、零命中吞立例句字样。）
3. 禁止事项写明——逐条列出本批禁止触碰的文件与禁止动作（联网、采集、改动面外文件）。

自由度标记：`[A]` 逐字执行（一字之差即偏差）／`[B]` 按方向自定实现（不得改变行为）／`[C]` 按验收标准执行。

## 三、施工与验收（核验三步／过程产物两项）

核验三步（规划方执行；施工方的自跑结果只作参考）。触发条件：每批施工交付后、请求提交前。

1. 改动面核对（最强一道闸）：`git status --short` 与 `git diff` 逐 hunk 对照规格文件级改动清单——出现清单外文件、或未声明的逻辑行变动＝P0 打回；`[A]` 项与规格给出文本 diff 为零；规格声明不得触碰的文件零 diff。副作用口径：`.tmp/` 等被忽略的临时产物不计（AGENTS.md 红线 2 已辖）；untracked 且未忽略的新文件须对应规格预期新增，否则仍 P0。
2. 断言独立重跑：规格验收断言的每条命令用规划方自己的会话重跑；退出码不经管道吞掉（反模式 #6）。
3. 内容抽查：机检覆盖不到的内容质量与规范健康度按 §五 分工走——重路径派产物审查分身，标准路径由规划方通读抽查。

断言预验：规格验收断言必须在写进规格前实跑（§二 自审条 2）；无法预验的标注「未预验」，交成稿审查分身重点核验。

过程产物两项（非平凡改动必落；无落点即核验未完成）：

1. 规格——细节落当批规格（含「开放项」节）；验收全部通过后移入 `docs/specs/archive/`，移动不留副本。
2. `CHANGELOG`——一行结论，条目 ≤ 400 字符，只写「改了什么 + 核验结论」，细节留在规格。落 `[Unreleased]` 对应小节，版本段定稿见版本与分发标准 §3。

不建全域台账、不建施工记录表。当批欠账当批修完；修不完的写进当批规格的「开放项」节，或该主题所属标准的「机检锚点／已知缺口」行——债跟着主题走，不跟着时间走。

修复后自核验三条（谁修谁核）：① 修改已落实到位 ② 无遗漏点 ③ 无衍生新问题——三项核完才算修复完成。（旧仓教训：修复引入双空格与 `CHANGELOG` 游离行，靠 lint 与事后复核才抓回。）

## 四、机器闸（段序真源／守卫纪律）

- 段序真源＝`scripts/check.sh` 头注（唯一真源，本文件不复制段序列表）；新增检查项按头注的维护入口追加一段并同步头注。守卫全景、各段现状与已知缺口见测试与验收标准 §1／§4。
- 何时必须跑：改任何文件后 `bash scripts/check.sh` 必须全绿（pre-commit 自动执行）；提交前必跑（§七）。有红先判因再改，呈报裁决前不在红基线上叠改动（AGENTS.md 红线 6）。
- 守卫纪律：守卫零外部依赖、不跑 LLM、不联网；失败先判因——禁止改断言、改数字、删检查来变绿。
- 边界声明：核验通过／全绿不等于运行时行为已验证——仅覆盖已检项与已知模式（扫描只能证伪不能证真）；汇报全绿时须声明已检范围（哪几段已实现、哪几段待建）。

## 五、审查（成稿审查／产物审查／止损）

两个 fresh 分身位。判据核心：评审者与创作者必须为不同上下文（防意图污染与自审偏袒）——规划方知道自己为什么这么写，看不见自己规范里的过时与矛盾（旧仓实证：某机制退役后理念层残留，规划方三轮自审未发现，fresh 分身首跑即报）。

| 位置 | 何时派 | 审什么 |
| --- | --- | --- |
| 成稿审查（规格侧） | 标准与重路径：规格成稿后、交作者确认前 | 规格本身四查——锚点真实性、改动清单完备可执行、验收断言可判定（含断言与 `[A]` 文本不互斥、断言对象实存、计数正确）、内部矛盾（含与既有条文冲突） |
| 产物审查（产物侧） | **改规则／结构／契约**的批次（含重路径与动标准条文的批次）：施工完成且核验第 1／2 步走完后。**产品层纯文档内容批**改派**单维核对**——只查引用闭合、数字一致与既有条文冲突，不逐段通读 | 两个维度——内容质量（语义通顺／逻辑自洽／数字一致／无断裂截断，重点看替换边界与新旧文衔接处）；规范健康度（本次改动是否使既有条文被现实违反或过时）。**单维核对**只覆盖其中的引用／数字／冲突面 |

- 分身不复用：同一批的成稿审查与产物审查必须是两个独立 fresh 分身（对象不同、时点不同）。复用会把施工期上下文带进产物审查。
- 报告落点：审查报告经规划方复核（分身也会误报）后转述入当批核验结论，并逐条追加到当批规格的「审查记录」节——不另建台账；采纳的修订入规格后才交作者确认。
- 无裁量：标准与重路径**一律送审**，无「感觉很小」式逃逸（旧仓 033／034 未送审即呈作者系旧病复发）；**送审深度**按 §二 分级——改规则／结构／契约批双维，产品层纯文档内容批单维核对。

止损三条（审查螺旋）。触发条件：任一审查位进入第 2 轮及以上时对照本节。

1. 全文审硬上限 2 轮：同一规格全文审最多 2 轮（初稿一轮、修订后一轮）；第 3 轮起只允许微修已知项 + 呈作者，不得再开全文审。规格前提失效时走作废重出——移入 `docs/specs/archive/` 并标废（文件名追加 `-已作废`），有效内容另批重新锚定后重出，不在失效前提上反复续修。
2. 重审只核修复面：findings 中 P0 ≥ 2 时，修订后只核原 P0 修复项 + 其直接影响面，不重开全文审；窄域审须逐条实跑自证（附命令输出），结论与全文审等效。对称条款：产物审查 findings 中 P0 ≥ 2 时，修订后重派产物审查分身复审一次。
3. 本条 1／2 的触发条件由原『同类精度 P0（计数／断言互斥／范围失控三类）』放宽为任意 P0 族。

立例依据：旧仓 039 批六轮 58 findings、046 批四稿、043／044 一审 23 findings 后整稿重写；047 批窄域复审 8 次工具调用即抓出 2 处新问题——窄域审判别力已实证。

## 六、偏差与止损（P0／P1、停摆呈报、反模式清单）

偏差分级（施工方与审查分身同一口径）：

| 级别 | 判定 | 处置 |
| --- | --- | --- |
| P0 阻塞型 | 规格与现状冲突、或违反红线，继续会做错 | 施工方立即停摆，全部输出改为偏差申报（禁止顺手按自己理解改断言或改期望）；规划方裁定后重落 |
| P1 观察型 | 规格含糊、边界模糊，不影响施工 | 按最合理理解执行 + 标注假设 + 核验请求偏差记录中申报；规划方裁定，作者可推翻 |
| P2 建议 | 风格／优化，不影响正确性 | 记录，不阻塞提交 |

- 停摆呈报：施工方遇 P0 一律停摆——旧仓 044 批施工方按纪律停摆申报（规格两节计数互斥），规划方裁定后产物侧零改动。
- 分歧升级：规划方与施工方对同一 finding 的性质或修法有分歧时，升级为裁决请求呈作者。禁止规划方压制施工方的 P0 报告，或施工方擅自把 P0 降为 P1。
- 失败回滚：验收不通过不得改断言求绿；规格前提失效走作废重出（§五 止损条）；已发布版本发现严重缺陷用 bump patch 重新发布，不删除已发布 tag（版本与分发标准 §6）。

### 反模式清单（事故回填）

> 格式：「错误做法 → 正确方式 + 事故出处」。继承自旧仓的通则出处标注「继承」；本项目事故发生后按此格式回填，并同步评估是否值得引入对应守卫。

| # | 错误做法 | 正确方式 | 事故出处 |
| --- | --- | --- | --- |
| 1 | 为过检改断言／改守卫数字 | 先判因；文档数字与实测对齐 | 继承 |
| 2 | 删改机制留文档残留（或反之） | 当次全仓 grep 清理全部引用；grep 词须含概念近义词，不止原句 | 继承（旧仓 032 立法只搜原句，姊妹文档「触发关键词」措辞漏网至次日审计） |
| 3 | 模板／文档写「格式同上、参照上文」式互引 | 显式内嵌完整内容或指向真实路径 | 继承 |
| 4 | 同一规范复制多份维护 | 单一真源 + 引用，发现第二来源即收口 | 继承 |
| 5 | CI／守卫里跑 LLM 或联网 | 场景走查人工判断 + 脚本断言；守卫零外部依赖 | 继承 |
| 6 | 验收命令的退出码经管道被吞（`cmd \| tail` 后取 `$?` 是 `tail` 的） | 退出码不经管道直接取；必须接管道时取 `PIPESTATUS[0]` | 2026-09-05 lint 体检首轮误判违例数 |
| 7 | 给带 shebang 的脚本插入头部注释（把 `#!` 挤离首行） | 注释插在 shebang 之后；脚本改动后必跑语法检查（`node --check`） | 2026-09-05 移植审计发现 6 脚本语法全坏 |
| 8 | `git add -A` 后直接提交，不核对暂存内容——提交标签与实际内容不符 | 提交前必看 `git status`／`git diff --stat` 对照预期改动清单 | 2026-09-06 核验协议提交扫入施工方未验收改动 |
| 9 | 纪律靠自觉不靠机制——写完纪律条文就以为会自动执行 | 可机械化的纪律固化为工具（`check.sh`／hook／脚本），不可机械化的写明触发条件 | 2026-09-06 全天多次「该查没查／该走规格没走」（shebang、治理同步、外审未转规格） |
| 10 | 在源仓库内运行分发／安装类工具（安装器把 `skills/` 符号链接化） | 分发工具只在目标项目目录运行；仓库加真目录守卫（`check.sh` [0]）拦截 | 2026-09-07 首次真机安装实测（旧仓规格 027） |
| 11 | 把施工／整改指令发给错误对象（未核对目标 id 的角色与可续性） | 发送前核对目标 id 的角色与可续性（§一 分身纪律） | 2026-09-11 旧仓 044 批整改指令误发复审分身（即时 interrupt + 撤回，该分身回报未改动、零损失） |

## 七、提交与登记

- 提交需作者明确确认：commit／push／tag／分支等一切 git 写操作每次单独取得作者确认，作者对其他操作的授权不外延（AGENTS.md 红线 1）。AI 会话不自建分支——批次为原子单元直推 main（作者明确要求除外）。
- 提交前必跑 `bash scripts/check.sh` 且退出 0（pre-commit 自动执行，见 §四）。
- 提交前自检四项：改动未越出规格范围；验收断言全绿；术语与[术语表](../product/术语表.md) 一致；新增文件符合命名标准。
- 一域一批：一次提交只承载一个域的批次改动，跨域改动拆批。多批在制时提交前逐路径对照 `git status`，禁 `git add -A` 后直接提交（反模式 #8）。
- 提交信息用 Conventional Commits：`type(scope): 主题`；type ∈ {feat, fix, docs, chore, test}，scope 取改动作用域——skill 资产＝`skill`，单域建设＝域名（见 `docs/product/架构设计.md` §一 域清单，如 `abzu-outline`），治理文档＝`governance`，标准件＝`standards`，规格＝`specs`。
- 登记：本批收尾只核两处落点（§三 过程产物两项）——规格（含审查记录）与 `CHANGELOG` 条目；规格随验收移入 `docs/specs/archive/`。不设施工记录表。

核验请求模板（施工方产出，逐字可复用）：

```

- 规格文件：{规格路径}
- 改动清单：逐文件对照规格改动清单
- 自核验结果：验收断言逐条 + 实际执行命令与输出摘要
- 偏差记录：P1 观察型偏差（如有）
- 未决问题：需规划方裁决的点（如有）
```

施工交底必带六项（交底不设模板，规划方按本节当面撰写）：

1. 规格路径，且要求先读规格全文与 `AGENTS.md` 再动手；
2. 身份与权限：施工分身／施工方，无 git 写权限，也无需尝试提交；
3. 自由度标记语义（`[A]` 逐字／`[B]` 按方向／`[C]` 按验收断言）；
4. 偏差分级与停摆条（P0 停摆申报、禁止改断言；P1 继续并在核验请求中申报）；
5. 输出要求：完成后按上模板输出【核验请求】全文，整段包在单个代码块里；
6. 必读输入清单（逐条列本批该读的文件与节）。
