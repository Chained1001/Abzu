# 施工机制

> 定位：开发时用的流程纪律——角色、规格流程、核验、审查、止损与模板；协作与流程类规则的单点权威。
> 适用范围：**开发侧**——读者是开发者与开发用的 AI 工具，本件不随产品安装分发；产品运行在 Claude Code 上（`/{skill 名}`），与本文无关（开发／运行分野见根 [`AGENTS.md`](../../AGENTS.md) 头注）。

## 一、角色与职责

协作三角色。触发条件：任何非平凡改动（§二 分流表的「标准」「重」两行）都按本节配角色。

- **规划方**（持全局上下文）：勘察现状、写规格、派生施工交底、spawn 审查 subagent、执行核验三步、统一提交。对规格初稿质量负首要责任——审查是兜底不是替代。
- **施工方**：只按规格施工；**无 git 写权限**，也无需尝试提交。默认形态＝规划方 spawn 的施工 subagent；备选形态＝作者在外部窗口施工（此时作者即施工执行者）。交付物只有一份【核验请求】（§八 模板）。
- **作者**：纯裁决位——规格确认、提交确认两处常规出手；另有**治理微调的会话内逐项确认**（§二 轻行）与**重大分歧裁决**（§六）两类例外。

subagent 纪律（触发条件：规划方 spawn 任一 subagent 时逐条核对）：

- 规格获作者确认后由规划方主动 spawn 施工 subagent，不退回作者粘贴中转、默认流程不经外部窗口；**作者主动选择 `§八` 外部窗口备选形态时除外**。
- **施工 subagent 一律后台 spawn**——前台结束后不可续、整改只能重新 spawn；后台 spawn 不阻塞且可续（补修／整改直接对同一 agent 续发指令，无需重派）；**规划方须在交底约定回报点、完成后主动取回报**（不阻塞不等于不管）。**对外部窗口形态**（§八 备选形态）：无 subagent，本条不适用。
- 审查 subagent 一律只读，不得承接整改或施工。
- 发送指令前核对目标 id 的角色与可续性（反模式 #11：旧仓 044 批整改指令误发复审 subagent）。

## 二、规格流程（判定表与四条路径分流）

四条路径分流表。触发条件：动手改任何文件前先定路径；不确定属哪条时取较重的一条（**同时命中两条 ≠ 「不确定属哪条」**——前者按「轻」行的优先规则定（「标准 × 重」由「重」行流程含标准路径判定），后者才取较重的一条）。**本表各条豁免所依赖的自述句（路径判定／真机走查豁免／「不涉某面」等）须逐句指认核对它的机械检查；指认不出者，该自述不生效、不得据以免除任何步骤——但本句只管「本该有机械检查而没写」的自述；真源明文交给作者或人判轨的豁免（「轻」行的作者会话内逐项确认、真机走查的语义判断）不在此列，照原文执行**（真源＝`规格写作标准` §4 第 5 条；射程界定见 `106` 批成稿审查 P1-3）。

| 路径 | 触发条件 | 流程 |
| --- | --- | --- |
| 轻 | 单文件且 < 5 行错别字／格式；或复盘驱动的治理微调 ≤ 3 文件（后者豁免条件缺一不可、另需作者会话内逐项确认、**当批 `CHANGELOG` 留痕不计入**；涉 `AGENTS.md` 者不得走轻行（该件修改另须作者确认，宪法 §六.1）；与其他行命中时——**若同时命中「重」行触发条件，以「重」为准**；否则以本行为准（具体优于一般）） | 直接改 → `bash scripts/check.sh` 全绿 → `CHANGELOG` 一行 |
| 标准 | 跨文件、或增删文件、或改规则 | 勘验现状 → 写规格 → 独立审查（成稿）→ 施工 → 核验 → **（触发产物审查条件时）产物审查** → 请求提交 |
| 重 | 动 `skills/`、改域内流程／规则／产物契约、架构级 | 标准路径 + 产物审查 + 真机走查（真机走查仅当本批改动用户可观测行为时必跑；纯治理／底座改动不跑，豁免理由写进规格） |

- 判据来源是 `规格写作标准` §1 判定表：「标准」行即该表 ✅ 各行（新增／删除／重命名文件、跨文件改动 ≥ 2 文件、新增或修改规范条目、架构／流程／规则变更、外审与外部参考研究驱动的修改）；「轻」行即该表 ❌ 各行（单文件错别字／格式修正 < 5 行、复盘驱动的治理微调 ≤ 3 文件，后者豁免条件缺一不可，且另需作者会话内逐项确认——归入「轻」不免除该确认）。（轻行细则以 `规格写作标准` §1 判定表原文为准——含「`CHANGELOG` 留痕不计入」与冲突优先规则）。
- **批内混装按最重项定级**：一批内只要有一项不是逐字替换，全批走标准路径，不得拆项规避——本句是 §二 前导语的批内细化、不取代之（前导语管「整批属哪条路径」的不确定；本句管「批内混装」）。**「快」行已于 2026-09-17 退役**（机制成本研究：近 14 批头注实测**快路径 0 次使用**，仅 `105` 一次误标；其专属守卫「路径定级」随之下线，见 `测试与验收标准` §4 销号注）。
- **产品层纯文档内容批**（写／改 `docs/product/` 的叙述与设计正文，不动契约字段与规则）按**标准路径**走，产物审查降为**单维核对**（见 §五）——定级判据是「改的是**叙述**还是**规则**」，不是「改了几个文件」。（实例：059／060／061 三批均为改标准／规则／结构 → 双维全审；单维核对的实例已在册（`archive/062` §八／`archive/085` 头注＋§九）——本条已非预立法。）
- 重路径的真机走查做法与记录落点见 `测试与验收标准` §3，走查记录落当批规格。
- **小改动攒批**：发现的零散欠账与同族残留，优先**夹带进邻近批次**（写进该批改动清单与核销表），不零散开批——一批＝一次施工＋一次审查；只有触发条件独立且紧迫时才单独立批。实例：088 夹带 087 三条账与审查标出的三处同族残留。

规格三要素（缺一不成规格）：现状锚点／文件级改动清单／验收断言。命名与归档位置见 `命名标准` §2；自由度与深度分级见 `规格写作标准` §3。

规格自审五条（真源＝`规格写作标准` §4；缺任一条不得产出施工交底）：锚点／断言／禁止／范围与期望同源／自述有守卫——细则见真源。

自由度标记：`[A]` 逐字执行（一字之差即偏差）／`[B]` 按方向自定实现（不得改变行为）／`[C]` 按验收标准执行。

## 三、施工与验收（核验三步／实跑纪律／过程产物两项）

核验三步（规划方执行；施工方的自跑结果只作参考）。触发条件：每批施工交付后、请求提交前。

1. 改动面核对（最强一道闸）：`git status --short` 与 `git diff` 逐 hunk 对照规格文件级改动清单——出现清单外文件、或未声明的逻辑行变动＝P0 打回；`[A]` 项与规格给出文本 diff 为零；规格声明不得触碰的文件零 diff。副作用口径：`.tmp/` 等被忽略的临时产物不计（`AGENTS.md` 红线 2 已辖）；untracked 且未忽略的新文件须对应规格预期新增（首选 `git diff --no-index /dev/null <文件>`——不需写索引。`--no-index` 有差异时**退出码＝1 属预期**（勿按失败读）），否则仍 P0。
2. 断言独立重跑：规格验收断言的每条命令用规划方自己的会话重跑；退出码不经管道吞掉（反模式 #6）。
3. 内容抽查：机检覆盖不到的内容质量与规范健康度按 §五 分工走——**触发产物审查条件的批次（改规则／结构／契约，含重路径与动标准条文的批次）派产物审查 subagent**（轻路径批次除外——不派审查 subagent，改后由规划方自查）；产品层纯文档内容批走**单维核对**；**其余批次（不含轻路径——轻路径不写规格、不走核验三步）由规划方通读抽查**。

断言预验：规格验收断言必须在写进规格前实跑（§二 自审条 2）；无法预验的标注「未预验」，交成稿审查 subagent 重点核验。

**实跑纪律（批式）**：断言与门禁的实跑一律**批式**——断言用一个脚本一次跑完并一次输出（每行三列：命令／实测／期望）；门禁命令取尾（`bash scripts/check.sh > .tmp/<任务>/chk.out 2>&1; tail -5`）；大输出先 `head`／`tail` 收敛。

**理由**：每次工具往返都要重发整段累积上下文，逐条单跑是批内成本的主要来源（088 实测 205 次往返／~23.5 M token）。

- **适用范围**：施工方自跑、规划方核验重跑、审查方抽样实跑三处同一口径。**本节三条同辖覆盖率面与回报面**——审查方与核验方的抽样实跑、以及任何『列出所读文件与所跑命令』的回报，同按本纪律。

过程产物两项（非平凡改动必落；无落点即核验未完成）：

1. 规格——细节落当批规格（含「本批核销」（相关时）与「开放项」节）；**移动前须逐条过该件 §八 开放项与 §九 审查记录中 P0／P1 的建议；凡判为跨批可复用的教训，须先落入 `施工机制` §六 反模式表／`测试与验收标准` §4 G 表／相应标准条文正文／`AGENTS.md` 之一，并在当批规格中逐条写出所落条号；判为「仅本批一次性」者须写明理由——未逐条写出落点者不得移入 archive**。验收全部通过后移入 `docs/specs/archive/`，移动不留副本。
2. `CHANGELOG`——一行结论，只写「改了什么 + 核验结论」，细节留在规格；**条目限长的规范真源**见 `版本与分发标准` §3。落 `[Unreleased]` 对应小节，版本段定稿见 `版本与分发标准` §3。 **`CHANGELOG` 条目末尾附成本註记**：`（往返 {R}／{T}）`——**`R` 与 `T` 须落实际数值**（如 `（往返 12／1-4h；施工段 8｜审查段 4｜合计 12）`），不得照抄花括号占位；供跨批比较；不占条目限长豁免（仍受 ≤400 字符约束）。**审查记录须同批落当批规格的『九、审查记录』节**——不得留占位符（`091`／`095`／`096`／`097` 四件实测未填，属已发生偏差）。**审查记录限长（2026-09-17 立，机制成本研究）**：**每轮一行**（形如「日期｜审查位｜findings 计数｜结论｜成本字段」）、**单行 ≤ 250 字符**；findings 明细、判定理由、执行方式报备等长内容**落该件 §八 开放项或 §一 锚点，不落 §九**；**`§九` 节体量目标 ≤ 规格全文字符的 15%**（`109` 实测 **30%**＝9,730／32,292 字符，为当前最大单节，而每个施工／审查实例都被要求装载规格）。
git 历史＝提交本身（追溯第三腿，非过程产物）——不入上述两项；规格＋CHANGELOG＋git 三腿互证即每批可追溯。

不建全域台账、不建施工记录表。当批欠账当批修完；修不完的写进当批规格的「开放项」节，或该主题所属标准的「机检锚点／已知缺口」行——债跟着主题走，不跟着时间走。

**开放项核销机制**：新批规格须核对**相关归档规格的开放项**，在本批规格内逐条标五档之一（已履行／作废／本批处置／仍待／待作者，含理由）；核销落本批规格的「本批核销」节（模板见 §八），**不另建台账、不建索引件**（`AGENTS.md` §四 平行台账不做）。**本批内被处置的开放项须同批改标**（不得留到下一批核销时才改——088 批 §八 10／11／12 曾三处已履行却仍写「触发＝下批」，致下一批核销档位算错）。触发条件：**本批改动面与某归档规格有交集**（**同一文件／同一主题／同一产物**，三者任一）（**不设时间触发**）。

**修订工具律**：仓内文本修订一律经 `scripts/patch_file.py`（或其等价的四段式实现）——**禁手写长串匹配的临时脚本**；该工具把反模式 #12 的三段式固化为机制并**加一步形态闸**（四段式：锚点由**磁盘**校验、命中 0 或 >1 即中止并打印实际命中行 → **形态闸**〔`.md` 目标件对**待写入全文**跑 lint，不过即零写盘〕→ 统一写盘 → 回读核验）。触发条件：**以脚本／命令行方式做批量或长串匹配的仓内文本改动**时本条适用；**宿主自带的一次一处、要求唯一匹配的编辑工具（Edit）不受本条约束**，但改前须 `grep` 取原文（#18）。

修复后自核验四条（谁修谁核）：① 修改已落实到位（**逐条 `grep`／read 核验目标文本确在文件中，不得凭脚本输出判「已改」**） ② 无遗漏点 ③ 无衍生新问题 ④ **断言对账**：每轮修订后逐条核断言 token／期望与正文一致（**能机械化者由 `check.sh` 的规格静态自检段报——段序真源见该脚本头注**（各段现状见 `测试与验收标准` §1.1）；报不到者以此条兜）——四项核完才算修复完成。（旧仓教训：修复引入双空格与 `CHANGELOG` 游离行，靠 lint 与事后复核才抓回。）

## 四、机器闸（段序真源／守卫纪律）

- 段序真源＝`scripts/check.sh` 头注（唯一真源，本文件不复制段序列表）；新增检查项按头注的维护入口追加一段并同步头注。守卫全景、各段现状与已知缺口见 `测试与验收标准` §1／§4。
- 何时必须跑：改任何文件后 `bash scripts/check.sh` 必须全绿（pre-commit 自动执行）；提交前必跑（§七）。有红先判因再改，呈报裁决前不在红基线上叠改动（`AGENTS.md` 红线 6）。
- 守卫纪律：守卫零外部依赖、不跑 LLM、不联网；失败先判因——禁止改断言、改数字、删检查来变绿。
- 边界声明：核验通过／全绿不等于运行时行为已验证——仅覆盖已检项与已知模式（扫描只能证伪不能证真）；汇报全绿时须声明已检范围（哪几段已实现、哪几段待建）。
- **守卫变更回写清单**：改 `check.sh` 段或 `check_*.py` 的检查项时，须**同批核五处**——① `测试与验收标准` §1.1 表（该段的「管什么」与「现状」——**本项的义务真源是该表 `:18` 的既有口径注「段序变更时须同步本表」，本条扩充其触发面为「检查项变更」并引之，不另立第二载体**）② `AGENTS.md` §七 自检信号（凡述及该守卫状态者）③ **`check.sh` 头注（段行与段名为主，含用法／依赖与前置行）**（段序真源）④ **`check_*.py` 工具自身的模块 docstring**（与同件内联注释、正则实现三者一致）⑤ **各标准件 §三 机检锚点表的状态列**（**含 `测试与验收标准` 自身**——11 件标准各 1 张，与该件 §1.1 表、§一.4 缺口表为**三张不同的表**）；另并列一类「**缺口表**」——`测试与验收标准` §4 缺口表逐行描述各检查的实现状态，检查项变更时须同步。——⑤ 与「缺口表」两类为何并入：`095`／`096` 两批的 P1 均发生在该两处。触发条件：**任何检查项的新增／删除／改判据**。本清单不设守卫（回写面含语义判断，机械化成本高于收益）；漏回写按 P1 观察型处置（§六 分级）。**表达形式（2026-09-17 立，机制成本研究）**：凡本批触**检查面**（`scripts/check*.py`／`scripts/check.sh`）者，规格 §五 须含一张**「回写面对账」表**——六行，逐面给结论：① `测试与验收标准` §1.1／② `AGENTS.md` §七／③ `check.sh` 头注／④ 工具模块 docstring／⑤ 各标准件 §三 机检锚点表／＋缺口表；每行写「已回写」或「**无需**（理由）」。**判据已机械化为检查 E 的判三**（只核该表是否写出、不核结论）。

## 五、审查（成稿审查／产物审查／止损）

两个独立上下文 subagent 位。判据核心：评审者与创作者必须为不同上下文（防意图污染与自审偏袒）——规划方知道自己为什么这么写，看不见自己规范里的过时与矛盾（旧仓实证：某机制退役后理念层残留，规划方三轮自审未发现，独立上下文 subagent 首跑即报）。

| 位置 | 何时派 | 审什么 |
| --- | --- | --- |
| 成稿审查（规格侧） | 标准与重路径：规格成稿后、交作者确认前 | 规格本身四查 ＋ 报告纪律——锚点真实性、改动清单完备可执行、验收断言可判定（含断言与 `[A]` 文本不互斥、断言对象实存、计数正确）、内部矛盾（含与既有条文冲突）；**报告纪律**见表格下方的纪律行 |
| 产物审查（产物侧） | **改规则／结构／契约**的批次（含重路径与动标准条文的批次；轻路径批次除外，见 §三 第 3 步）：施工完成且核验第 1／2 步走完后。**产品层纯文档内容批**改派**单维核对**（**单维核对由独立上下文的只读 subagent 执行**——判据同 §五 判据核心句：评审者与创作者必须为不同上下文；覆盖面见本行既列三面，不逐段通读；并引本条「subagent 不复用」条） | 两个维度——内容质量（语义通顺／逻辑自洽／数字一致／无断裂截断，重点看替换边界与新旧文衔接处）；规范健康度（本次改动是否使既有条文被现实违反或过时）。**单维核对**只覆盖其中的引用／数字／冲突面 |

- **机器已覆盖面不重复**：派审查 subagent 的交底须附『本批 `[4]` 段已覆盖的面』（**面清单不复述，口径见 `测试与验收标准` §1.1**）；审查方**跳过该面**、只做机器做不到的语义面（锚点真实性／改动清单可执行性／内部矛盾／内容质量）。**不删审查面，只删重复**。
- **报告纪律**：**计数／行数／条数类发现须附实测命令与输出**（`wc -l`／`grep -c` 等）对**成稿审查／产物审查／单维核对三处审查位通用**，未附者标注「估计」且不计入 findings（只能作观察项）。
- subagent 不复用：同一批的成稿审查与产物审查（含单维核对）必须是两个独立上下文 subagent（对象不同、时点不同）。复用会把施工期上下文带进产物审查。
- 报告落点：审查报告经规划方复核（subagent 也会误报）后转述入当批核验结论，并逐条追加到当批规格的「审查记录」节。审查报告若在其**对象件归档之后**才回报（如 `091` 的双维审查 findings 在 `091` 归档后才到），按 §七 归档件纪律本不可改归档件，此时**改落『下一批规格的 §九 审查记录』并以出处件点名**（不另建台账、不破归档只读）；**例外：归档后补记**——采纳的修订入规格后才交作者确认。
- **审查记录写法三则**：① 节标题固定为『九、审查记录』；② 档位词取值只认 §六 分级表的 P0／P1／P2（表外档位词如 P3 不得使用；确需新档位须先经作者裁定并同批回写分级表）；③ 同时给出 findings 总数 N 与各档位数时，**N ＝ 各档位之和**，观察项**不计入 N**、另列。
- 无裁量：标准与重路径**一律送审**，无「感觉很小」式逃逸（旧仓 033／034 未送审即呈作者系旧病复发）；**送审深度**按 §二 分级——改规则／结构／契约批双维，产品层纯文档内容批单维核对。

止损三条（审查螺旋）。触发条件：任一审查位进入第 2 轮及以上时对照本节。

1. 全文审硬上限 2 轮：同一规格全文审最多 2 轮（初稿一轮、修订后一轮）；第 3 轮起只允许微修已知项 + 呈作者，不得再开全文审。规格前提失效时走作废重出——移入 `docs/specs/archive/` 并标废（文件名追加 `-已作废`），有效内容另批重新锚定后重出，不在失效前提上反复续修。
2. 重审只核修复面：findings 中 P0 ≥ 2 时，修订后只核原 P0 修复项 + 其直接影响面，不重开全文审；窄域审须逐条实跑自证（附命令输出），结论与全文审等效。对称条款：产物审查 findings 中 P0 ≥ 2 时，修订后重派产物审查 subagent 复审一次（单维核对同此）。
3. 本条 1／2 的触发条件由原「同类精度 P0（计数／断言互斥／范围失控三类）」放宽为任意 P0 族。

立例依据：旧仓 039 批六轮 58 findings、046 批四稿、043／044 一审 23 findings 后整稿重写；047 批窄域复审 8 次工具调用即抓出 2 处新问题——窄域审判别力已实证。

## 六、偏差与止损（P0／P1、停摆呈报、反模式清单）

偏差分级（施工方与审查 subagent 同一口径）：

| 级别 | 判定 | 处置 |
| --- | --- | --- |
| P0 阻塞型 | 规格与现状冲突、或违反红线，继续会做错 | 施工方立即停摆，全部输出改为偏差申报（禁止顺手按自己理解改断言或改期望）；规划方裁定后重落 |
| P1 观察型 | 规格含糊、边界模糊，不影响施工 | 按最合理理解执行 + 标注假设 + 核验请求偏差记录中申报；规划方裁定，作者可推翻 |
| P2 建议 | 风格／优化，不影响正确性 | 记录，不阻塞提交 |

- 停摆呈报：施工方遇 P0 一律停摆——旧仓 044 批施工方按纪律停摆申报（规格两节计数互斥），规划方裁定后产物侧零改动。
- 分歧升级：规划方与施工方对同一 finding 的性质或修法有分歧时，升级为裁决请求呈作者。禁止规划方压制施工方的 P0 报告，或施工方擅自把 P0 降为 P1。
- 失败回滚：验收不通过不得改断言求绿；规格前提失效走作废重出（§五 止损条）；已发布版本发现严重缺陷用 bump patch 重新发布，不删除已发布 tag（`版本与分发标准` §6）。

## 七、提交与登记

- 提交需作者明确确认：**凡改变仓库状态的 git 命令**（commit／push／tag／分支等，含只改 `.git/` 者）每次单独取得作者确认，作者对其他操作的授权不外延（`AGENTS.md` 红线 1）。AI 会话不自建分支——批次为原子单元直推当前工作分支（`git branch --show-current` 返回值；作者明确要求除外）。
- 提交前必跑 `bash scripts/check.sh` 且退出 0（pre-commit 自动执行，见 §四）。
- 提交前自检四项：改动未越出规格范围（**轻路径无规格，该项改按「改动未越出轻路径触发条件」自检**）；验收断言全绿；术语与[术语表](../product/术语表.md) 一致；新增文件符合 `命名标准`。
- 一域一批：一次提交只承载一个域的批次改动，跨域改动拆批。多批在制时提交前逐路径对照 `git status`，禁 `git add -A` 后直接提交（反模式 #8）。
- **未跟踪件不能被 pathspec 命中**：`git commit -- <路径>` 对未跟踪文件无效（pathspec 不匹配、静默漏掉该件）——未跟踪件须**先 `git add`**、再以 `git diff --cached --name-status` 核暂存面、再提交；提交后以 `git show --stat` 复核该件**确在提交内**（与 `#8`「`git add -A` 后不核对」互补：本条管 add 与 pathspec 的语义，`#8` 管核对面）。
- 提交信息用 Conventional Commits：`type(scope): 主题`；type ∈ {feat, fix, docs, chore, test}，scope 取改动作用域——skill 资产＝`skill`，单域建设＝域名（见 `docs/product/架构设计.md` §一 域清单，如 `abzu-outline`），治理文档＝`governance`，标准件＝`standards`，规格＝`specs`，**开发守卫＝`scripts`**（`check.sh`／`check_spec.py` 等；其改动为主作用域的批次取 `scripts`；074／075 两批按历史用 `standards`／`governance`，不复改）。主题宜含批号（NNN）。

### 规格模板「本批核销」节的口径

- 触发：本批改动面与某归档规格**有交集**（**同一文件／同一主题／同一产物**，三者任一）时，此节必写；无相关归档规格则整节省略，不留空节。
- 核销面：**必列**——① 前一批规格的全部开放项；② 本批改动直接触及或使其状态可能变化的条目（含前批应销未销者）。**不必重列**——已由既往核销表承载、且本批未使其状态变化者，本节只给该表的索引指针（避免两份并行口径）。
- 写法：**只核销、不复述原文**——一行一条，状态取五档之一（已履行／作废／本批处置／仍待／待作者），理由写当时判据或落点（无理由的「仍待」等于没核）。**理由列写「已沉淀」时须点名台账条号（条号形如反模式 `#N`／缺口 `GN`／标准件 `X` §N）；不给条号即视为未沉淀。**
- 表：列名固定为「来源｜条目｜状态｜理由／落点」，末附汇总行。
- 汇总行尾注：**恒列五档、无该档计 0**，且逐格可复核、不得与表列不符。
- 落点纪律：核销落**本批规格**，不另建台账、不建索引件（`AGENTS.md` §四 平行台账不做）；跨批检索以各批规格的核销表为唯一索引落点。
