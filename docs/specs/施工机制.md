# 施工机制

> 定位：开发批次的流程纪律——工作方式、核验、机器检查、审查、提交；协作与流程类规则的单点权威。
> 适用范围：**开发侧**——读者是开发者与开发用的 AI 工具，本件不随产品安装分发；产品运行在 Claude Code 上（`/{skill 名}`），与本文无关（开发／运行分野见根 [`AGENTS.md`](../../AGENTS.md) 头注）。
> 依据：旧仓 `AGENTS.md` §3 与协作模板全套条文（来源件已随 rebuild 作废，逐条迁移并通用化）；**2026-09-17 效率重构**——直接干立为默认、审查按风险分级（沿革与实测成本见 `CHANGELOG`）。

**四步主线总览**：准备（§一 定角色、§二 定方式）→ 执行（§三 施工）→ 自查（§三 核验／§四 机器检查／§五 审查）→ 归档（§七 提交）；偏差与分歧走 §六。

## 一、角色与职责

- **作者**：裁决位——提交确认（红线 1）、重大分歧裁决、治理微调的会话内逐项确认。
- **执行 AI**：默认**规划与施工合一**，在作者在场的主会话内完成勘察、改动、自查与呈报；仅方案先行时分出规划方／施工方两角色（规格模板与断言写法已内联至本件 §二）。
- **审查位**：独立上下文的只读审计，**按风险触发**（§五）；不承接整改、不复用施工上下文；发送指令前核对目标 id 的角色（事故记录 #11）。

**实跑批式纪律**：断言与检查一律批式——一个脚本一次跑完一次输出（每行三列：命令／实测／期望），禁逐条单跑；大输出先收敛再读。

## 二、工作方式

**默认直接干**：改 → `bash scripts/check.sh` 全绿 → git commit。不需要方案、不需要前置审查——改完呈报，作者看 diff 即审查。

**先写方案再干（例外）**——两种触发：

1. **作者指定**：你说「先写方案」「先对齐一下」——AI 写方案，你确认后再执行。
2. **AI 建议且作者同意**：AI 判断改动面大（>5 件文件、或动核心规则／架构／检查器／`AGENTS.md`）时，建议「这批先写方案」——你裁定。

方案须含三要素（缺一不成方案）：**现状位置**（现场核过）／**改动清单**（逐文件逐条）／**验收断言**（每条可命令验证）。

**断言写法七条**：①写进方案前实际跑一遍；②计数禁目视估计，行数＝换行符次数；③断言与替换文本不互斥——token 须在替换文本中存在且不被意外命中；④替换范围写明「只替换 XX，其余原样保留」；⑤一条断言一条命令一个期望值，禁多值聚合；⑥等价性断言排除本批全部改动件；⑦扫描类断言排除本方案本身。

**触检查脚本／标准条文／`AGENTS.md` 的批次**（无论直接干还是方案先行）：另做 §四 同步更新五处核对——会话内逐面呈报并同批落地。

**真机人工试跑**：仅当本批改动**用户可观测行为**时必跑；纯治理改动不跑。做法：按 `README` 装入目标项目 → 新会话（交互面板）走该域主流程 → 对照验收清单核对＋守卫全绿。

## 三、施工、核验与登记

**核验两步**（每批收尾）：① `git diff` 逐块对照任务范围——范围外文件或未声明的逻辑变动＝先呈报，不得顺手带入；② `bash scripts/check.sh` 全绿。规格批加第三步：验收断言逐条独立重跑（断言写法见 §二 规格条）。

**修订工具律**：仓内文本修订一律经 `scripts/patch_file.py`（或等价四段式：匹配文本磁盘校验 → 形态检查〔写盘前对全文跑 lint，不过即零写盘〕→ 统一写盘 → 回读核验）；禁手写长串匹配的临时脚本；宿主 Edit 工具（一次一处、唯一匹配）不受此辖，但改前 `grep` 取原文。修复后自核：逐条 `grep` 确认已落、无遗漏、无衍生问题、受影响的断言与计数重算。

**登记**：`CHANGELOG` **只落用户可感知的变更**（skill 新功能、行为变化、bug 修复、破坏性修改），格式＝列 0、以 `-` 加空格起首、**≤400 字符**（`check_content` `[3]` 段脚本检查），只写「改了什么＋核验结论」。**内部治理改动不进 CHANGELOG**——git commit message 即为记录。直接干的登记＝① check.sh 全绿＋② git commit（含详细 message），CHANGELOG 仅在改了用户可见行为时才落。

**欠账进清单**：修不完的欠账写进**所属清单**——条文覆盖见各标准件 §三 表、踩坑记录见本件 §八；**债跟着主题走，不跟着批次走**。

## 四、机器检查关（段序以 check.sh 头注为准／守卫纪律）

- 段序与段现状以 `scripts/check.sh` 头注为准（`# [N]` 行＝已实现、`# TODO: [N]` 行＝待建；本文件不复制段序列表）；新增检查项按头注的维护入口追加一段并同步头注。已知限制写在各守卫脚本自身注释与各标准件 §三 表。
- 何时必须跑：改任何文件后 `bash scripts/check.sh` 必须全绿（pre-commit 自动执行）；提交前必跑（§七）。有红先判因再改，呈报裁决前不在红起点上叠改动（`AGENTS.md` 红线 6）。
- **红起点**：已实现段判为失败＝红；「未建设」（段未实现或前置缺失而明示跳过）不计红；候选类发现与明示跳过不算失败。段内分档：`[3]` 可判为失败项＝行数与条目限长；`[4]` 判为失败只指环境缺失或工具崩溃（静态发现恒只呈报）；`[5]`＝语法错或前置缺失。
- 守卫纪律：守卫零外部依赖、不跑 LLM、不联网；失败先判因——禁止改断言、改数字、删检查来变绿。
- 边界声明：核验通过／全绿不等于运行时行为已验证——扫描只能证伪不能证真；汇报全绿须声明已检范围。
- **守卫变更同步更新清单**：改 `check.sh` 段或 `check_*.py` 的检查项时（新增／删除／改判定标准），同批核五处——① `check.sh` 头注（段行与段名——段序以它为准）② `AGENTS.md` §七 自检信号 ③ 工具模块 docstring（与内联注释、正则实现三者一致）④ 各标准件 §三 脚本检查点表状态列 ⑤ 守卫脚本自身注释的已知限制段（若有）。漏同步更新按 P1 观察型处置（§六 分级）。凡触**检查脚本**的批次须含一张**「需同步更新的文件核对」表**（逐面给「已同步更新／无需＋理由」）——直接干在会话内逐面呈报，方案先行的写入方案 §五（检查 E 的同步更新文件核对核其存在）。
- **条文立法质量**：新增／修改规范条文须至少附一个正例或反例；无实例者标「预立法，随首批实例校准」并**附关联实例判定标准**；本批触及的标准件内预立法标记逐条核，判定标准命中即同批校准或删除标记。
- **规则新增同步更新清单**：新增／修改硬约束类条文（`须`／`不得`／`禁止`级）时，同批核该条文的**适用范围面**（由条文自身描述限定，如新事故记录行核该族全部入口）；面内有不满足者同批补齐。本句为同步更新纪律的最后一层——不得再为「同步更新纪律本身」立新规则。

## 五、审查（按风险分级）

判定核心：**独立上下文审查的价值与批次风险成正比，与批次大小无关**——改叙述的批次，作者看 diff 即审查；审查的注意力只花在规则、守卫、契约面上。

- **默认（直接干）**：无前置审查；作者看 diff 即审查。
- **事后审计（按风险触发）**：触规则／结构／契约、或动标准条文的批次，以及 ＞10 件的大改动——派**一个只读 subagent** 只看 diff 与守卫输出，报告 ≤500 字符（结论行：`发现的问题 共 N：P0:a P1:b P2:c`＋逐条「文件:行｜问题｜实测命令与输出」指针，不复制原文）。
- **规格批**：成稿审查（规格交作者确认前——查位置真实性、改动清单完备可执行、断言可判定、内部矛盾与既有条文冲突）＋施工后事后审计（同上形态）。报告结构按 §五 事后审计形态。
- **报告纪律与停手**：计数类发现须附实测命令与输出，未附者只作观察项；审查开工说明须附『已知项（不许重报）』——已裁定在案的问题只评处置；审计不循环——发现问题→修→复审只看修复面（上限一轮，逐条实跑自证），仍有分歧升级作者裁决；同一对象全文审硬上限 2 轮。

## 六、偏差与停手（P0／P1、事故记录清单）

偏差分级（施工方与审查位同一计算方式）：

| 级别 | 判定 | 处置 |
| --- | --- | --- |
| P0 阻塞型 | 与现状冲突、或违反红线，继续会做错 | 立即停手，全部输出改为偏差申报（禁止顺手按自理解改断言或改期望）；呈报作者裁定后重做 |
| P1 观察型 | 含糊、边界模糊，不影响执行 | 按最合理理解执行＋标注假设＋在核验请求或呈报中申报；作者可推翻 |
| P2 建议 | 风格／优化，不影响正确性 | 记录，不阻塞 |

- 分歧升级：执行 AI 与审查位对同一发现的性质或修法有分歧时，升级为裁决请求呈作者；禁止压制 P0 报告或擅自降级。
- 失败回滚：验收不通过不得改断言求绿；前提失效走作废重出（移入 archive 标 `-已作废`，有效内容另批重出）；已发布版本发现严重缺陷＝修复后 bump patch 重新发布、不删已发布 tag。

## 七、提交

- 提交需作者明确确认：**凡改变仓库状态的 git 命令**（commit／push／tag／分支等，含只改 `.git/` 者）每次单独取得作者确认，作者对其他操作的授权不外延（`AGENTS.md` 红线 1）。AI 会话不自建分支——批次为原子单元直推当前工作分支（作者明确要求除外）。
- 提交前必跑 `bash scripts/check.sh` 且退出 0（pre-commit 自动执行）。
- 提交前自检：① 改动未越任务范围（`git status` 逐路径对照；规格批可用 `scripts/check_spec.py --reconcile <规格>` 机械化核对）；② `check.sh` 全绿；③ 术语一致（`check.sh` [3] 段＋人工抽查）；④ 新增文件符合 `文字与命名标准` §1。
- 一域一批：一次提交只承载一个域的批次改动；多批在制时逐路径对照 `git status`，**禁 `git add -A` 后直接提交**（事故记录 #8）。
- **未跟踪件不能被 pathspec 命中**：`git commit -- <路径>` 对未跟踪文件无效——未跟踪件须先 `git add`、以 `git diff --cached --name-status` 核暂存面、提交后以 `git show --stat` 复核该件确在提交内。
- 提交信息用 Conventional Commits：`type(scope): 主题`；type ∈ {feat, fix, docs, chore, test}；scope——skill 资产＝`skill`、单域建设＝域名、治理文档＝`governance`、标准件＝`standards`、规格＝`specs`、开发守卫＝`scripts`；主题宜含批号。
- 登记：收尾核两处——`CHANGELOG` 行已落；规格批随验收移入 `docs/specs/archive/`（移动不留副本；移入前逐条过该规格 §八 开放项与 §九 审查记录中 P0／P1 建议，判是否积累成文进清单）。
- 归档件纪律：`docs/specs/archive/` **原则只读**；两处例外——移入时的作废头注、归档移动造成的机械找不到对应可只改路径；归档后不再修改，作废批带 `-已作废` 后缀不再重命名。归档件内的实测值随工具演化失效，引用须标明工具与起点，不得据其直接下结论。
