## 三、填写规则

1. **时机**：修完立刻加，不等收尾。
2. **进哪一区**：修完**当场已立法**（写进条文或建检查器）的，直接进**已总结区**并写去向；**只修了没立法**的进**未总结区**。
3. **类型**五选一（不造新词）：**命令**（工具或命令用错）｜**格式**（Markdown 或文件格式写错）｜**流程**（该做的步骤漏了）｜**判断**（语义或结论错）｜**引用**（链接、节号或文件名指错）。
4. **场景**从词表选（同场景同措辞——聚类靠它）：`接到任务`｜`跑核验`｜`跑内联脚本`｜`写文档`｜`批量替换`｜`计数`｜`数字符`｜`对比输出`｜`提交`｜`派 subagent`｜`改守卫`｜`写规格`。需新场景时先问作者。
5. **问题**和**修法**各限一句（≤30 **中文字符**，含标点；按字符计——拉丁与标点各计 1），细节留在 git commit。
6. **加重前先查同类行**：未总结区有同类行 → 次数＋1；**已总结区有同类行 → 未总结区另开新行**，修法写「复发：原去向 X，需查规则为何未拦住」。
7. **严重度**三选一：**严重**（已产出或必然产出错误结果，且未被检查器拦住）｜**一般**（耽误进度但及时抓到）｜**轻微**（顺手修的小事）。**与《施工机制》§七 的 P0／P1／P2 偏差等级不是一回事**。
8. **AI 不自行立法**：修错＋记行在任务范围内；写条文或建检查器须作者裁定。

## 四、总结方法（作者说「总结经验」时执行）

**只对未总结区聚类**（已总结区豁免）。逐簇按顺序判：

1. 次数 **≥3 且能机械判定** → 建议进 `check.sh`（给出具体检查逻辑）。
2. 次数 **≥3 但不能机械判定** → 建议进标准件（给出条文草案）。
3. 次数 **=2** → 建议进标准件。
4. 次数 **=1** → 问作者「还会再犯吗」；不会则建议删行。
5. **例外**：高价值、低成本、能机械判定的单次问题，作者可直接裁定建检查（不受次数约束）。

裁定通过后：写条文或建检查器 → 原行**移入已总结区**并写去向 → **删掉未总结区的原行**。

**去向写法**：进条文的写「`AGENTS.md` §三 速查」这类**件名＋节号**；进检查器的写「检查器 `check.sh [N]`」这类**脚本名＋段号**——新会话据此能直接去核。
