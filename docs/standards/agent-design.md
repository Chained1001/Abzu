# Agent 设计规范（骨架蓝图版）

> 版本：v0.4（沿革见 CHANGELOG 与 git 历史）
> 定位：Abzu 子代理（subagent）的命名、设计判据、结构模板与协作协议的单点权威——**骨架立法**（指约束规则已生效，但无运行时实体实现）：骨架与判据现已生效（约束设计与文档），**分身（工序角色）为现行默认工序**（见下文分身节），实体 agent 的创建待 T1 触发。
> 依据：Claude Code 官方 sub-agents 文档、Anthropic Building Effective Agents（编排/评审模式）。
> **术语边界**：本规范的「agent」特指 **Claude Code 子代理（AI 分身，独立上下文窗口）**。外部 CLI 工具（如 agent-browser——浏览器自动化依赖）不是 agent，属环境依赖，归 references/scan/scan-cdp-base.md「前置条件」与 README 安装前置管辖。

## 一、命名与文件

| 项 | 规则 |
| --- | --- |
| agent 文件 | `abzu-{角色名}.md`，kebab-case，一角色一文件 |
| 角色名 | 职责即名（如 `evaluator`、`researcher`），禁泛化名（helper/util） |
| 目录 | 物化目标为书项目 `.claude/agents/`（由 abzu-setup 部署）；仓库内源码位 `[T1-TODO]`（规划中：`templates/agents/`） |
| frontmatter | 官方字段：`name`（=文件名）、`description`（触发条件+边界，第三人称）、`tools`（白名单，最小权限）、`model`（按任务配级，廉价任务降级模型） |
| tools 白名单 | **禁止继承主会话全部工具集**——每个 agent 的 tools 只保留完成本职工作必须项；禁全量授权 |

## 二、分身（工序角色）与实体 agent 的分野

本规范的「agent」是上位概念，其下有**两条轨道**——同一机制（Claude Code 子代理）的**不同用途**，不是两套东西：

- **分身（工序角色）**＝**开发工具链用法**：由规划方在会话内 spawn（独立上下文窗口），随会话存在、**无物化文件**，不进用户书项目。
- **实体 agent**＝**运行时物化**：有 `abzu-{角色名}.md` 文件、装进用户书项目，**待 T1 触发**（判据见下文启用判据节）。

**现行三个分身角色**（承 [AGENTS.md](../../AGENTS.md) §3.8 与 collab-log）：

| 角色 | 职责 | 关键约束 |
| --- | --- | --- |
| 施工分身 | 只按规格施工 | 无 git 写权限 |
| 独立审查分身 | 施工前审规格（fresh context） | 只回报 findings，不当场改文件 |
| 产物审查分身 | 施工后审产物（fresh context） | 不复用独立审查分身 |

三者均为**默认工序**；spawn 时机、可续性、只读约束等**工序细则**以 [collab-log](../specs/collab-log.md) 为单点权威（本规范只立「轨道存在」这一层，不复制细则）。

**适用边界**：本节所载分身**不属**「实体 agent」，故不违 T1 禁令。启用判据节末的「四条全不沾 → 不建 agent」、其后「反模式（严禁 spawn agent 的场景）」小节各条、以及协作协议节的「agent 内部**禁止再 spawn 其他 agent**」，三处裸「agent」表述一律辖**实体 agent**——分身不适用（不得由本节首句与头部「术语边界」推出「分身亦须过四条判据」）。**措辞规则**：本规范此后新增／改动的条文，凡涉「agent」而需指实体者一律写「实体 agent」；只对未来改动生效，**不回溯改造既有条文**。

（单称「分身」指本节所立**工序角色轨**；头部「AI 分身」系子代理的通俗注解，非轨名。）

## 三、启用判据（四条，命中才准建实体 agent）

1. **批量并行**：同构任务数量大，主会话逐个做效率不可接受
2. **上下文隔离**：重型阅读（数万 token 语料/榜单/全书）会淹没主会话，且结果只需蒸馏结论
3. **审查隔离**：评审者与创作者必须分身，防自审偏袒
4. **条件性重活**：轻量版主会话先做，复杂时才 spawn

四条全不沾 → 不建 agent。**fallback 主线程纪律**：任何 agent 不可用时，主会话必须能完成同等任务（降级而非中断）。

### 反模式（严禁 spawn agent 的场景）

以下场景**直接主线程完成**，开子代理 = 过度拆分：

- 简单文本改写、格式转换、单文件小修改
- 短文本阅读（≤ 10 行），主会话一眼能看完
- 简单逻辑判断（是/否、数值计算），不需要独立上下文
- 单条命令的输出解读（跑命令→看结果→报结论）

## 五、协作协议

1. **上下文隔离**：spawn 只传任务增量；稳定规则由 agent 自身定义承接，不随调用重复
2. **结果回传**：结构化产出先落文件再由主会话消费（文件账本律）
3. **失败语义**：spawn 失败即 fallback 主线程，同一任务重试 ≤ 1 次
4. **权限最小化**：tools 白名单按职责最小配置；禁全量授权；**禁止继承主会话全部工具集**
5. **嵌套禁令**：agent 内部**禁止再 spawn 其他 agent**——嵌套调试难度指数上升、错误溯源不可控；确需嵌套必须单独立项评审
6. **调用方责任**：spawn 前调用方须校验前置条件（被引文件存在/路径正确）；记录 spawn 溯源（哪个任务、哪个步骤拉起了该 agent，便于排查）
