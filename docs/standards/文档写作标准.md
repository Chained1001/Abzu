# 文档写作标准

> 定位：约束 Markdown 写法与 AI 友好写法（禁模糊指代、禁时间敏感、示例优先）——结构、中文排版、符号允许清单、不采用的规则。
> 依据：旧仓《Markdown 写作规范》全文（来源件已随 rebuild 作废，条文逐条迁移）；markdownlint 规则集（工具配置见 `.markdownlint-cli2.jsonc`）、中文文案排版指北、Anthropic skill 写作实践。

## 一、条文

### 1. 结构规则

1. 标题仅用 H1–H3：全文唯一 H1（文件标题）居首，小节从 `##` 起，逐级递进禁止跳级；更深的层次用列表表达。
2. 代码块必标语言（`bash` / `json` / `yaml` / `markdown`，目录树用 `text`）；中文话术、模板示例的围栏不标语言。
3. 超 100 行文件，头部放节目录——目录为手动列表（`- 节名`），不依赖渲染器 TOC 语法，条目与 H2 标题逐字一致。
4. 单文件超过 300 行应考虑拆分（skill references 建议上限 300 行，见 [skill形态标准](skill形态标准.md)）。
5. 无序列表统一用 `-`；有序列表只在顺序有意义时使用；子列表缩进：顶层列表 2 空格，嵌于有序列表之下时与父项内容列对齐（3-4 空格，以 markdownlint 实判为准）。
6. 表格上下留空行；单元格内的竖线用 `\|` 转义；对齐标记可省略（默认左对齐）。
7. 段落之间空一行；文件结尾保留一个空行。
8. 不使用 HTML 注释与 HTML 标签（内部备注走规格或 git 历史）。
9. 条文分组可用 `章.节[.条]` 前缀标记（如 `1.1`／`1.2.3`），脚本检查点表以该前缀引用。

### 2. 中文排版

1. 中英文之间加空格（如：在 Claude Code 中运行）；中文与数字之间加空格（如：第 3 章）；行内代码与全角标点邻接不加空格（如：运行 `npm install`）。
2. 全角标点与其他字符之间不加空格。
3. 标点不叠用（如 ！！、……。）。
4. 专有名词大小写正确：GitHub、Claude Code、markdownlint。
5. 中文语境省略号用 `……`，不用 `...`。
6. 引号三分：① 节名与需逐字复现的内容用「」；② 中文普通引语用直引号 `"`（本仓常态）——中文与代码混排下弯引号与全角标点易混，且弯引号全仓实测几乎不用；③ 代码与参数内的引号随语言惯例。
7. 移植文件（来源标注含「移植自」）的存量排版偏差豁免——移植保真优先，不做批量规范化；增量编辑部分仍须遵循本规范。现仓已无「移植自」标注文件，本条为休眠条款（预立法，随首批实例校准；**关联实例判定标准：文件头两行含来源标注「移植自」者出现**）。

### 3. AI 友好写作

1. 术语一致：全文只用[术语表](../product/术语表.md)的叫法，发现第二种叫法当次收尾。
2. 示例优先于规则：教格式或风格必须给输入/输出对——本文件 §二 的示例对照块即此履约。
3. 指令用命令式语态（「读文件后再改」）。
4. 引用带节位置：`outline-workflow.md`「草稿步」节。
5. 禁模糊指代：不写「格式同上、参照上文、如前所述」——分段读取时读者看不到"上下文"；带明确节位置的具体引用不受此限。
6. 禁时间敏感表述：不写「X 年 X 月后用 Y」；只写当前方法，版本沿革一律记 `CHANGELOG.md`（含治理文档头部的版本行——只留版本号，不写沿革）。
7. 路径用正斜杠并用反引号包裹：`skills/{skill 名}`。
8. 加粗：单文件 `**` 数 ≤ 行数 ÷ 3（数值上限为保底做法）；定性规则优先——加粗仅用于红线、路径、数字、检查关四类，一段至多一处。**计数计算方式**：本文的「`**` 数」指 `**` **标记出现次数**（含 glob 等非加粗用途）。**适用范围**：保底做法阈值针对**叙事型文档**（以连续段落为主）；**以表格与编号条目为主要结构者**（各标准件、产品层域设计、清单型文档）**不计保底做法**——此类文档的加粗用于检查关、路径与数字，属定性规则辖域。**目录要求**：§一.1.3 的节目录适用于**常驻文档**；**规格与归档件不适用**（在制与历史工作件，读者从头读）。〔出处：061 开放项 8／062 开放项 0 存量债〕
9. 箭头 `→` 仅用于流程映射与条件分支（起点 → 终点／条件 → 动作），禁作装饰；趋势枚举 `↑/→/↓` 中的 → 表示持平，为例外。
10. **底座不写产品层的计数**：治理文档只写指向唯一出处的指针，不复述产品层会变的数字（词条数、字段数、件数、字数）——数字写进底座即**从落地那刻起开始过期**；确需引用时改写为「见 `X` §N」。
11. **引用须写到能唯一写入位置的那一级**：写 `X §N` 时，`§N` 须是**该内容实际所在的那一级**（二级形 `§一` 与三级形 `§一.3` 混用会读到**空节**——父节只承载子节标题、正文在子节）；判定标准＝照该指针去读，**必须直接读到内容**，读到空节即降级或升格重写。

### 4. 符号允许清单

清单与状态列的**符号型**取值须出自本允许清单：`✅` 已就绪／已修入｜`🚧` 已立项未建设｜`🔴` 未修入或待处置｜`🔨` 校准中｜`⏳` 待讨论｜`➕` 开放集补充｜`⚠️` 风险或依据强度提示。

- 本允许清单只管**符号型**状态取值；文字型取值（`已实现`／`待建`／`无守卫（人工判断）` 等）不受辖——各标准件 §三 的脚本检查点表（每件 1 张）即文字型取值的现存实例。
- 产品文档可在其头部另设图例界定本名单内符号的亚义——图例不得引入名单外符号，新增符号须回改本允许清单，禁纯装饰性 emoji。
- 不属清单与状态列取值的符号不受本名单辖：示例对照、判定表与自核验模板用的正反例标记（`✅`／`✓`／`✗`／`❌`），以及命令输出样例与沿革叙述中指称的符号（如 `⏱`／`⏸`）。
- 现状：各标准件 §三 脚本检查点表的状态列均为文字型取值，符号型状态清单尚未建立，故允许清单整体为**预立法，随首批实例校准；关联实例判定标准：任一标准件 §三 脚本检查点表（或产品层清单）「状态」列出现符号型取值（如 ✅／🚧 类）**。

### 5. 编码与行尾

全仓 UTF-8 编码、无 BOM；行尾统一 LF，由 `.gitattributes`（`* text=auto eol=lf`）强制。细则见[运行环境标准](运行环境标准.md)。

### 6. 不采用的规则（带理由）

| 规则 | 理由 |
| --- | --- |
| MD013 行长度上限 | 中文与代码混排不适配 80 列，以段落可读性为准 |
| MD040 代码块语言（全量要求） | 本规范采用选择性标注：真代码的语言标注由 §一.2 条文约束；中文话术、目录树、模板围栏无语言可标，全量要求不适用 |

配置摘要（与 `.markdownlint-cli2.jsonc` 对齐）：上表两条已在配置关闭；裸 URL 规则（MD034）未关闭——裸 URL 会报，属有意保留；配置对 MD024 设 `siblings_only`（重复标题仅同父级下才算——各平台段落下的同名小节是合法平行结构），特此登记以免规范与配置各说一套。其余规则以 markdownlint 默认集为准；新增不采用须改本文件并说明理由。

### 7. 给 agent 读的文档

本节把「写给人看」与「写给 agent 读」分开：agent 每次运行都走同一套过程，可靠性来自措辞与结构，不来自读者的悟性。

1. 指针：留在上下文里、指向别处材料并携带触发条件的那句话即指针——`description`、`AGENTS.md` 里的指路行、`SKILL.md` 里的引用行都是它。决定 agent 何时去读的是**指针的措辞**，不是目标本身；必需的目标配了弱措辞＝方差 bug，处置顺序是先磨措辞、磨不动才把材料内联。指针做两件事：说清材料是什么、列出该触发的分支（正例：`AGENTS.md` §二 路由表的「任务 → 去哪份」，条件在前，读者一眼判定；反例：只写「详见标准件」而不写何时该去读）。
2. 两种负荷：新增任何文档或指针都花掉两种预算之一——context load（常载材料每轮烧 token 与注意力，不论是否触发）与 cognitive load（人记住「有哪些文档、何时用哪份」的负担；人就是索引，这不是要最小化的成本，而是人的能动性代价——花在需要人工判断断处，其余处删掉）。
3. 信息层级与下沉判定标准：文件内步骤 → 文件内参考 → 下沉参考（被指针指向、触发才加载的独立文件）。下沉的判定标准是分支——每个分支都要用的内联在文件内，只有部分分支会读的才沉下去；行数阈值只是保底做法信号。同一概念的规则、定义与注意放同一节（co-location，正例：本条把定义与判定标准写在一处）；同一意思写两处（duplication）与同一意思碎在多处（scattering）是两种病，单一唯一出处律须同时覆盖这两维。
4. 修剪：环境也是唯一出处（配置、目录、`--help` 输出能查到的东西，复述＝缓存，只在查不到时才值得写）；逐句找 no-op——模型默认就会照做的指令白花负荷，一句失格就删整句而不是改字；没有任何修剪纪律时，默认命运是 sediment（陈旧层层层沉积，加得安心、删得心虚，最后要钻进岩芯里才找得着还活着的部分）。

### 8. 禁令须配正向目标

1. 否定式反弹：以禁令驱动行为会把被禁行为拉进上下文并提高其可用度——否定是弱修饰，压不住被强烈激活的概念（反例：「别想大象」，结果满脑子都是大象；条文只写「禁止删文件」而不说该做什么，等于把「删文件」摆在读者眼前）。条文首选正向写法，即直接写要做的事（正例：「改文件前先读全文」，被禁行为不出现在正文里）。
2. 禁令只在无法正向表达的硬护栏上保留，且须在同一处给出正向目标句，让注意力落在该做什么。红线（`AGENTS.md` §一 六条）与事故记录清单的「正确方式」列、以及 `AGENTS.md` §四 不做清单的「条目 ＋ 解冻触发关键词」速查形态（完整形态见其 git 历史原版本），均视为已履行本节义务。
3. 存量条文按本节校正：各标准件中「禁止 X」式条文须补正向目标句；补不出正向目标的，说明该条其实是硬护栏，须同处给出理由与红旗自检。

### 9. 产品层文档范式

适用于 `docs/product/` 各件与 `README.md` 的域条目（本批只立规范，域设计内容待业务设计阶段落笔）。

1. 定义性约束（defining constraint）：一句话写出该域区别于显然默认做法的那一件事，写成陈述句——它让读者明白「为什么不能照常识来」。正例：「本域只产出大纲，不写正文——正文归另一域」；反例：写「关键点：本域很重要」式标签（标签不携带信息，读者仍不知该域特殊在哪）。
2. 跑通信号（It's working if）：作者不打开 skill 内部即可自查的信号（正例：「你拿到的大纲里每个卷都有明确的冲突句」）。判定标准是它在该作者自己的工作里可见——不得拿内部合规检查（lint 全绿、断言通过）冒充。
3. 角色定位：一句话标出该文档或该域属链步、一次性配置、周期性，还是随时可用——角色决定读者何时来读它。
4. 常见问题：须来自真实来源（实际被问过、实际踩过的），数量忠于证据；宁可少写也不注水，并保留说不好听的实话。

### 10. 维护

- 违反本规范视同文档 bug：改文件当批顺手修，不单独开规格。
- lint 体检命令：`npx markdownlint-cli2 "**/*.md"`（配置见 `.markdownlint-cli2.jsonc`）。
- 固化检查工具的两条技术要求：围栏感知（代码块内 `#` 非标题——2026-09-05 误报教训）与正则词边界（`gb18030` 撞 `B\d\d` 误报教训）。

## 二、正例与反例

示例对照（✅ 合规 ｜ ✗ 违规）：

- 行内定义：✅ `**核心要点**：一句话说明` ｜ ✗ `**核心要点**: 一句话说明`（半角冒号）｜ ✗ `**核心要点** ：一句话说明`（冒号前空格）
- 引号分工：✅ 「你倾向哪个选题？」（中途暂停话术，逐字复现）｜ ✅ 这就是所谓的"降维打击"（普通引语）｜ ✗ 在节名位置里用直引号 `"产物格式"节`（节名须用「」）
- 箭头：✅ `起点 → 终点`（流程）、`样本不足 → 降"中"`（条件）｜ ✗ `这是一本 → 非常好看的书`（装饰性断行）
- 加粗：✅ `**必须**写入文件数据质量三行`（红线）｜ ✗ `这段**历史**讲的是过去`（无强调必要的装饰加粗）
- 加粗密度适用范围：✅ 保底做法阈值只量叙事型文档，以表格与编号条目为主要结构者用定性规则 ｜ ✗ 拿加粗密度保底做法阈值判清单型文档（`AGENTS.md` 现 **91 处**属红线加粗，非赘述——**该数随该件改动而变，判读看性质不看数值**）
- 模糊指代：✅ 「字段定义见[书目录契约](../product/书目录契约.md) §2」｜ ✗ 「字段格式同上」
- 状态符号：✅ 状态列取值 `✅`／`🚧`／`🔴`（就绪／建设中／待处置）｜ ✗ 自设 `🟡` 之类名单外符号作状态值（旧仓实录：某追踪表自设图例引入名单外符号，被要求回改允许清单）
- 时间敏感：✅ 「版本号记在 `CHANGELOG.md` 版本段」｜ ✗ 「2026 年 9 月后改用新写法」
