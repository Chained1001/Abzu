# 测试与验收标准

> 定位：守卫全景（哪道闸管什么、何时必须跑）＋域上线验收清单＋真机走查做法与记录落点＋已知缺口。
> 依据：旧仓《守卫与验收规范》全文（来源件已随 rebuild 作废，条文逐条迁移）；来源件为多域时期内容，已通用化改写；域上线验收清单与真机走查命令整块迁入 `docs/product/`，未落地的守卫按现状标「待建」。

## 一、条文

### 1. 守卫全景（机检确定轨）

1.1 `scripts/check.sh` 段序：

> **段序真源＝`scripts/check.sh` 头注**（唯一，本标准不复制段序列表——052 批的教训是同一列表在六处载体里漂移）。下表列全部段（现状标已实现／待建）：

| 段 | 管什么 | 现状 |
| --- | --- | --- |
| [0] 真目录守卫 | `skills/` 是否被安装器符号链接化（安装器在源仓库内跑过的机械拦截）；目录未建时跳过 | 已实现 |
| [1] lint | markdownlint-cli2 全仓 `.md` | 已实现 |
| [2] skill 格式校验 | `agentskills validate` 逐壳校验 frontmatter 与 description | 待建（脚本头注已留 TODO 位） |
| [3] 内容轨 | 引用闭合（治理文档相对链接与 skill 资产路径引用须实存）＋加粗密度＋TOC 存在性＋`SKILL.md` 行数＋`CHANGELOG` 条目限长 | 待建 |
| [4] 规格静态自检 | 在制规格的断言自噬预警、计数重算、`[A]` 项「替换为」侧文本逐字核对、规格写作机械检查 | 待建 |
| [5] 脚本语法 | 逐 `skills/{skill 名}/scripts/*.js` 跑 `node --check` | 待建 |

退出码：全绿 `0`；任一段置红 `1`（末尾统一打印「检查未全绿，禁止提交」）。

1.2 何时必须跑：

- 改任何文件后：`bash scripts/check.sh` 必须全绿（提交门禁启用后由 `pre-commit` hook 自动执行，启用命令见 [AGENTS.md](../../AGENTS.md) §三）。
- 改 skill 资产后：在全绿基础上**真机走一遍该域主流程**，并对照产品层该域设计的验收清单节逐条核对（做法见 §3；真机走查是否必跑按[施工机制](../specs/施工机制.md) §二 重路径行的真机走查豁免判据）。
- 非平凡改动收尾：按[规格写作标准](规格写作标准.md) 的过程产物两项自查（`CHANGELOG` 条目、规格与归档）。
- 禁带病开工：动工前先确认当前无已知失败；有红先呈报裁决，不在红基线上叠改动。**基线定义**：建设期内，验收清单条目因「能力尚未建设」而失败的，不计入红基线；只有**已建设能力出现回归**才算红。

1.3 守卫纪律：守卫零外部依赖、不跑 LLM、不联网；失败先判因——**禁止改断言、改数字、删检查来变绿**。

1.4 边界声明：核验通过 ＝ 按规格改了、语法没坏、文档合规、没越界，**不等于运行时行为验证**（需联网／真机的归实测阶段）。「全绿」也**不等于没问题**——仅覆盖已检项与已知模式（扫描只能证伪不能证真）；汇报全绿时须同时声明已检范围。

### 2. 域上线验收清单（人判轨）

清单本体迁入产品层——域内条目见 [大纲域设计](../product/大纲域设计.md)／[卷纲域设计](../product/卷纲域设计.md)／[正文域设计](../product/正文域设计.md) 的验收清单节，全域通用条目与未建域待启用验收点见 [验收场景](../product/验收场景.md)；本标准只定做法与记录约定（§3）。

### 3. 真机走查做法与记录

做法（仓库内禁跑安装器，见 §1.1 [0] 段守卫）：按 `README.md` 安装说明装入目标项目 → 新开会话跑该域主流程 → 逐条核对产品层该域设计的验收清单节与全域通用条目，＋ §1 的守卫全绿结果。

具体安装命令与真机步骤（含离线备选）见[验收场景](../product/验收场景.md) §三。

记录约定：

- 走查记录**落当批规格**（日期 ＋ 域 ＋ 通过／失败 ＋ 备注）——不另建台账（平行台账是明确不做项，见 `AGENTS.md`「不做清单」节）。
- 条目失效（行为有意变更）：同批更新规格与本清单，**禁止只改清单**。
- 无当批规格时（如日常使用中发现问题）记入下一次改动的规格。
- **每域最低测试要求**：① `check.sh` 全绿 ②产品层该域设计的验收清单节逐条走查通过 ③涉脚本域加沙盘验证（幂等／异常态）④真机走查欠账不得超过下一个域建成；真机走查是否必跑按[施工机制](../specs/施工机制.md) §二 重路径行的真机走查豁免判据。

### 4. 已知缺口（机检／工具／守卫类）

> 定位：机检／工具／守卫类技术债的落点——债跟着主题走，不跟着时间走。协议／协作类缺口落[施工机制](../specs/施工机制.md) 的已知缺口节；规范文本类落各标准件的「待收口」注。多数缺口随旧仓守卫件退役而**待建守卫重建时一并处置**——重建前逐条留痕，不得丢失。

| 编号 | 缺口 | 触发条件 |
| --- | --- | --- |
| G1 | 内容轨加粗密度检查扩展至治理文档（旧仓只扫 `skills/`，阈值须另行立法） | 阈值另行立法 |
| G2 | 规格静态自检的计数重算量词扩展（`条`／`项`／`处` 类计数因定义随文件类型而异未覆盖） | 待出现漏报后按类扩 |
| G3 | 规格静态自检工具更名（现名只覆盖「断言」，静态阶段已超其字面） | 工具重建时一并裁定 |
| G4 | 计数重算分级只有「是否本批改动清单件」一维——他批未提交改动件被在制规格引用尺寸时会误判「计数不符」而阻断提交 | 工具重建时 |
| G5 | 工具头注「退出码恒 0，仅呈报」主语为全工具，而核验比对模式可阻断退出——宜加限定词 | 工具重建时 |
| G6 | 预验器脚本的文档与健壮性补遗（转义引号残差注记／依赖与前置段补不可审计类／非仓根调用口径） | 工具重建时 |
| G7 | 核验比对的边界补遗（待验规格自身归档移动的自指噪声／「无发现」剩余可达情形改述） | 工具重建时 |
| G8 | 清单判定用子串匹配偏松——「本批改动件」判定与核验比对的「声明集」均把仅被提及的文件计入 | 工具重建时 |
| G9 | 脚本用法文本多载体同步风险（头注参数表／`usage()` 输出／域文档选项表）——属可机械化同步点 | 出现同类脚本时 |
| G10 | `[A]` 逐字核对载体覆盖缺口（只核 bullet 成对与具名多行形态，内联载体不核）与归档件历史噪声 | 扩展覆盖前 |
| G11 | 规格写作机械检查在非规格件上误报；同一行的嵌套反引号构造产出同文重复预警 | 工具重建时 |
| G12 | 开发脚本无体积上限（体积纪律只约束 `SKILL.md`／references）——预算体系是否扩展到开发脚本 | 若体积预算范围扩展 |
| G13 | 未来守卫待办：`check.sh` 增 references 相对链接扫描 | 无归属，待认领 |

## 二、正例与反例

- ✅ 改完任何文件跑 `bash scripts/check.sh` 且退出 0；改 skill 资产后另跑真机主流程并对照产品层该域设计的验收清单节逐条核对。
- ✅ 汇报全绿时声明已检范围（如「内容轨未建，本批只覆盖 lint 与真目录守卫」）。
- ✅ 走查记录落当批规格一行（日期＋域＋通过/失败＋备注）。
- ✅ 退出码不经管道取（`cmd | tail` 后 `$?` 是 `tail` 的；必须接管道时取 `PIPESTATUS[0]`）。
- ✅ 建设期未建设能力的失败不计入红基线；已建设能力回归才算红。
- ✗ 为过检改断言／改守卫数字（先判因；文档数字与实测对齐）。
- ✗ 给带 shebang 的脚本插入头部注释（把 `#!` 挤离首行——注释插在 shebang 之后，改完必跑语法检查）。
- ✗ 在源仓库内跑分发／安装类工具（安装器把 `skills/` 符号链接化；[0] 段守卫拦截）。
- ✗ 建独立台账登记走查与守卫欠账（不建平行台账）。
- ✗ 带病开工：在已知红基线上叠改动。
- ✗ 拿「核验通过」当运行时行为已验证（核验只覆盖已检项；联网／真机验证归实测）。
