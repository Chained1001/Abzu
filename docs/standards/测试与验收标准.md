1.2 何时必须跑：

- 改任何文件后：`bash scripts/check.sh` 必须全绿（提交门禁启用后由 `pre-commit` hook 自动执行，启用命令见 [AGENTS.md](../../AGENTS.md) §三）。
- 改 skill 资产后：在全绿基础上**真机走一遍该域主流程**，并对照产品层该域设计的验收清单节逐条核对（做法见 §3；真机走查是否必跑按[施工机制](../specs/施工机制.md) §二 重路径行的真机走查豁免判据）。
- 非平凡改动收尾：按[规格写作标准](规格写作标准.md) 的过程产物两项自查（`CHANGELOG` 条目、规格与归档）。
- 禁带病开工：动工前先确认当前无已知失败；有红先呈报裁决，不在红基线上叠改动。**基线定义**：建设期内，验收清单条目因「能力尚未建设」而失败的，不计入红基线；只有**已建设能力出现回归**才算红。**判据**：「未建设」＝该段未实现（`check.sh` 中以 `TODO:` 注释占位、**不执行**）或前置缺失而**明示跳过**（如 `skills/` 未建时的 [0] 段）——两者均不置红、不计基线；**已实现段（现为 `[0]`–`[5]`）的置红一律计红**（**失败＝置红条件**；候选类发现与明示跳过不算失败）。**段内分档**：`[0]`／`[1]`／`[2]` 的置红＝检查本身失败；**`[4]` 的置红只指环境缺失（Python 探测链全缺）或工具崩溃**——其**静态发现一律只呈报、恒不置红**（退出契约见 `scripts/check_spec.py` 头注；外部评审 P1-2 澄清）。`[3]` 的置红＝环境缺失或工具崩溃 ＋ 其**可置红项**（`SKILL.md`／reference 行数、`CHANGELOG` 条目限长）超标；其余三项（引用闭合／TOC／「维护出处」标注）为候选类，只呈报、恒不置红。`[5]` 的置红＝语法错或前置缺失。

1.3 守卫纪律：守卫零外部依赖、不跑 LLM、不联网；失败先判因——**禁止改断言、改数字、删检查来变绿**（[1] 段 lint 工具链为例外，见 `运行环境标准` §一.1.3）。

1.4 边界声明：核验通过 ＝ 按规格改了、语法没坏、文档合规、没越界，**不等于运行时行为验证**（需联网／真机的归实测阶段）。「全绿」也**不等于没问题**——仅覆盖已检项与已知模式（扫描只能证伪不能证真）；汇报全绿时须同时声明已检范围。

### 2. 域上线验收清单（人判轨）

清单本体迁入产品层——域内条目见 [大纲域设计](../product/outline/大纲域设计.md)／[卷纲域设计](../product/volume/卷纲域设计.md)／[正文域设计](../product/write/正文域设计.md) 的验收清单节，全域通用条目与未建域待启用验收点见 [验收场景](../product/验收场景.md)；本标准只定做法与记录约定（§3）。

### 3. 真机走查做法与记录

做法（仓库内禁跑安装器，见 §1.1 [0] 段守卫）：按 `README.md` 安装说明装入目标项目 → 新开会话跑该域主流程 → 逐条核对产品层该域设计的验收清单节与全域通用条目，＋ §1 的守卫全绿结果。

具体安装命令与真机步骤（含离线备选）见[验收场景](../product/验收场景.md) §三。

**走查环境前提**：①用**会直接调用核心工具**（读文件／执行命令类）的模型会话——已知有模型会自述「本会话没有文件工具」而实际具备（其只检索延迟加载面即下断言），此时应换模型重试并记录 ②`-p` 无头模式**不展开**斜杠命令（当路径处理），真机走查只在**交互面板**内做。

记录约定：

- 走查记录**落当批规格**（日期 ＋ 域 ＋ 通过／失败 ＋ 备注）——不另建台账（平行台账是明确不做项，见 `AGENTS.md`「不做清单」节）。
- 条目失效（行为有意变更）：同批更新规格与本清单，**禁止只改清单**。
- 无当批规格时（如日常使用中发现问题）记入下一次改动的规格。
- **每域最低测试要求**：① `check.sh` 全绿 ②产品层该域设计的验收清单节逐条走查通过 ③涉脚本域加沙盘验证（幂等／异常态）④真机走查欠账不得超过下一个域建成；真机走查是否必跑按[施工机制](../specs/施工机制.md) §二 重路径行的真机走查豁免判据。
