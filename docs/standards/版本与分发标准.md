# 版本与分发标准

> 定位：约束版本号载体与分发清单（单一真源、清单与 skill 一一对应）。
> 依据：旧仓《版本与发布规范》全文（来源件已随 rebuild 作废，条文逐条迁移）；SemVer 2.0.0、Keep a Changelog 1.1.0；多域时期内容已通用化改写，已退役机制（旧产物兼容实现件）的条文按现状标「待设计」。

## 一、条文

### 1. 版本语义（SemVer + skill 定制）

| 变更 | 版本动作 |
| --- | --- |
| 行为变化：新阶段、新产物文件、流程规则变更 | minor |
| 措辞修正、勘误、文档完善 | patch |
| 产物结构破坏性变更（老产物目录不再直接可用；具体产物契约由产品层定义） | major |

0.y.z 阶段照常执行上述语义（比 SemVer 默认的"0.y.z 任意可变"更严格，主动收紧）。

**边界示例**（易混场景判定）：

- references 内业务阈值／判定规则修改（如样本阈值、折算值）＝**行为变更 → minor**，与修改载体无关。
- 纯错别字、排版、失效链接修复＝patch。
- 新增可选产物字段＝minor；删除／改名既有产物字段＝major 候选（视兼容性）。

### 2. 版本四处一致（单一真源）

套件发布版本号出现在且仅出现在四处，禁止散落第五处：

1. 已建壳（`skills/{skill 名}/SKILL.md`）的 `metadata.version`，套件统一节奏同批 bump。
2. `.claude-plugin/marketplace.json` 插件 `version`（＝套件发布版本）——**现状预留**：`.claude-plugin/` 尚未建立，该载体待首个发布批建齐。
3. git tag `vX.Y.Z`（打在发布提交上）。
4. `CHANGELOG.md` 版本段标题。

**真源与时机**：发布时以「CHANGELOG 定稿」动作同步另三处——先定稿 CHANGELOG 版本段，再改 frontmatter 与插件清单，再打 tag。发现第五处版本号＝收口（同一规范复制多份维护是反模式）。

**可跑校验**：四处一致由人工纪律升级为**可跑的一致性校验**——比对脚本只读版本号行、有差异即非零退出（借外部仓库 `sync-plugin-version.mjs --check` 的核法）。我方四处里的 git tag 与 `CHANGELOG.md` 版本段属人工核对项（按 §3 发布流程逐条核对），机器可覆盖的是已建壳 `metadata.version` 与插件清单 `version` 两处；校验脚本随该两处载体建齐一并落地（见 §8 已知缺口），本条只落规范措辞。

**第五处口径**：`README.md` 状态行**不写套件版本号**——该行改为指认「套件版本见 `CHANGELOG.md` 版本段与已建壳 `metadata.version`」，故不构成第五处载体；日后新增任何文档若要写套件版本号，一律按本条口径改为间接指认。治理文档头注不设版本行（头部规范见[skill形态标准](skill形态标准.md) §13），因此也不构成第五处。

### 3. 发布流程（六步）

1. 上线验收全绿——自包含口径：lint 0 违例 + 各壳 validate 通过 + 各域上线验收清单无「已建设能力」的回归失败（建设期未建设能力的失败不计红；清单与真机走查做法见[测试与验收标准](测试与验收标准.md)）。
2. CHANGELOG 定稿：`Unreleased` 段移为 `[X.Y.Z] - YYYY-MM-DD` 版本段（ISO 日期），新开空 `Unreleased`；兼容影响类条目加 `[兼容]` 前缀，用户在升级说明中第一时间可见。
3. bump 已建壳 `SKILL.md` 的 `metadata.version` 与 `.claude-plugin/marketplace.json` 的 `version`，并与 CHANGELOG 对齐。
4. `git tag vX.Y.Z`（发布时推送——**git 写操作每次单独取得作者确认**，见 `AGENTS.md`「红线」节）。
5. 插件清单预检（可选）：本机装有 claude CLI 时执行 `claude plugin validate . --strict`；CLI 缺失则记录跳过，不阻塞发布。
6. 安装实测：`npx skills add Chained1001/Abzu -y` 后在独立文件夹跑**该域真机主流程**（做法见[测试与验收标准](测试与验收标准.md)）。

### 4. 写作项目兼容

- **兼容四原则**：新字段／新文件全部可选增量；老数据零丢失；迁移先备份；不兼容变更必须提供迁移说明（写入 CHANGELOG 版本条目）。
- **迁移执行边界**：迁移**默认只输出迁移说明**（改哪些文件／字段、如何操作），由作者确认后执行或自行手动执行——**自动改写用户书稿文件须单独立项裁定**（默认禁止，防 AI 静默修改用户书稿）。
- **替代机制待设计**：原产物版本兼容机制的实现件已随该机制退役删除，现行设计真源**尚未定义替代的版本兼容机制**——本条只保留兼容四原则与迁移执行边界两条通用条文。

### 5. 预发布版本

- 命名：`vX.Y.Z-alpha.N`（功能试探）／`vX.Y.Z-rc.N`（发布候选），N 递增。
- 预发布**不触发兼容迁移承诺**（兼容变更只在正式版引入）；冒烟可简化为安装实测，但安装实测本身不可省。
- CHANGELOG 以正式条目记录预发布变更，条目尾标注预发布性质。

### 6. 回滚预案

- 已发布版本发现严重缺陷：**修复后 bump patch 重新发布**，不删除已发布 tag（行业惯例）。
- 必要时在 CHANGELOG 该版本条目尾标注 `[YANKED]`（Keep a Changelog 撤回标注）。
- 用户侧回滚 = 重新复制上一版本 skill 文件夹（建议用户保留旧版本文件夹，升级前不删）。

### 7. 发布渠道分层

- 当前：`npx skills add Chained1001/Abzu -y` 或手动复制到用户级 `~/.claude/skills/`。
- 发布前置（届时执行）：插件市场提交（清单载体 `.claude-plugin/marketplace.json` 随首批发布建齐；预检命令见 §3 第 5 步）；引入第三方内容时补 `THIRD_PARTY_NOTICES.md`（版权边界见[安全与合规标准](安全与合规标准.md)）。

### 8. 已知缺口

| 编号 | 缺口 | 触发条件 |
| --- | --- | --- |
| V1 | 行为变更批（改脚本／域资产行为）未 bump 任何 `metadata.version`——版本 bump 归套件统一节奏（§2），须在下次发布 bump 时并入 CHANGELOG 段，并处理各载体间的四处不一致 | 下次发布 bump |
| V2 | `.claude-plugin/marketplace.json` 载体未建；§2 的四处载体（已建壳、插件清单、tag、`CHANGELOG` 版本段）均未落实，首个发布批逐项建齐 | 首个发布批 |
| V3 | `v1` 首次发布未发生（无 tag、无 CHANGELOG 版本段），§3 六步属首次发布时按条执行 | 首次发布 |

### 9. 维护

- 本规范与 `CHANGELOG.md` 实际内容冲突时当次修正（版本纪律以本文件为准）。
- 改动写作项目结构前必读本节 §4；域资产行为变更时核对 §1 版本语义与 §8 缺口的触发条件。

## 二、正例与反例

- ✅ CHANGELOG 先定稿版本段 → 再改 frontmatter 与插件清单 → 再打 tag（四处一次对齐）。
- ✅ references 内业务阈值修改判为 minor（判定看行为变化，不看修改载体）。
- ✅ 已发布版本发现缺陷：修复后 bump patch 重新发布，旧 tag 保留。
- ✅ 不兼容变更在 CHANGELOG 版本条目中给出迁移说明；迁移默认只出说明、作者确认后执行。
- ✅ 预发布（`-rc.N`）不引入兼容变更；安装实测照跑。
- ✗ 在 `README.md` 状态行写套件版本号（第五处载体——改为间接指认）。
- ✗ 同一版本号在文档里散落多处各自维护（发现第二来源即收口）。
- ✗ 删除已发布的 tag 来"回收"版本（行业惯例禁；用 bump patch 或 `[YANKED]` 标注）。
- ✗ AI 自动改写用户书稿文件做迁移（默认禁止，须单独立项裁定）。
- ✗ 纯错别字改动 bump minor（属 patch；也不能不 bump 就发布）。
