# 已知问题

当前已知的缺口、风险与已定未做的调整。

**本文件只记还没解决的事**。已修复的条目在修好时直接删掉，不在正文里留删除线与「X 版本已修复」的痕迹——那类信息属于 CHANGELOG 与 `git log`，留在现状文档里会让读者分不清哪些还成立。

每条尽量写：**症状**（能观察到什么）、**影响**（谁会碰到、代价多大）、**现状**（目前做到哪一步）、**出口**（什么条件下算解决）。没有明确出口的会注明「无排期」。

相关：[技术现状](现状.md)。

## 1. 技术侧：代码与运行时

### 1.1 长篇规模下的性能与上下文

**症状**：章节数到几百上千时操作显著变慢，上下文被撑大。

**影响**：长篇作者的主要手感问题；状态查询与检索是高频操作。

**现状**：已窗口化的部分——`novel_get_story_status` 返回最近 20 章完整加其余一行摘要（可传 `最近N章`／`卷` 展开）；状态查询不再装配 recovery injection，不读材料包；`novel_get_book_progress` 章列表只列首尾各 15 章并标省略数。指纹缓存按 stat 档判定，书未变时直接复用快照（首次仍全量）。

**仍未处理**：五本账本是单文件追加、每次沉淀整文件重写（读侧已降载，分类已知时只读该本）；世界书条目每章追加事实块，文件持续变长；近期窗口保留全部已消费条目；分片与账本解析缓存未做。

**出口**：账本改为分片或增量写入，且单次沉淀的写入量与章数脱钩。

### 1.2 草稿目录残留

**症状**：同章改名后，草稿区会留下旧键的工件目录。

**影响**：不污染真源（草稿区独立 git、不进真源提交），但占空间，且让人误以为有两份稿。

**现状**：工件键已带章号（`卷NN-NNNN-章名`），同卷同名不同章不再相撞。同章改名留下的旧键靠归并与定稿清理收口，存量书跑 `草稿清理.mjs`。

**出口**：改名时能自动回收旧键目录，无需手动跑脚本。

### 1.3 文件门禁可被绕过

**症状**：门禁挂载失败时，插件只记自检与日志（优先 `error`，宿主无该级别时退回 `warn`）后照常运行；此时文件工具写入不受 Abzu 门禁保护。

**影响**：**这是残余缺口，不是 fail-closed**。模型用文件工具直接写书仓时，定稿只读等约束不生效。

**现状**：`decideBookWrite` 已是书仓内写入门禁的单源，`decidePreExecute` 复用它，`gates.ts` 的重复实现已移除。核心判定收敛了，但「宿主是否提供写钩子」这个外部条件仍可缺席。

**出口**：宿主不提供写钩子时拒绝加载插件，而不是降级运行。

### 1.4 core 单源未收拢

**症状**：同一字面量在多处各写一份，改一处会让另一处误判。

**影响**：改动风险，不影响运行时正确性。

**现状**：`'# 近期窗口'` 读写两侧各一份（`derive/scan.ts`、`design/volume.ts`）；`'## 窗口覆盖'`、`'## 窗口外锚点'`、`'（无摘要沉淀）'` 各三处；段标题尾注剥离正则分别写在 `design/volume.ts` 的 `sectionTitles` 与 `derive/design.ts` 的卷纲缺段扫描里，两处口径一致但未合单源。记忆类别已收窄为 `MEMORY_KINDS` 单源。

**出口**：上述字面量与正则各有唯一定义处，其余位置 import。

### 1.5 计数依赖模型

**症状**：破折号、比喻、句长分布等密度判据要模型自己数。

**影响**：判据执行不稳定，同一稿两次审读可能给出不同计数。

**现状**：代码的确定性检查只有字数、空正文、套话黑名单、连续空格与硬约束字面核对（`review/src/checks.ts`）。

**出口**：高频密度判据有机器可数的实现，模型只做判断不做计数。

### 1.6 没有输出质量评估

**症状**：没有黄金样本、回放、评判或对照实验。

**影响**：改技能后无法量化正文质量的变化，只能靠读感。

**现状**：无。

**出口**：有一套可在固定输入上复跑的评测，能对比两次技能改动。

### 1.7 心智不可观测

**症状**：心智落点没有统计，「零消费即删」这条规则无法执行；任务包「总约束账」未实现。

**影响**：心智条目只增不减。

**出口**：能统计每个心智条目的触发次数。

### 1.8 主会话负载

**症状**：加载过的技能与判据不会卸载；走完一遍逐部设计流程，指令与判据约 7–10 万 token（按字节估算）。

**影响**：长流程后段上下文紧张。

**出口**：流程切换时能卸载不再需要的判据件。

### 1.9 测试

**症状**：约 26% 的断言逐字匹配提示词原文；满载时 `host-loader` 等集成测试会超时；两个收据文件在慢机上偶发超过 15s；测试代码不做类型检查；没有覆盖率统计。

**影响**：改提示词会大面积红，红得未必是真问题；覆盖率不明导致不知道该测哪。

**现状**：对实测超过 8s 的用例逐个加了 per-it 超时，`inProcess` spawnSync 超时收敛。满载红按工程规范 §9 单跑复核。

**出口**：断言改为匹配结构而非逐字原文；有覆盖率基线。

### 1.10 代码规范存量

**症状**：27 个函数超过 100 行（`createDesignTools` 666 行）；core 汇总导出约 588 个；错误处理 `throw` 与 `ok:false` 混用，失败结果大多只有中文 `reason`、没有机器可读的 `code`；无格式化工具。

**影响**：新读者难以定位；程序化处理失败时只能匹配中文字符串。

**现状**：已接入 typescript-eslint recommended 基线，并加 typed-lint 三条试点；依赖版本收敛 pnpm catalog；`tsconfig.base` 开 `noImplicitReturns`＋`noImplicitOverride`；`noUnusedLocals`/`noUnusedParameters` 先开在 drafting/polish/review 三包。分域契约已写进[工程规范](../标准/工程规范.md)第 7 节。

**出口**：失败结果带 `code`；`noUnusedLocals` 开满五包。

### 1.11 版本与分支

**症状**：所有版本只递增 patch，没有 minor/major 语义；仓库只有 master 分支。

**影响**：外部无法从版本号判断是否有破坏性变更。

**现状**：发布时打唯一 tag。

**出口**：明确什么时候该动 minor（当前约定见工程规范）。

### 2.1 力量锚点自动追加

**症状**：「已展示锚点」行尚未在定稿沉淀时自动回写进力量体系条目。

**影响**：作者需手工维护，漏记会让后文写得更弱而无记录。

**现状**：世界常量回写已落地——正文新出现的常量经事实变更段随入档自动追加。力量锚点未做。

**出口**：定稿沉淀时自动写入力量体系条目的「已展示锚点」行。
