# Abzu 技术现状

系统怎么实现：包结构、运行时、安全模型、状态推导、数据层、构建安装、开发命令、CI 与发版、外部资产。

相关：[已知问题](已知问题.md)、[判据体系](../标准/判据体系.md)、[产品是什么](../产品/是什么.md)。

## 1. 系统总览

Abzu 是 DeepSeek Harness（DSH）的插件，安装包名 `abzu`，只针对一个 DSH 版本验证（固定版本见 `packages/bundle/dsh-baseline.json`）。运行时由三部分组成：

1. **确定性代码**：`novel_*` 工具、文件门禁、事务与锁、作者审批、状态推导、检索增强，以及书房、编辑器等客户端界面。
2. **运行时技能**：13 个 Markdown 技能（0.0.56 拆出《卷幕规划》，0.0.58 拆出《素材库与采风》），由 DSH 的 agent 加载执行；主控按技能调度，正文、审读等创作工作交给子代理。
3. **薄脚本**：技能目录下的 `scripts/*.mjs`，由主控在命令行运行，调用打包后的确定性 CLI。

创作类的模型调用全部由 DSH agent 完成。TypeScript 代码只在三处直接调用模型服务：嵌入（`packages/bundle/src/retrieval/http.ts`）、场景识别（`retrieval/auxiliary-models.ts`）、参考小说分析（`reference/host.ts`）。

## 2. 包结构

| 包 | 目录 | 职责 | 内部依赖 |
| --- | --- | --- | --- |
| `@abzu/core` | `packages/core` | 书仓读写、状态推导、设计与大纲工件、账本、记忆、修订、定稿、检索、导出、门禁、事务、锁、Git 提交 | 无 |
| `@abzu/drafting` | `packages/drafting` | 起草上下文与作者稿导入 | core |
| `@abzu/review` | `packages/review` | 审读确定性检查与发现项结构 | core、polish |
| `@abzu/polish` | `packages/polish` | 润色规则与保真核对（被 review 引用，属产品链路） | core |
| `abzu` | `packages/bundle` | 宿主接线、工具注册、客户端、技能、脚本、打包 | core、drafting、review、polish |

依赖方向单向，没有循环。core 通过 `src/index.ts` 汇总导出。内部包不独立发版，打包时内联进 `abzu`；Cordis、DSH、React 等宿主共享模块保留为 peer 依赖。

## 3. 运行时结构

### 3.1 宿主接线

`packages/bundle/src/index.ts` 的 `apply` 在插件启用时：注册全部工具；为每个 agent 挂文件门禁；挂书房 Web 路由（16 条，卸载时逆序交回）；注入客户端；限制子代理可用的工具；记录装机自检状态（`self-check.ts`，`abzu:self-check` 步骤输出一行 JSON）。

### 3.2 技能与子代理

- 技能目录与资产清单的单源是 `packages/bundle/scripts/artifact-contract.mjs`（技能列表、判据件清单、薄脚本清单），打包与测试都按它核对。
- 主控会话先加载 `novel-director`，再按节点加载其他技能。加载过的技能内容以工具结果的形式留在会话上下文里，不会卸载。
- 子代理看不到主会话，所需材料全部由主控组装进任务包（规则见[技能编写规范](标准/技能编写规范.md)第 7 节）。

### 3.3 工具

工具注册在 `packages/bundle/src/tools/`（按域拆分为设计、大纲、起草、审读、修订、定稿、参考等文件，`index.ts` 汇总），共 32 个作者可用工具（0.0.50 删除 `novel_record_memory`，0.0.54 新增 `novel_record_polish`），另有 1 个只在 `ABZU_TEST_TOOLS=1` 时注册的测试工具。

每个工具的**身份**只在 `packages/bundle/src/tool-spec.ts` 声明一处：`TOOL_SPECS` 一行七个字段——`name` / `title`（结果卡标题）/ `stage`（工作流视图阶段，`null` 为不上视图）/ `register`（`author` 或 `test-only`）/ `lock`（书锁作用域）/ `designIdempotence`（是否参与本轮重复空提交查重）/ `receipt`（是否产回执）。注册顺序即表序；`NOVEL_TOOL_NAMES`、`NOVEL_TEST_TOOL_NAMES`、`novelToolTitles`、`toolStages` 都是对它的投影，不再各存一份字面量。工具的 `parameters` 与 `execute` 仍留在各域文件——那是每个工具真正的 interface。

`lock` 有四个值，作用域各不相同：`book-sync`（工具层 `withBookWrite` 同步锁）、`book-async`（批准类工具，作者裁决后才落锁）、`core-only`（工具层不加锁，锁在 core 的 `bookWriter` 里）、`workspace`（参考小说四件走 `referenceLocked`，锁在 workspace 而非 bookRoot）。域文件产出表外工具、或表登记了未实现的工具，注册时直接 `throw`。

| 类别 | 数量 | 代表 | 写入与提交 |
| --- | --- | --- | --- |
| 只读 | 3 | `novel_select_book`、`novel_get_story_status`、`novel_get_book_progress` | 不写 |
| 检索与参考 | 6 | `novel_search_finalized`、`novel_index_manage`、参考小说四件 | 写索引与参考库，不提交书仓 |
| 设计写入 | 9 | `novel_create_book`、`novel_update_contract`、`novel_update_full_outline`、`novel_update_volume_layout`、`novel_roll_window`、`novel_confirm_worldbook_entry`、`novel_confirm_volume_outline`（目标：卷纲／计划时间线／幕纲／卷摘要）、`novel_confirm_outline`、`novel_note_pending` | 写真源并自动 `design:` 或 `vol:` 提交；代码不向作者提问 |
| 草稿与记录 | 10 | `novel_new_outline_draft`、`novel_assemble_materials`、`novel_import_draft`、`novel_apply_revision(_batch)`、`novel_record_review_findings`、`novel_record_polish`、`novel_record_proposal`、`novel_resolve_proposal`、`novel_prepare_pack` | 写草稿区或记录，不提交 |
| 作者审批 | 2 | `novel_settle_chapter`（`ch:`）、`novel_apply_retcon`（`retcon:`） | 代码经宿主提问通道取得作者批准后才写入并提交 |
| 编辑器 | 1 | `novel_editor_suggest` | 产出行内建议，由作者在编辑器里采纳并保存 |

所有工具执行前先按各自的 JSON Schema 校验参数，违规返回 `invalid-args`；写入类工具在书锁内执行。

**未在 SKILL 主链点名的工具**（不是死代码，只是由编辑器/维护入口直接使用）：`novel_editor_suggest`（编辑器行内建议）、`novel_index_manage`（索引维护）、`novel_search_finalized`（已定稿检索）、`novel_seed_min_design`（`ABZU_TEST_TOOLS=1` 下的测试夹具）。

### 3.5 客户端

`packages/bundle/src/client/`：书房（书目、文件树、打开定稿与草稿）、书稿编辑器（CodeMirror，选区改写、续写、审读批注、行内建议逐条采纳）、可视化（故事图谱、写作流程状态）、检索索引面板、工具结果卡片。

## 4. 安全模型

### 4.1 代码强制的规则

门禁挂载失败时本插件只记自检与日志（优先 `error`，宿主无该级别时退回 `warn`；`packages/bundle/src/index.ts:635` 附近），插件照常运行，文件工具写入不受 Abzu 门禁保护；这是残余缺口，不是 fail-closed。

1. **文件门禁**（`packages/bundle/src/gates.ts`、`packages/core/src/gate/`）：草稿区可写；定稿与构想只读；其他真源只能经受信写入器写；回执目录受保护；路径规范化后再判断是否逃逸。未登记、带路径参数的工具一律返回 `ask` 请作者确认；子 Agent 的审批策略为 `never`，这类请求由宿主自动拒绝。
2. **书锁**（`core/src/repo/lock.ts`）：跨进程锁，原子改名发布，按持有者 PID 与宿主存活判定；同步写入锁拒绝异步回调。
3. **事务**（`core/src/repo/transaction.ts`、`atomic.ts`）：多文件写入带清单，每次写入前先恢复中断的批次，崩溃后要么旧态要么新态。
4. **作者审批**（`core/src/arbitration/`、`bundle/src/approval-snapshot.ts`）：经宿主提问通道发问；没有答复、答复异常或取消一律视为拒绝；批准绑定待定稿包内容与参数的 sha256，并在锁内复核。
5. **Git**（`core/src/commit/`）：只由受信代码执行；`commit --only` 加字面路径；顶层目录白名单；合并或变基进行中、`index.lock` 存在、书仓在云同步目录内时拒绝提交；定稿只追加。
6. **路径**：写入目标先规范化并解析到书仓或书房边界；接受书仓内绝对路径与 `书id:仓内相对路径`，裸相对路径在文件门禁层拒绝；盘符、逃逸、保留名与越界路径一律拒绝。

### 4.2 只靠提示词约束的规则

1. 设计侧确认（契约、世界书、全书大纲、分卷、卷纲、细纲）由模型判断作者是否同意，然后直接调确认工具并提交。这类写入不经过作者审批通道：其中契约、世界书、全书大纲、分卷、卷纲、近期窗口六个设计写入工具经宿主原生 `write` 落盘（`bundle/src/native-write.ts`），由精确的 `callId`/`parent`/`agent`/`file`/`content` 五项匹配授予本次受信写入；native-write 桥自身用 `resolveInsideBook` 校验目标在书仓内，再由 core 写入器落盘；细纲确认走 core 的 `confirmOutline` 写入器。宿主会不会就此另弹写入审批取决于宿主策略，未核实。
2. `core/src/arbitration/kinds.ts` 声明了五类不可逆动作，其中世界书条目转正、规则来源声明等实际没有走作者审批（「记忆入记」一类随 0.0.50 作者层记忆删除而失效）。
3. 起草前细纲必须已确认：代码只报告状态，不强制（`core/src/gate/writeDraft.ts`）。
4. 审读子代理之间互不通气，只是提示词要求。
5. shell 命令不经文件门禁（设计如此）。

**0.0.65 声明-实现对账**（逐条核对 4.1/4.2；`真实` ＝ 有代码路径，`部分` ＝ 有条件或存在残余，`未核实` ＝ 依赖宿主/提示词）：

| 条 | 状态 | 依据与残余 |
| --- | --- | --- |
| 4.1-1 文件门禁 | 部分 | 分区、回执保护、规范化、`ask` 均成立；门禁挂载失败只记录，受信原生写绕过 pre-execute |
| 4.1-2 书锁 | 真实 | 跨进程锁、原子改名发布、PID/宿主存活、同步锁拒异步 |
| 4.1-3 事务 | 真实 | 清单、写前恢复、崩溃后旧态或新态 |
| 4.1-4 作者审批 | 真实 | 缺答/异常/取消即拒；批准绑定 sha256 并在锁内复核 |
| 4.1-5 Git | 真实 | `commit --only` 字面路径、顶层白名单、健康检查、定稿追加 |
| 4.1-6 路径 | 真实 | 书仓内绝对路径与 `书id:仓内相对路径` 均校验；裸相对路径在文件门禁层拒绝；盘符/逃逸/保留名拒绝 |
| 4.2-1 设计侧确认 | 真实（作为提示词规则） | 六工具精确受信原生写、`resolveInsideBook` 路径校验、不走作者审批；细纲走 `confirmOutline` |

| 4.2-3 细纲须确认 | 真实（只播报） | `gateWriteDraft` 只校验草稿路径形状；确认状态由 `reportDraftReadiness` 播报，不阻断 |
| 4.2-4 审读子代理互不通气 | 未核实 | 无直接运行时隔离证据，取决于派发提示词与宿主隔离 |
| 4.2-5 shell 不经门禁 | 真实 | 文件门禁未登记 shell；靠沙箱/授信兜底 |

## 5. 状态推导与恢复

章节状态由文件推导，不维护会话状态。`packages/core/src/derive/derive.ts` 对每一章给出 11 行事实清单，建议环节取最后一个成立的行，只作参考，判断归主控：

| 行 | 环节 | 成立条件 |
| --- | --- | --- |
| 1 | 章细纲（待定位） | 近期窗口有可进入的条目 |
| 2 | 章细纲（待确认） | 有候选细纲 |
| 3 | 写作备料 | 细纲已确认 |
| 4 | 写稿 | 材料包状态为段齐备 |
| 5 | 审核 | 有唯一待审稿 |
| 6 | 改稿 | 有审核记录且未过期 |
| 7 | 润色 | 审核完成且润色未承接 |
| 8 | 定稿准备与沉淀 | 审核完成且润色已承接且待定稿包不完整 |
| 9 | 作者定稿裁决 | 待定稿包完整且未被退回 |
| 10 | 定稿入档 | 待定稿包完整且已批准 |
| 11 | 完成 | 已定稿 |

（0.0.54 润色后移：章节顺序改为「起草 → 审读 ⇄ 改稿 → 润色 → 沉淀」。审核通过后润色会改字，正文哈希与审读指纹随之失配，`core/src/derive/scan.ts` 据此把审核判为过期；审核记录新增可选字段 `润色`（`core/src/evidence/record.ts` 的 `PolishCarryover`）——`novel_record_polish` 登记「当前稿是已审稿经润色的直接子稿、保真通过、确定性复核通过」（或作者登记跳过）后，推导认可审核仍有效，`润色已承接` 为真、行 7 不成立、进第 8 行。`有草稿 && !唯一待审稿` 时叠加标记「有草稿但无唯一待审稿→核对稿件角色」。）

`novel_get_story_status` 返回设计面事实与章节事实清单；主控开场据此写回归简报。恢复逻辑在 `core/src/recovery/index.ts`。0.0.57 起状态查询窗口化：完整重建（每章 scanChapter＋材料包＋状态卡）只做「章号最大的 N 章＋全部 章:0 未定位键＋指定卷的章」，其余章只回一行摘要（key＋已定稿＋建议环节取 完成/未完成 两值，不 scanChapter）——工具参数 `最近N章`（默认 20，常量 `RECOVERY_DEFAULT_RECENT`）与 `卷`（该卷全量，与近章窗口并集）可展开；返回带 `总数/完整返回数/省略数`，有省略时 message 注明「其余 N 章已省略，传 卷 或 最近N章 展开」。千章书返回体从数 MB 降到每章一行摘要的量级。

## 6. 数据层

- 书仓目录与写入边界见[书仓格式](标准/书仓格式.md)；路径常量在 `core/src/repo/paths.ts`（含 0.0.52 新增的 `paths.幕纲(卷, 幕, 幕名)`＝`故事剧情/卷规划/卷<NN>/幕纲/幕<NN>-<幕名>.md`，卷号与幕号均两位）。
- 书仓本身是 Git 仓，设计确认、定稿、吃书补偿各自产生提交；草稿区与书房另有独立 Git 仓做快照（`core/src/repo/draft-git.ts`）。
- 账本、本书记忆、世界书由专用工具更新；世界书事实进入材料包时只取最近 30 条切片。本书记忆 0.0.50 起收成 文风／决策 两类（`core/src/repo/paths.ts` 的 `MEMORY_KINDS`；旧书仓 对话/灵感 两类文件只读兼容、查询按只读跳过，沉淀解析器对这两类给出「只接受 文风/决策」的拒绝原因）。作者层记忆（工作范围 `书房/作者记忆/`）已于 0.0.50 整层删除：`core/src/memory/author.ts` 移除，会话开始不再注入作者记忆目录快照（选书时的本书记忆目录仍随 `novel_select_book` 结果附带，`bundle/src/status-context.ts`）。
- 账本读侧降载（0.0.57）：`queryLedger` 的 `分类` 已知时只读该本账（其余不读不解析，他账缺失/损坏不再连坐——全书健康由不带分类的查询守）；`章上限` 下推到解析流内，归属章号晚于上限的条目边解析边丢、不构造对象。分片与解析缓存本批不做。
- 定稿后清理（0.0.57）：`novel_settle_chapter` 入档成功后在同一写临界区调 `archiveDraftChapter`（`core/src/repo/draft-cleanup.ts`，删草稿区五处：草稿/材料包/审核记录/待定稿包/候选细纲，新旧两代键都清）＋`snapshotDraft` 快照留痕；清理失败不回滚入档、如实进返回 message。存量书跑 `node packages/bundle/skills/novel-settle/scripts/草稿清理.mjs --book <root> [--卷 N] [--执行 true]`（薄入口，实现 `bundle/src/scripts/draft-cleanup-cli.ts`，默认只算不写）。
- 草稿区章键带章号（0.0.57）：五处草稿区工件的目录/文件名改 `卷NN-NNNN-章名`（章号四位，未定位章占位 0000）；旧格式 `卷NN-章名` 读侧兼容（`core/src/repo/draft-paths.ts` 的 `resolveDraftRel` 新键优先、旧键 fallback；候选细纲先于章定位落盘，按 卷+章名 认领同名候选）。写侧一律新键，该章旧格式工件还在旧位置时原位重写。
- 检索指纹缓存（0.0.57）：`scanFinalized` 先算 stat 档指纹（定稿树每文件 size+mtime+ctime+ino＋场景记录文件），与进程内缓存（`core/src/retrieval/cache.ts`，按 bookRoot 键）一致则复用快照对象，不一致才全量——一次检索最多三次复扫不再每次读+哈希+解析+分块全部定稿文件。逐命中再读校验（`readFinalizedBytes`）保留；同尺寸同 mtime 篡改由校验触发缓存失效＋原样重试一次（`searchFinalized` 自愈），场景边界遗忘主动失效。
- 检索增强默认关闭：嵌入（OpenAI 兼容接口，对定稿切片建索引）、场景识别（宿主模型）、重排（独立接口）。失败时显式降级，不伪造增强结果。模型、维度或原文变化会让索引失效重建。
- 参考小说：本地 TXT/EPUB 预检与导入只在本机进行；分析前须作者明确允许把选定范围发送给模型服务。

## 8. 构建与安装

环境：Node 24.15.0（支持 ^22.19.0 或 ^24.0.0）、pnpm 11.27.1、配套版本的 DSH 桌面端；书仓版本记录需要可用的 Git。

```text
pnpm install --frozen-lockfile --store-dir <仓外目录>
pnpm release:build
```

`release:build` 在 `.tmp/release/<version>/` 下生成 `abzu-<version>.tgz`、源码包、`release-notes.md`、`SHA256SUMS` 与 `release-manifest.json`；默认先跑 `test:release`＋`check:version`，`--skip-tests` 只供本地调试，正式发版不得跳过。`--store-dir` 指向仓外目录，否则 pnpm 会在仓库根建 store，导致 `check:public` 失败。

安装：在 DSH 桌面端侧栏打开"插件 → 添加插件"，选择本地 tgz，按提示应用变更；需要重启时从应用菜单完全退出再打开。命令行方式（独立 Web profile）：

```text
dsh --profile abzu --from-default-profile web --dump-config
dsh plugin --profile abzu add <tgz 所在的无空格目录>/abzu-<version>.tgz
dsh --profile abzu --host 127.0.0.1 --port 6104 --no-open
```

然后在 DSH 设置里配置聊天模型与凭据，选择一个工作区。开发时可以用 `packages/bundle/scripts/start-local.mjs <DSH 的 lib/bin.js 路径>` 启动，它会动态生成本机 patch；开发入口与正式安装入口不要同时启用。

数据流：作品、草稿、账本、记忆、索引都存在本地；主模型调用会发送对话、选取的作品材料、工具结果和必要正文；参考小说分析、嵌入、场景识别、重排都要显式启用。插件没有独立的遥测通道。工作台服务只绑定本机回环地址。

  普通测试用系统 `%TEMP%`；依赖 esbuild 落盘的五个文件（`host-loader`、`retcon-retry-receipt`、
  `archive-receipt`、`transaction-process`、`retrieval/settings`）由 `packages/core/tests/helpers/scratch.ts`

  （`Access is denied`），而 Node 自己的 `writeFileSync` 写同一目录却成功——不是 ACL 问题。

- 测试构成：以真实文件系统与 Git 的集成测试为主；`skills-batches.spec.ts` 与 `skills-core.spec.ts` 检查运行时技能文本与代码的一致性。文件与用例计数随每次提交变化，以 `pnpm test` 的输出为准，不在此处写死。

### 11.1 跟随 DSH 版本的策略

DSH 每 6 天左右发一个 rc，走 `next` 预发布通道（`latest` 长期停在 0.0.1，不能用它判断）。本仓**不逐版跟进**，只在下面两种情况升基线：

1. **宿主桌面端自动升到了新版本**。桌面端是自动更新的 Electron 应用，这时 `dsh-source.mjs` 的 commit/版本硬相等检查会失败，属于必须处理。
2. **某个 rc 修掉了我们实际踩到的 bug**，或者改了 Abzu 依赖的宿主 API。

不跟的理由：rc 之间常改内部 API，逐版跟进的验证成本远大于收益；而 `next` 是预发布通道，没有稳定性承诺。

`pnpm check:dsh` 比对三个来源并报告落差：

| 来源 | 读哪里 | 落差含义 |
| --- | --- | --- |
| 基线 | `packages/bundle/dsh-baseline.json` | 本仓验证过的版本 |
| 上游 | npm 上 `@deepseek-ai/dsh-tools` 的 `next` | 官方最新预发布；比基线新只是待办 |
| 宿主 | `$DSH_HOME/dsh-runtimes/dsh-primary-runtime/runtime.json` 的 `desktopVersion` | 实际运行 Abzu 的环境 |

**只有「宿主比基线新」以非零码退出**，因为那意味着当前环境上的运行从未被验证过。「上游比基线新」只报告不拦截——否则每发一版都会让检查变红，等于逼着跟 `next` 走。宿主或上游读不到时记为未知，同样不拦（CI 与别人的机器上没有桌面端）。

升级到新 rc 时改动范围：`dsh-baseline.json` 的 `source.tag`/`source.commit`/`source.version` 与 `registry` 段、`packages/bundle/package.json` 的五个 `@deepseek-ai/dsh-*` peer 依赖版本、以及上游改动 `sessionFormat` 时的 `packages/bundle/tests/skills-batches.spec.ts`。改完跑 `pnpm test:dsh-source -- <对应 commit 的 DSH checkout>` 做类型校验与宿主集成测试——**没有匹配的 checkout 就不要升**，否则是盲改。
