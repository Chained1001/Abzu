# 工程规范

本规范约束提交、版本、测试、发版与文档的做法。具体命令和流水线结构见 [技术文档](../技术文档.md)。

## 1. 提交

1. 提交与推送只由作者执行或批准。
2. 标题使用 conventional commits 类型（`fix:`、`feat:`、`docs:`、`chore:`、`refactor:`、`test:`），写清最终行为；可以用中文。
3. 一批一提交：一次改动批次对应一个提交，不混入无关改动。顺手修复必须在同一提交里声明。
4. 提交前通过全部检查（见技术文档"开发命令"）。涉及发行链或公开文档时，另跑 `pnpm check:public`、`pnpm check:version`、`pnpm --filter abzu pack-check`。
5. 主线和已发布的 tag 不强推、不改写，不用 `push --all`、`--mirror` 或批量推标签。
6. 不提交 API key、启动 token、完整会话、私人作品或个人绝对路径；`check:public` 会扫描全部历史并拒绝这些内容。
7. 仓库没有启用 git hooks。

## 2. 版本

1. 安装包版本的真源是 `packages/bundle/package.json`，根 `package.json` 必须与它相等。
2. 按 SemVer 递增，0.x 阶段按本项目现行口径执行：以 patch 作批次号，每批改动（含新增能力）一律递增 patch；minor 保留给接口或工作区/书仓格式的不兼容变化，出现时在 CHANGELOG 写迁移影响；1.x 之后破坏兼容递增 major。
3. 下次升 minor 的判定：公开工具接口、包入口导出面或工作区/书仓格式出现需要迁移的不兼容变化时才递增 minor（0.x 内即 0.1.0、0.2.0……，`check:version` 与 CHANGELOG 照常同批改齐）；只新增能力、不改既有接口与格式的，继续递增 patch。
4. 纯文档改动不发包。内部 workspace 包（core、drafting、review、polish）不独立发版。
5. 每次升版同批改齐以下位置，否则 `check:version` 或测试会失败：
   1. 两个 `package.json` 的 `version`；
   2. `CHANGELOG.md` 顶部新增 `## [<version>]` 节；
   3. 根 `README.md` 与 `packages/bundle/README.md` 中的版本串（`abzu-<version>.tgz`、`abzu@<version>`、当前版本说明）；
   4. `packages/bundle/tests/skills-batches.spec.ts` 版本纪律组的版本钉位。
6. `docs/` 下的文档不写安装示例的具体版本号，需要时用 `<version>` 占位。`check:version` 会扫描 `docs/` 全部文档里的安装示例，发现与当前版本不符就报错。
7. 发行 tag 形如 `abzu-v<version>`，tag、CHANGELOG、包版本与附件必须对应。已发布的同版本字节不得替换，有错就发新版本。

## 3. 测试

1. 改变行为必须带回归测试。文件写入复用现有的事务、路径校验和作者授权通道，不另写一套。
2. 测试只用合成书仓与固定响应，不用真实作品，不需要 API key。
3. 在 DSH 宿主内跑全量测试前，把 `TEMP`、`TMP` 指到工作区内（原因见技术文档）。
4. 失败时先读具体断言和最后活动的测试文件，再判断是代码问题、测试进程异常还是机器负载。不全局提高超时，不跳过失败断言，不自动重试整套测试。
5. 本机满载时个别集成测试会超时（已登记的有 `host-loader.spec.ts` 等）；单独复跑通过的才可判为负载问题，并在提交说明里如实记录。
6. 测试断言优先检查结构和行为（节存在、引用可解析、工具名一致、写入结果正确），避免逐字匹配提示词原文——只改措辞时也会让逐字断言失败。

## 4. CI 与发版

1. `v8-required` 必须等 Linux 策略检查和全部 Windows 测试分片成功才算通过。Linux 运行时观察任务失败不阻塞。
2. GitHub Actions 只用固定 commit 的 action，权限最小；fork PR 不获得秘密或发版权限。
3. 发版前：在干净 checkout 跑完整测试、构建与实包检查；公开内容扫描与依赖许可证核对通过；没有未说明的格式迁移或数据恢复问题。
4. 验收和上传必须使用同一份生成的 tgz。程序回归报告不能替代真实模型的创作质量判断。
5. 发版失败时保留检查记录和产物，不宣布成功。需要改源码就用新提交和新版本；不重写已发布的 tag。
6. 依赖变更要审查锁文件、实际内联清单和原始许可证；high 及以上漏洞须修复，或给出可核对的范围与处置记录。

## 5. 文档

1. `docs/` 只放三类文档：产品文档（产品是什么、流程怎么走）、技术文档（系统怎么实现、怎么开发发版）、标准（必须遵守的格式与规则）。不写面向终端用户的教程。
2. 文档描述现状，必须与运行时一致；历史放在 git 与 CHANGELOG，不在文档里写演变过程。**例外**：解释当前口径所必需的简短沿革句可保留（如“0.0.57 起窗口化”），但版本流水、逐版已修复清单必须进 CHANGELOG，不堆在现状文档里。
3. 一词一义：术语以产品文档术语表为准，同一事物只用一个名称（例如"审读"与"审核"不互换，"工作区"与"书仓"不互换）。
4. 结论放段首，条件写在动作前面，用主动语态；一段只讲一个主题。
5. 文档里的相对链接必须能解析到仓内文件，`check:public` 会逐个检查。

## 6. 数据铁律

1. 参考小说原文（语料）永不入仓。
2. 交接档案永不入 git；仓外沙盘（测试、成品积累、档案）的产物不入项目。
3. 仓库只保存产品代码、运行时技能和文档；方法论知识库源由作者在仓外维护。

## 7. 错误处理分域契约（throw 与 Result 各管一侧）

1. **写侧不变量用 throw，中文文案**：写入器（`bookWriter`/`withBookWrite` 包裹的落盘路径）与不变量校验（章键形状、路径白名单、版本协议）违反即 throw，消息用中文、点名收到的值（例：`路径字段「章名」不合法:…(B2 路径白名单)`）。写侧 throw 由外层事务与书锁统一兜底，崩溃后要么旧态要么新态。
2. **读侧用 Result，不 throw**：读与推导（`readBookText`、对账、扫描、`loadProposal` 等）返回 `{ok:false, reason, …}` 形状，`reason` 区分 `missing`/`io`/解析失败，不得把「文件不在」当异常抛出调用方。
3. **工具层单点转译**：`novel_*` 工具的 execute 把 core/drafting/review/polish 的 throw 捕获并转成 `{ok:false, reason:'中文语境: <原消息>'}` 返回（前缀点名工具场景），schema 校验失败统一回 `code:'invalid-args'`——模型永远拿到结构化失败，不接收裸异常。新增工具必须沿用该形态：入参先过 schema 校验，core 调用包 try/catch，中文 reason 点名参数与收到值。
4. 空串与空白值按「未提供」处理：必填字段 trim 后为空在工具层或写侧入口点名拒绝（如提案 `内容`、定稿 `summary`），不落盘占位记录。

## 8. 导出面纪律：禁止新增 `export *`

1. **禁止新增 `export *`**（含 `export * from './x'` 汇总桶）：它让符号来源不可追溯、掩盖命名冲突，也会把内部面意外扩大成公共 API。新增导出一律逐名书写（`export { a, b, type C } from './x'`）。
2. 存量 `export *`（2026-10-17 实测 46 处：core 45＋bundle 1，集中在 core 的 `src/index.ts` 与各子域 `index.ts`）**逐步点名化**：动到哪个子域就顺手改写哪个，不要求一次性全清；点名化时删掉不再被引用的导出。
3. 公共 API 面以各包 `index.ts` 的具名导出为准；跨包 import 只从包名入口进（`@abzu/core`），不深路径引用（`@abzu/core/retrieval-policy` 白名单除外）。
