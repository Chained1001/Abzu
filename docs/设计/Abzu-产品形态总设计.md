# Abzu 产品形态总设计

> 状态：待裁决
> 产品形态上位文档：Abzu 由哪几个界面组成、怎么走。不写代码、不做技术选型。

---

## 0. 一句话形态

**Abzu 是一个「书架 → 书 → 章」三级整页 + 对话常驻的写作工作台。**

- **看和改书的东西在整页里**（有位置、能返回、占满宽度）。
- **做决定的东西在对话里**（呈报、裁决、确认点，一律不搬进页面）。
- **就地小工具在右栏**（索引进度之类）。

三个界面各司其职，不互相抢地方。这是对现状"全部寄生在别人界面里"的正面回答。

### 0.1 要解决的问题：作者提的那个诉求

作者说 DeepSeekBot 那种"点击进入新页面"不错。它好在三点，Abzu 全都不具备：

| DeepSeekBot 的做法 | 为什么重要 | Abzu 现状 |
|---|---|---|
| 侧栏有独立条目，点进去换整页 | 有"一个地方"可去，不是临时开个 tab | 零个整页表面，最大地盘是左栏 264–420px |
| 页面是稳定的，切会话不重置 | 位置是页面的，不是会话的 | 右栏 tab 和可视化都绑 session，切会话就没了 |
| 层级靠返回/面包屑 | 知道自己在哪、怎么回去 | 关掉 tab 就丢，重开靠再点一次 |

## 1. 完整信息架构

### 1.1 五级层级（书仓的真实结构）

```text
工作区（会话选中的目录，可放多本书）
└── 书（书仓，一本一个 Git 仓）
    ├── 设计面（契约 / 世界书 / 全书大纲 / 分卷布局）      ← 书级基线
    ├── 卷（卷纲 / 计划时间线 / 近期窗口 / 幕纲 / 卷摘要）  ← 卷级滚动
    │   └── 幕（幕纲）
    │       └── 章（细纲 / 材料包 / 草稿 / 审核 / 定稿）    ← 章级循环
    ├── 账本（故事线 / 人物弧线 / 承诺 / 线索 / 时间线）
    └── 本书记忆（文风 / 决策）
书房（跨书资产：灵感池 / 灵感库 / 参考库）              ← 不在书里，在书之上
```

这条层级不是设计出来的，是书仓目录本来的样子（`docs/产品/是什么.md` §3.1）。**页面结构照它长，不另造一套。**

### 1.2 界面清单：一共几个面

| # | 界面 | 层级 | 形态 | 一句话职责 |
|---|---|---|---|---|
| 1 | **对话** | 会话级 | DSH 原生，永久保留 | 做决定。所有〔谈〕确认、〔码〕审批、呈报都在这 |
| 2 | **书架页** | 工作区 | 整页 | 有哪些书、每本到哪了、新建一本 |
| 3 | **书页** | 书 | 整页 | 一本书的全貌：设计基线、卷列表、账本、记忆 |
| 4 | **章工作台** | 章 | 整页 | 这一章走到哪、该干什么、正文在这 |
| 5 | **书房页** | 工作区 | 整页 | 跨书资产：灵感池、灵感库、参考库 |
| 6 | **右栏工具** | 会话级 | DSH 右栏 | 索引进度之类的就地小工具 |
| 7 | **编辑器** | 文件 | 侧面板/整页内嵌 | 看和改单个文件（真源只读、草稿可写） |

**只有 3、4、5 是 Abzu 自己独占的整页。** 对话和右栏是宿主的，Abzu 只在里面放按钮和工具卡，不抢。

### 1.3 为什么设计面不单独开页面

设计面（契约、世界书、全书大纲、分卷、卷纲）**不做独立整页**，理由三条：

1. **它们的写入全部带确认语义**。契约六部按部更新、卷纲要"方向选择"、细纲要过十查——这些是〔谈〕确认点，性质由产品文档第 8 节定义。做成页面表单就等于在页面上造第二套写入口，绕过门禁。
2. **它们是"当前状态"，不是"操作对象"**。作者不会"打开契约页面干活"，而是"想知道契约定了没有、第几部还留白"。
3. 文件本身已经能被看和改（真源只读、经编辑器）。

**所以设计面在书页里以「状态卡 + 跳对话」的形式出现**：显示当前处在设计面哪一态、哪些部已确认、哪些还留白，需要改动就回对话。这是"看见"而不是"操作"。

## 2. 导航模型（最终形态）

### 2.1 左栏：会话列表 + 两个 Abzu 条目

```text
┌─ 左侧栏 ─────────────┐
│ [＋ 新会话]           │
│                      │
│ 书架          ← Abzu  │  点 → 整页 · 书架
│ 书房          ← Abzu  │  点 → 整页 · 书房
│ ─────────────────    │
│ 会话 A（当前）        │  点 → 对话
│ 会话 B               │
│ 会话 C               │
└──────────────────────┘
```

- 两个 Abzu 条目在上，原生会话列表在下。**这是 DSH 自己的"插件"页、"定时任务"页同款形状**，不是 Abzu 发明的。
- 当前在整页时，对应条目高亮（`aria-current="page"`）；点任意会话回对话。
- **左栏不再被 Abzu 整列替换**。现状的"工作区/书房双 tab"退役——那是抢宿主的位置。
- **但退役有一个硬前提，写在这里防止踩空**：章工作台现在的唯一入口是"左栏书房树点章级文件"（见[《章工作台-产品文档》](章工作台-产品文档.md) §1.2）。左栏交还宿主 = 书房树消失 = **章工作台没有入口了**。
  所以顺序只能是：**先把入口迁到"书架页 → 书页 → 卷 → 章"这条面上，再退役左栏替换**。两件事同批做，不能先拆后建。
  这也说明 P1 现在的入口是**过渡态**：它借了书房树这个将退役的表面，不是在最终形态里。P1 验收不受影响，但别把它当成"入口已经设计好了"。

### 2.2 整页内部：面包屑

```text
书架 / 《书名》 / 卷01 / 第12章 章名
  ↑       ↑        ↑         ↑
 可点    可点     可点      当前
```

- 面包屑是**页内导航**，不改变"当前在哪个整页"。
- 点上一级回到该级列表（仍在整页里，不跳回对话）。
- 返回对话只有一个出口：点左栏任意会话。

### 2.3 三条导航纪律

1. **对话与整页是同级，不是父子。** 不做"返回上一页"按钮，避免和浏览器语义混淆。
2. **位置属于页面，不属于会话。** 切会话不重置当前书/章；但也不做持久化——刷新后回对话，由点击重新定位。**不假装恢复。**
3. **一个整页容器，三层内容。** 书架 → 书 → 章是同一个整页的不同深度，不是三个独立面板。这样"位置感"才连得起来。

## 3. 各页面设计

### 3.1 书架页（工作区级）

```text
┌──────────────────────────────────────────────────────────┐
│ 书架                                    [＋ 新建一本书]   │
├──────────────────────────────────────────────────────────┤
│ 《长夜行》                                                │
│   卷01 · 已定稿 12 / 待写 3 · 当前：第13章 审读            │
│                                          [进入 →]        │
│                                                          │
│ 《旧稿》                          ⚠ 书目缺少有效书id      │
│                                                          │
│ 当前工作范围还没有作品。可在对话中开始构想。               │
└──────────────────────────────────────────────────────────┘
```

| 元素 | 内容 | 数据来源 | 可得 |
|---|---|---|---|
| 书名 | 书仓名 | `shelf` 的 `name` | ✅ |
| 一行近况 | 已定稿数 / 待写 / 当前在哪一章哪一步 | `shelf` 的 `progress`（`activeChapterLine` 现算） | ✅ |
| 书 id 异常 | 「书目缺少有效书id」 | `shelf` 的 `error` | ✅ |
| 新建一本书 | 跳回对话开始构想（**不在页面上建书**） | — | — |

**新建入口是跳对话，不是表单。** 建书要收敛构想七要素、要作者确认〔谈〕，那是对话的事。

### 3.2 书页（书级）

```text
┌──────────────────────────────────────────────────────────┐
│ 书架 / 《长夜行》                                         │
├──────────────────┬───────────────────────────────────────┤
│ 设计基线          │ 分卷                                  │
│  作品定调    ✓    │  卷01  ✓ 已定稿 12                    │
│  世界构建    ✓    │  卷02  ◐ 进行中  当前                 │
│  全书大纲    ✓    │  卷03  ○ 未开始                       │
│  分卷布局    ◐    │  卷04  ○ 未开始                       │
│  当前卷规划  ○    │                                       │
│                  │ 账本（只读摘要）                       │
│ 本书记忆          │  线索 8 条 · 未收 3                   │
│  文风锚点 12 条   │  承诺 5 条 · 未兑现 2                 │
│  决策 4 条        │                                       │
└──────────────────┴───────────────────────────────────────┘
```

| 区块 | 内容 | 数据来源 | 可得 |
|---|---|---|---|
| 设计基线 | 设计面当前处在哪一态 + 各阶段达没达到 | **设计面七态**，现只在 `novel_get_story_status` 工具返回里 | ❌ **客户端拿不到** |
| 分卷列表 | 每卷的定稿数、当前卷 | `/chapters` 按卷聚合 | ✅（千章需窗口化） |
| 账本摘要 | 各账本的条目数与未结项 | `账本/*.md` 读文件后统计 | ✅（需解析，本期可只显示文件在不在） |
| 本书记忆 | 文风锚点条数、决策条数 | `本书记忆/` 读文件 | ✅（同上） |

**诚实的结论**：书页最值钱的那块——"这本书设计做到哪了"——**客户端现在拿不到**。设计面七态（`DesignPosition`：灵感阶段/作品定调/世界构建/全书大纲/分卷布局/当前卷规划/开写就绪）只由工具层计算并经对话返回。

所以书页有两种做法：

| 做法 | 结果 | 代价 |
|---|---|---|
| **甲**（建议） | 书页第一期只做"分卷列表 + 账本/记忆的条目计数"，设计基线那块显示「未接入，回对话看」 | 零 API 改动；书页信息量偏薄 |
| 乙 | 扩一条接口把 `deriveDesign` 的七态与事实项返回给客户端 | 扩数据面，需作者批；但书页立刻变成真正有用的"书的仪表盘" |

**这是完整产品设计里第一个需要作者拍板的技术前提**（不是技术选型，是"要不要为产品体验扩数据面"）。

### 3.3 章工作台（章级）

**已细化，见[《章工作台-产品文档》](章工作台-产品文档.md)。** 本文只记它在全局里的位置：

- 它是"书 → 卷 → 章"的**最深一级**，面包屑最后一段。
- 它只覆盖**后 5 步**（起草→审读→改稿→润色→定稿），细纲和备料仍走对话 + 右栏（那份文档 §1.2.1 的"甲"）。
- 左栏的 7 环节是本页内的进度显示，**不是全局导航**。

### 3.4 书房页（工作区级）

```text
┌──────────────────────────────────────────────────────────┐
│ 书房                                                      │
├──────────────────────────────────────────────────────────┤
│ 灵感池  (23)     灵感库  (8 部 / 131 条)                  │
│ 参考库  (3)      评审    (12)                             │
│ 信息释放台账 (2)  开书草案 (1)                            │
└──────────────────────────────────────────────────────────┘
```

| 元素 | 内容 | 数据来源 | 可得 |
|---|---|---|---|
| 分区列表 + 计数 | 书房下各目录的文件数 | `tree`（`shared` space） | ✅ |

书房现在就在左栏的"书房"tab 里（`browser.tsx` 的 `StudyBrowser`）。整页形态只是**把它从 400px 宽挪到满宽**，功能不变。这是三个整页里最省事的一个。

### 3.5 对话（永久保留）

不重做、不改形态。它承担全部确认点：

| 动作 | 为什么必须在对话 |
|---|---|
| 建书、选书 | 切书必须作者明确指定〔谈〕 |
| 契约/世界书/大纲/分卷/卷纲/细纲确认 | 〔谈〕，由主控判断作者是否同意 |
| 定稿入档、吃书补偿 | 〔码〕审批弹窗 |
| 审读发现项处置、写前十查 🔴 | 涉创作取舍，作者裁决 |
| 子代理失败 | 不代劳，报错误详情 |

**页面上只显示"有没有等你决定的事"，不替自己做决定。**

## 4. 数据可得性总表（这一节决定分期）

把上面所有页面要的数据拉平，标注现状来源：

| 需要的数据 | 现在从哪来 | 客户端可得 | 备注 |
|---|---|---|---|
| 书目 + 一行近况 | `shelf` | ✅ | 现成 |
| 文件树（书仓/书房） | `tree` | ✅ | 现成 |
| 单文件内容 | `read` / `resolve` | ✅ | 现成，含只读判定 |
| 全文搜索 | `search` | ✅ | 现成 |
| 章列表 + 建议环节 + 定稿 | `chapters` | ✅ | 现成，但全量扫描（千章 21 秒） |
| 人物关系图 | `graph` | ✅ | 现成 |
| 工具调用流水 | `workflow` | ✅ | 现成 |
| 保存 + `fix:` 提交 | `save` | ✅ | 现成 |
| 索引进度/控制 | `index-status` / `index-control` | ✅ | 现成 |
| 行内建议 | `suggestions` | ✅ | 现成 |
| **设计面七态 + 事实项** | `novel_get_story_status`（工具层） | ❌ | **只在对话里，客户端无接口** |
| **章↔幕归属映射** | 幕纲自由文本 | ❌ | 无机器可读映射 |
| **审读发现项** | 审核记录 JSON | ❌ | 能读到原文，但解析契约在核心侧 |
| **账本未结项统计** | `账本/*.md` | △ | 能读到文件，统计要客户端解析 |

**四条 ❌/△ 就是完整产品的真实边界。** 前三期不碰它们也能做出有用的三页；要碰就必须扩数据面，每条都要作者批。

## 5. 分期（按"能独立上线、不返工"排序）

| 期 | 内容 | 依赖 | 产出 |
|---|---|---|---|
| **P1** | 章工作台（后 5 步） | 无新 API；入口借书房树（**过渡态**） | 写作时有个满宽的章页面 |
| **P2** | 书架页 + 书页（甲：不做设计基线）；书房页整页化 | 无新 API | "点进新页面"真正成立 |
| **P3** | 侧栏两个 Abzu 条目 + 面包屑；**同批把章工作台入口迁到书页**，然后退役左栏替换 | 宿主 `sidebar.panellist` 真机验证 | 有位置感：知道在哪、怎么回去 |
| **P4** | 书页设计基线（设计面七态） | **需扩数据面** | 书页变成真正的仪表盘 |
| **P5** | 幕层（章↔幕分组） | **需章↔幕映射** | 左栏多一层 |
| **P6** | 审读发现项进右栏 | **需扩数据面** | 章工作台右栏真正有用 |

**P3 必须和 P2 一起考虑**：没有侧栏条目，整页没有入口——作者只能靠"点某个文件"偶然进去，那不是产品形态。所以 P2 和 P3 应当算一期。

一个重要的排序判断：**P2/P3 的产品价值高于 P1 的完善**。作者现在最缺的是"有个地方可去"，不是"章页面再多一块"。如果只能做一件事，做 P2+P3。

## 6. 关键取舍与不选什么（明确不做）

| 不做 | 理由 |
|---|---|
| 不做独立应用 | 已研究过：DSH 本身是 Electron 桌壳，自建等于重做全部基础设施（见[DeepWrite 研究报告](DeepWrite研究报告.md)） |
| 不做页面上的第二套写入通道 | 所有〔谈〕/〔码〕确认点的性质由产品文档第 8 节定义，页面不新增授权面 |
| 不抢宿主界面 | 不整列替换左栏、不顶替右栏文档预览；只用公开插槽 |
| 不做读者数据 / 平台运营 / 商业节奏 | 产品范围（README、产品文档 §1） |
| 不做多人协作、不做移动端 | 单作者桌面工具 |
| 不做"分步向导" | 章工作台不是向导；环节是事实报告不是关卡 |

## 7. 验收标准：这个产品形态算成立吗

一句话：**作者能指着屏幕说"我在哪本书、哪一卷、哪一章，我要回去就点一下"，而不是"我刚才开着哪几个 tab"。**

可测的四条：

1. 左栏有两个 Abzu 条目，点进去换整页，条目高亮。
2. 从书架进书、进卷、进章，面包屑能一路点回去。
3. 点任意会话回对话，位置不丢；再点条目回到刚才那本书。
4. 关掉应用重开，不会假装恢复，但两步点回去。

做不到第 1 条，整个形态不成立——那就还是现在这样。
