# Abzu 产品形态提案

> 状态：**提案，待作者拍板**。非实施计划。
> 起因：作者认为当前产品形态不够好，希望参考同类产品，并偏好 DeepSeekBot 那种"点击进入新页面"的导航。

---

## 一、结论先行

**一句话形态**：Abzu 是"侧栏有独立入口的写作工作台"——对话归对话（聊决策），书房归书房（看和改书），右栏只放就地工具。

**推荐方案 B（三块分工）**，分两步落地：先建整页骨架，再收拢入口。

**技术前提已核实**：DSH 原生就有"点侧栏条目 → 换整页"的机制，Abzu 至今一个都没用。

---

## 二、当前形态的实测清单

Abzu 现在**没有任何整页表面**，全部寄生在 DSH 既有界面里。逐个入口：

| 入口 | 挂在哪 | 打开什么 | 形态问题 |
|---|---|---|---|
| 书稿/书房浏览 | 替换整个 `sidebar.workspaces`（左侧栏"工作区"区变成"工作区 / 书房"双 tab） | 书目列表 + 文件树 | 抢了原生会话列表的位置，原生行为要靠代码镜像（`workspace-slots.tsx` 的 `mountNativeEntry` 就是在做这件事） |
| 可视化（创作阶段 / 写作流程 / 人物关系 / 章节进度） | `conversation.view` 加一个 tab | 中栏整块换成视图 | per-session：切会话就没了；和 chat / trajectory 挤一条 tab 条 |
| 书稿编辑器 | `sidebar.right.pane.tab`（复用原生文件预览 tab） | CodeMirror 编辑正文 | 右栏默认视口 45%、上限 70%，正文和对话并列两边都窄；写一章要长时间专注 |
| 检索索引 | `sidebar.right.pane.tab` | 索引进度/重试 | 合理，属于就地工具 |
| 书稿按钮 | `conversation.input.right` | 打开右栏编辑器 | 入口之一，不是页面 |
| 左右互换 | `shell.overlay` + DOM 探测 | 把对话挪到右栏 | 靠 `[data-rightbar-col]` / `[data-sidebar-right-panel]` 猜宿主结构（`layout-swap.ts`），宿主改版即自检失败 |
| 工具结果卡片 | `tool.call.toolview` | 结构化卡片 | 合理 |

**"形态不好"的技术根因候选**（可核对）：入口数量不少，但没有一个"页面"，所以每个入口都要跟别人的界面抢空间；用户没有"我在哪、怎么回去"的位置感。

## 三、A. 同类对标

### A1. AI 写作 / 长文创作工具

**1. Novelcrafter** —— 一本书一个工作区，顶部四个模式（Plan / Write / Chat / Review）切换整块主面板，Codex（设定库）常驻侧栏。

- 核心形态：模式守恒的工作台。切换发生在"主面板里换界面"，不是在边上加 tab。
- 导航：顶部模式切换 ↔ 主面板；左侧 Codex 可钉住；左侧栏底部放帮助、导出、同步。
- 信息架构：侧栏（Codex / Snippets / Chats）+ 小说导航（回书库、书设置）+ 顶部模式 + 主面板。
- 值得抄：**把"计划 / 写作 / 聊天"做成对等的主面板模式**——正好对应 Abzu 的"设计 / 正文 / 对话"三种心流。
- 不该抄：顶部模式里还有二级 View 下拉，层级偏多；Abzu 的书比 Novelcrafter 多一层"幕/卷"，直接照搬会更深。
- 来源：[Novelcrafter's Layout](https://www.novelcrafter.com/help/getting-started/quick-start/novelcrafter-layout) · [App Layout](https://www.novelcrafter.com/help/docs/app/app-layout)

**2. Sudowrite** —— 编辑器为中心，AI 能力以卡片形式出现在右侧面板；Story Bible 单独一屏。

- 核心形态：原文编辑器 + 右栏 AI 建议卡片（一键插入正文）。
- 导航：Story Bible / Write / Canvas / Brainstorm 是几个并列的入口，各自成屏。
- 值得抄：**AI 产出以卡片进侧栏、由作者逐条采纳**——Abzu 的行内建议已经是这个思路，方向对。
- 不该抄：工具入口太散。Reedsy 的评测直接指出"容易把时间花在调工具上而不是写作上"。Abzu 已经有 13 个技能，再散成十几个入口会更糟。
- 来源：[Sudowrite Review（Reedsy）](https://reedsy.com/blog/guide/book-writing-software/sudowrite/) · [Story Bible 文档](https://docs.sudowrite.com/using-sudowrite/1ow1qkGqof9rtcyGnrWUBS/what-is-story-bible/jmWepHcQdJetNrE991fjJC)

**3. Scrivener** —— 三栏（Binder 结构 / Editor 正文 / Inspector 元信息），外加 Composition Mode（全屏专注）与 Quick Reference（浮窗查资料）。

- 核心形态：三栏职责固定，另有两个"降低干扰"的专用呈现。
- 导航：结构在左、正文在中、元信息在右；Navigate 菜单在任意布局（含隐藏侧栏、全屏写作）下都能跳转。
- 值得抄（最有价值的一个）：**三件事分三种呈现**——长时间专注写作给全屏模式；查一条设定给浮窗；日常给三栏。Abzu 的"写正文"和"查世界书"现在挤在同一个右栏里。
- 不该抄：Navigate 菜单式的隐藏导航，只有老手会用。
- 来源：[Scrivener Navigate 菜单](https://www.literatureandlatte.com/blog/how-to-use-scriveners-navigate-menu-to-access-elements-of-your-projects)

作为反例提一句：国内的墨狐 AI、笔灵 AI 是"功能列表 → 每个功能一个独立页"的工具集（生成器、黄金开头、拆书……），没有工作台概念。Abzu 不是这个形态，不学。
来源：[墨狐AI](https://www.aihub.cn/tools/writing/inkfox-ai/) · [笔灵AI小说](https://aitool.csdn.net/6772679261f6a61b9460abd7.html)

### A2. 把会话式 AI 做成可进入页面的工作台

**4. DSH / DeepSeekBot 本身**（作者点名的那种方式）

- 核心形态：左侧栏一组导航条目 + 一个整页面板。点条目 → 主面板整块换成该页面；点会话 → 回到对话。
- 机制（本机 bundle 已核实）：`sidebar.panellist` 注册导航条目，`main` 是 keyed 插槽（`conversation` 是保留 key），`ctx.layout.selectPanel(id)` 选页面、`selectPanel(null)` 回对话；重复选同一个、或选未注册的 key 会抛错并保留当前选择。侧栏条目用 `aria-current="page"` 标出当前位置。
- DSH 自己的"插件"页和"定时任务"页就是这个形状，代码量很小（一个 nav 注册 + 一个 main 注册）。
- 值得抄：**就是它本身**。Abzu 一个都没用。
- 不该抄：无。

**5. Claude Projects** —— 项目是一个容器页，项目内右侧固定 Project knowledge，聊天在项目内进行。

- 值得抄：**容器（项目）与内容（knowledge）分离**，knowledge 是跨对话常驻的。Abzu 的"书仓"正是这种容器，现在却没有容器页。
- 不该抄：它没有正文编辑器这类重内容页，重内容还得靠外部工具。
- 来源：[How can I create and manage projects?](https://support.claude.com/en/articles/9519177-how-can-i-create-and-manage-projects)

**6. Cursor（Agents 窗口）** —— 右侧 tab 面板 + "把单个 tab 全屏"（expand 按钮 / `Cmd+Shift+M`），全屏时对话退化成浮动输入条。

- 值得抄：**同一内容两种呈现（面板 / 全屏），而不是做成两个页面**。这是"右栏不够宽"的最低成本解法。
- 不该抄：把它当默认。Cursor 的默认仍是并排，全屏是"我要专注"时才按。
- 来源：[Cursor 3.4 Changelog](https://cursor.com/changelog/3-4)

### A3. 直接回答两个问题

**"点击进入新页面"具体解决了什么？**

1. **空间**：整页给内容，不再和对话抢宽度。Abzu 右栏上限 70%，正文和对话并列时两边都窄。
2. **上下文隔离**：`main` 面板是 root scope，**不绑单个会话**。切会话不会把页面重置掉——现在的中栏 tab 是 per-session，一切会话就没了。
3. **位置感与返回**：侧栏条目高亮当前位置，回对话就点会话，规则只有一条。
4. **可编程的深链**：别的插件/代码可以先 `selectPanel(id)` 再设内部状态（DSH 的 `pluginNavigation.openBundle` 就这么做）。意味着"工具结果里点一下，跳到某个页面并定位到某处"是原生支持的。
5. **对话流不被打断**：页面在 root 级，会话在中栏照常跑；现在的中栏 tab 会顶掉对话。

**Abzu 现在的"右侧栏 tab"卡在哪？**

1. 宽度：默认视口 45%、上限 70%，两边都窄，写正文尤其难受。
2. 生命周期绑会话：`conversation.view` 的 tab 随会话走，换会话就重来。
3. tab 条拥挤：chat / trajectory / 可视化 挤在一条。
4. 没有位置感：所有入口都是"按钮打开一个 tab"，没有"我在哪、怎么回"。
5. 补丁感：`layout-swap` 靠 DOM 属性探测宿主结构，宿主一改版就自检失败、功能静默消失。
6. 入口分散但都不是页面：书稿能从 4 个地方点开，却都只是"打开右栏的一格"。

## 四、B. 形态提案（两选一）

### 方案 A：补一个整页（最小改动）

- **一句话形态**：Abzu 仍是寄生式插件，只是多一个"书房"整页入口，其他全不动。
- **主界面分区**：
  - 左侧栏最上方新增一个导航条目"书房"（`sidebar.panellist`）
  - 点进去是整页（`main`）：左侧书目 + 文件树（复用现有 `browser.tsx`），右侧放现有四个视图（创作阶段 / 写作流程 / 人物关系 / 章节进度）
  - 右栏编辑器、会话内"可视化" tab、左右互换全部保留原样。
- **进入/返回**：侧栏点"书房" → 整页；点任意会话 → 回对话（`selectPanel(null)`）。
- **与 DSH 能力匹配度**：高。与 DSH 自带"插件"页完全同构，两个注册调用即可。
- **代价**：小。新增一个 main 面板组件；`browser.tsx` 与 `visualization.tsx` 基本可复用；不动现有入口。
- **风险**：**形态没变，只多了一个入口**。同一个视图两个入口，用户仍要记"哪个内容在哪看"；右栏窄、tab 拥挤、DOM 补丁全都还在。**这是缓解，不是解决。**

### 方案 B：三块分工（推荐）

- **一句话形态**：对话管决策，书房管书，右栏管就地工具——一个目标只在一种表面上完成。
- **主界面分区**（四块，各有唯一职责）：

  ```text
  ┌────────────┬──────────────────────────────┬─────────────┐
  │ 左侧栏      │ 中栏                          │ 右栏         │
  │            │                              │             │
  │ ▸ 会话列表  │  对话（原生）                  │ 就地工具      │
  │ ▸ 书房 ★   │   ── 点"书房"整页替换中栏 ──▶   │ · 检索索引    │
  │ ▸ 设置      │                              │ · 审读发现项  │
  │            │  ┌─────────────────────────┐  │ · 工具结果    │
  │            │  │ 书房整页                 │  │             │
  │            │  │ 左：书/卷/章/世界书树     │  │ （窄、可收起） │
  │            │  │ 中：正文 或 设计 或 总览   │  │             │
  │            │  │ 右：进度/口径/待办         │  │             │
  │            │  └─────────────────────────┘  │             │
  └────────────┴──────────────────────────────┴─────────────┘
  ```

  - **对话**：只承载"要 AI 做决定"的事（开书对谈、呈报、裁决）。不承载浏览与编辑。
  - **书房整页**：书的全部静态内容。页内三栏 + 页内三个模式（与 Novelcrafter 的 Plan/Write 同构，但只保留 Abzu 真有的三种）：
    - **写**：卷/章树 + 正文编辑器 + 章节进度（现"章节进度"视图搬入，按当前卷定位）
    - **设计**：契约六部 / 世界书七类 / 全书大纲 / 分卷 / 卷纲幕纲（现文件树按工件类型重组，而不是按目录）
    - **总览**：现"创作阶段 + 写作流程 + 人物关系"三合一
  - **右栏**：只留就地工具——检索索引、审读发现项、工具结果卡片。**不放正文编辑。**
- **进入/返回**：
  - 侧栏点"书房" → 整页（`selectPanel('abzu-studio')`），侧栏条目高亮
  - 页内点某章 → 中栏切成该章正文，页面不跳转
  - 写作时按"专注"（全屏，参照 Scrivener 的 Composition Mode / Cursor 的 expand）→ 隐藏两侧栏；Esc 或按钮退出
  - 点任意会话 → 回对话（`selectPanel(null)`）
  - 从对话里的书稿链接 → 进书房整页并定位到该章（深链，用 `selectPanel` + 页内状态）
- **与 DSH 能力匹配度**：高。`sidebar.panellist` + `main` + `layout.selectPanel` 都是宿主公开面；侧栏高亮、返回会话由宿主自己处理。
- **代价**：中到大。
  - 新增：main 面板 + 页内三栏 + 三个模式（大部分组件已有，主要是重组）
  - 改动：撤回对 `sidebar.workspaces` 的整个替换（交回原生工作区列表）；"可视化"从 `conversation.view` 摘掉、并入整页；正文编辑器从右栏搬到整页（右栏 tab 保留只读预览）
  - 可删：`layout-swap` 的 DOM 探测换列（整页方案下它失去意义，或降级为可选）
- **风险**：
  1. **整页与 session 的绑定**（待 Dev 确认）：`main` 是 root scope、不绑会话，而现有客户端取数几乎全走 `useSession` / `callStudy(sessionId, …)`。整页要从哪拿"当前工作区 / 当前书"，需要 Dev 给结论。
  2. **外部插件是否被允许注册 `main` / `sidebar.panellist`**（待 Dev 确认）：这两个插槽的声明在 `dsh-client-ui-layout` 与 `ui-sidebar` 包里，DSH 内置插件确实这么用；第三方插件是否同样放行需要核实。
  3. **摘掉会话内"可视化" tab 会改变现有习惯**：边聊边看图谱会消失，需要作者认可；可先保留一个版本再摘。
  4. 撤回 `sidebar.workspaces` 替换后，原生工作区列表的行为要确认完整还原。

## 五、推荐

**推荐方案 B，分两步走**：第一步只建骨架（`sidebar.panellist` + `main` 整页，内容先搬现成的书目/文件树/四视图），验证整页与 session 的绑定成立；第二步再把正文编辑搬进整页、把"可视化"并入、撤掉 DOM 换列补丁。

理由：A 只解决"多一个入口"，右栏窄、tab 拥挤、无位置感、DOM 补丁四个病一个都没治；B 让"一个目标只在一种表面上完成"，才真正回答作者说的"形态不好"。而 B 的第一步代价很小——和 DSH 自带"插件"页同构，两个注册调用就能验证。

**技术可行性拿不准的都标了"待 Dev 确认"，不在这里替开发做选型。**
