## 三、真实缺陷（已修）

### 3.1 章型双轴的接线漏洞 ★★★

拆轴做完后，**工具 schema 的说明文字与实际枚举不符**，且「章纲分级」旧节名残留 4 处引用：

| 问题 | 影响 | 修法 |
|---|---|---|
| `outline-tools.ts:22` 描述写「承诺档 关键/常规，情绪位…过渡」 | core 实为 `关键/过渡` × `铺垫/高潮/余波/切换`。**用户照描述填「常规」会被 `章型问题` 直接拒** | 描述改为正确枚举，并写明「情绪位不用过渡，改称切换」 |
| 「章纲分级」引用 4 处（`写前十查.md:10,25`、`novel-outline/SKILL.md:30`、`步骤卡-章细纲.md:10`） | 该节拆轴后已改名「章型双轴」，4 处指针**全部悬空** | 全部改为「章型双轴」「章型放宽」，并按新双轴重写取档口径 |
| `评审分级与门禁.md:45` 仍用散文定义关键章 | 与 `章型` 字段**并列成两套标准**，两处判定对不上时无人对账 | 改为「位置档直接取 `章型` 字段」，旧散文降为「字段缺失时兜底」 |

**新增测试**：`chapter-type-consistency.spec.ts`（5 项，锁枚举一致性 + 示例可解析 + 旧节名不得残留）、`chapter-type-gate.spec.ts`（6 项，锁门禁表读字段而非重判）。

### 3.2 卷纲第五段「压力升级检查」是空头要求 ★★★

文档两处要求卷纲必写第五段（`arcplan/SKILL.md:27`、`卷纲固定段规格.md:3,5`），但：

- `core/design/volume.ts:30` 的 `卷纲脚手架段` **只有四段**，缺第五段不拦；
- 建书脚手架 `book/scaffold.ts:37` 也只建四段。

**修法**：不并入硬校验（存量卷纲没这段，硬拦会让旧书全部确认不了），改为**软校验 + 播报**（与章型同款口径）：

```
volumeUpgradeCheckNotice(body): string | null
  缺第五段          → 播报「未写第五段…存量可后补，不拦确认」
  有标题无分条      → 播报「有标题但没有分条核对项」（走了形式）
  整体标〔留白〕    → 不播报（合法留白）
```

工具层在 `finishDesignCommit` **之后**把播报附加到返回值（不 return，否则会跳过提交）。新增 `volume-upgrade-check.spec.ts` 8 项测试。

### 3.3 幕纲「大致章数」自相矛盾 ★★

- `幕纲固定段规格.md:52`：**「本段不写数字」**
- `arcplan/SKILL.md:43`：要求每幕一行写到「大致章数」

直接冲突，执行者无从判断。**修法**：SKILL 改为「行内不写章数——幕的体量由幕纲『章组排布』段的章组体现，章数只在章纲逐章落定时才存在」。

### 3.4「备料自查」可选段的含义被误解 ★★

`幕纲固定段规格.md:70` 标题写「（可选段）」，但它同时是**细纲侧备料五项自查的唯一判据源**（`novel-outline/SKILL.md:90` 已把五项全推给它）。标题的「可选」极易被读成「可以不做」。

而 `幕纲必备段` 不含它，机器侧零校验——缺整段会静默落空。

**修法**：在规格里补一段说明「可选」的准确含义（不是每幕必写，但一旦要备料就是唯一判据源；本幕一项碰不到才可整段省略，省略须在「本幕故事」段末注明）。

## 四、真实缺陷（未修，需你裁决）

这些都需要改设计取向，不是改字能解决的。

### 4.1 审读有两类返回节点没有落地通道 ★★★

`novel-review/SKILL.md:42-47` 定义六类返回节点，其中两类**下游完全不读审核记录**：

| 返回节点 | 声称去向 | 实际情况 |
|---|---|---|
| 「细纲」 | 升细纲 | `novel-outline` 只有「重入勘误」通道（`:72-79`），**不读审核记录**，无接收槽 |
| 「沉淀（账本更正）」 | 账本更正 | `novel-settle` 无对应通道；settle 侧只有 retcon 整条更正，前置是提案回路 |

**影响**：审读发现「细纲层面有问题」时，主控只能口头转述，无工件流转。这是**结构性缺口**。

### 4.2 沉淀组包前置是文字闸，可绕过 ★★★

`novel-settle/SKILL.md:18` 要求「审核完成 + 润色已承接」才能组包。但 `preparePack`（`prepare/pack.ts:169-190`）**全文不读审核/润色状态**——绕过技能直接调工具不会报错。

**影响**：门禁只在人守流程时有效。若要硬拦，需在 `preparePackLocked` 里加状态读取（属于功能新增）。

### 4.3 润色是唯一无工具闸的正文落盘环节 ★★

四个技能里，起草/改稿都有专用工具（`novel_import_draft`、`novel_apply_revision_batch`），**润色新稿由子代理用通用写工具直落**（`novel-polish/SKILL.md:40,81`），无 schema 校验，`保真风险` 字段靠自觉填。

### 4.4 改稿的「发现项→改动映射」无承载字段 ★★ ——**已修（0.0.87）**

`SKILL.md:58` 要求「处置与改动一一对应」，`改稿章程.md:45-48` 要求子代理回传映射清单。但 `novel_apply_revision_batch` 参数（`revision-tools.ts:76-99`）**没有映射字段**，逐条对应关系无处存。

另：`followup`（硬约束回查失败/仍待处置）由 core 算出（`apply.ts:187`），但 batch 工具 output schema（`revision-tools.ts:102-113`）**没有该字段**——只有 `novel_import_draft` 暴露（`drafting-tools.ts:40`），改稿批次把它丢了。

### 4.5 入档即删审核记录，跨章结论失去数据源 ★★ ——**已修（0.0.87）**

`settle-tools.ts:150` 在入档后清理审核记录（`SKILL.md:21` 明列五处含审核记录）。**影响**：「哪类审读问题反复出现」这类跨章统计永久失去数据。

**修法**：清理**不动**（只增不改的定稿区不该塞审核原文），改为入档前先从审核记录派生一份计数摘要到 `定稿/卷NN/审读摘要/NNNN-章名.json`，再由 `archiveChapter` 的 `extraPaths` 并进同一次 `ch:` 提交——跨章统计源落在定稿区，随审核记录清理不再断源。摘要只留模块发现项计数、严重程度分布、处置分布、已处置/作者保留条数与指纹（`审核记录哈希`/`审读指纹`/`审稿哈希`），不含问题说明原文；子目录＋`.json` 使定稿区所有章扫描器对它不可见。写侧 `core/src/evidence/digest.ts`（`writeReviewDigest`），读侧 `loadReviewDigest`。

### 4.6 参考文献「三个消费位」实列六行，且三个是空头 ★★ ——**已修（0.0.87）**

`评审分级与门禁.md:168` 标题写「三个消费位」，表内实际**六行**；且其中三个指向的技能里**没有那一节**：

| 声称消费位 | 实际 |
|---|---|
| 《细纲备料》章纲确认 | outline SKILL 无此节、全篇不引该件 |
| 《全面审读》正文审核 | review SKILL 无此节、不引该件 |
| 《精修润色》表达层 | polish SKILL 无此节、grep 无「评审分级/门禁/强度」 |

另三个（director 节点路由、design ③两席评审、arcplan 幕纲评审）是真实存在的。

### 4.7 阶段地图与代码事实项两套口径未对齐 ★★ ——**已修（0.0.87）**

四阶段（开书→书级基线→卷级滚动→章级循环）**只存在于 UI 文案** `client/stage-data.ts:13`，文件头注释明写「不参与路由或授权」。真实可机器判定的是 `DesignPosition` 七值 + 章级十一行。
