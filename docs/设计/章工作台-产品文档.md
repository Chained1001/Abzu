## 0. 一句话

**Abzu 多一张「章工作台」页面：从左栏书房点某一章进去，一眼看到这章走到哪一步、这一步在等什么、有没有等作者裁决的东西，正文就在这页里读和改。**

页面的主语是**一章**。卷、幕、全书大纲是它的上游，看得见，但不占这页的主位。

### 0.1 谁用、什么时候用

作者本人，长篇网文连载，写的是单章循环。高频动作只有三个：

1. **"接着写这一章"** —— 打开就是这章正文，直接改字。
2. **"这章卡在哪了"** —— 左栏 7 个环节一眼看完。
3. **"有没有等我拍板的"** —— 右栏一行，有就回对话。

一天进这页几十次，不是一次性的开书向导。这决定了三件事：**进去要快、字要大、不要弹窗**。

### 0.2 三条纪律（违反即返工）

1. **不新增需要维护的书状态。** 所有状态从文件推导，页面只读、只显示、只把作者的动作转成对已有能力的调用。页面自己只记"上次看的是哪一章"，存内存，不落盘。
2. **取不到就不显示，绝不用 0 冒充。** 现有 `client/stage-health.ts` 的注释写明"绝不以 0 冒充已接通"，本页同一口径：拿不到的一律「未接入」或「暂无」。
3. **这页不新增任何授权面。** 〔码〕仍走宿主原生审批弹窗，〔谈〕仍在对话里呈报。页面不放"确认细纲""批准入档"这类按钮。

## 1. 要解决的问题：两处硬伤，先钉死再画图

这一节是给 Dev 和 QA 看的定稿口径。前两版文档在这两处自相矛盾，以本文为准。

### 1.1 硬伤一：状态数据只有两个字段，7 个环节

**事实**：客户端拿到的章节数据只有两个字段（`packages/bundle/src/study/types.ts:59` 的 `ChapterView`）：

```text
{ volume, chapter, title, status, finalized?, source? }
```

`status` 是文件事实推出的**建议环节字符串**，`finalized` 是是否已定稿。**11 行布尔事实没有暴露到客户端**——它们在 `packages/core/src/derive/derive.ts` 里算完就留在服务端，`/chapters` 只回 `建议.环节`。

**决定：本期按 7 个环节显示，不扩接口。** 理由是作者批的是"照规格填内容"，不是扩数据面；改 `service.chapters` 的返回结构要另批。

`status` → 环节，一一对应，**不得增补、不得改写**：

| `status` 原文（逐字，半角括号） | 左栏环节 |
|---|---|
| `章细纲(待定位)` | 细纲 |
| `章细纲(待确认)` | 细纲 |
| `写作备料` | 备料 |
| `写稿` | 起草 |
| `审核` | 审读 |
| `改稿` | 改稿 |
| `润色` | 润色 |
| `定稿准备与沉淀` | 定稿 |
| `作者定稿裁决` | 定稿 |
| `定稿入档` | 定稿 |
| `完成` | —— 7 项全完成 |

四态规则三条：

1. 当前环节标 **进行中**；它**之前**的标 **完成**；**之后**的标 **未开始**。
2. `status === '作者定稿裁决'` 时，「定稿」标 **需裁决**，不标进行中。
3. `finalized === true` 时 7 项全部 **完成**，忽略 `status`。

两个额外规定：

- **未知的 `status` 字符串**：7 项全部「未开始」，并把原文显示在顶部条。不猜、不归一到最近的环节。
- **这些标记只用于显示。UI 不得据此禁用按钮、不得拦截操作。** `derive.ts` 首行注释已写明"建议无权威、不参与门禁"。

**作废**：早期草稿里"右栏 11 行逐行亮/暗""不做单值进度条因为行间可同时成立"整套口径，本期不实现。那 11 行（章细纲(待定位)、章细纲(待确认)、写作备料、写稿、审核、改稿、润色、定稿准备与沉淀、作者定稿裁决、定稿入档、完成）**不在页面上出现**，标 **下期（需 `/chapters` 暴露事实项）**。

### 1.2 硬伤二：入口与返回，只有一个版本

前两版文档在这处给了三套互相矛盾的说法。定死如下，**不许再有第二种**：

| | 唯一版本 |
|---|---|
| **进入** | 左栏书房层级树 → 点**章级文件** → 主内容区切成整页 |
| **返回** | 顶部条左侧「← 返回书稿」按钮 → 回对话 |
| **不做** | 不做侧栏「章工作台」独立条目；不做"点侧栏会话返回"的说法；不做第二个返回出口 |

配套定义：

- **章级文件判定**：路径落在 `定稿/卷NN/` 或 `草稿区/草稿/卷NN-NNNN-章名/` 下，且文件名形如 `NNNN-章名.md`（定稿章）或 `稿N.md`（草稿）；0.0.57 之前建的仓，`草稿区/草稿/卷NN-章名/稿N.md` 这种不带章号的旧键**同样算章级文件**。
- **非章级文件**：点击保持现状（右栏编辑器打开），不进整页。
- **返回后**：记住刚才那章；再次点同一章直接回到该章。**这里的"记住"是"位置不被清空"，不是"页面自动恢复"**——返回动作只切面板，不改 `selection`。（刷新/重开应用后位置丢失，见 §6.3；那条是"不落盘"，与这条不冲突。）
- **次入口（同一套规则，不另立）**：左栏搜索结果里命中的章级文件；对话里点书稿链接、且解析出章文件时。

### 1.2.1 一处必须先补的缺口：细纲态与备料态点不进去

**这是本期开工前要决定的一件事，不是可以边做边看的事。**

现行章级文件只有两种（`packages/bundle/src/client/chapter-target.ts:20-22` 的三个正则）：

```text
定稿/卷NN/NNNN-章名.md
草稿区/草稿/卷NN-NNNN-章名/稿N.md
草稿区/草稿/卷NN-章名/稿N.md        ← 旧键
```

而前两个环节的文件都不在这里：

| 环节 | 这一章在盘上的文件 | 点它现在会怎样 |
|---|---|---|
| 细纲（待定位） | 只有近期窗口条目，**盘上没有本章文件** | 无文件可点 |
| 细纲（待确认） | 候选细纲 `草稿区/章细纲/卷NN-NNNN-章名.md` | 右栏编辑器 |
| 备料 | 确认细纲 `故事剧情/卷规划/卷NN/章细纲/NNNN-章名.md` | 右栏编辑器 |

**后果**：图 3（细纲态）和图 4（备料态）在现行判定下**到不了**。作者想从"细纲"这一步进整页，没有门。

**三个可选做法，要作者拍一个**：

| 方案 | 做法 | 代价 | 风险 |
|---|---|---|---|
| **甲** | **不扩入口**（本期采用）。细纲态、备料态进不了整页，图的这两张按"能到达时"画 | 零 | 前两步的体验没改善，作者还是要靠右栏 + 对话。**7 个环节里只覆盖后 5 个** |
| **乙** | 候选细纲、确认细纲也算章级文件，点它们进整页 | 改一处判定（`chapterTargetOf` 加两个正则）；中栏对这两类文件显示细纲正文 | 与 §1.2「非章级文件保持现状」冲突，要同步改文档和 V5；细纲是作者常手改的真源，进整页会多一条编辑面 |
| **丙** | 新增"章选中"入口：左栏章树（按 `/chapters` 列出的章）点章名就进整页，与有没有文件无关 | 要新做一棵"按章列出"的树（现在左栏是文件树，不是章树） | 工作量最大；且与 `chapters` 全量扫描性能问题叠在一起 |

**本期的取法：甲。** 理由是乙会让"点细纲文件"有两种完全不同的行为（有时右栏、有时整页），丙要新做章树、撞上千章性能，两件都不该和第一版混在一批。

**但这条必须让作者知道再开工**——它决定了验收范围：**本期的章工作台只覆盖「起草 → 审读 → 改稿 → 润色 → 定稿」五步，前两步（细纲、备料）作者的入口仍是对话 + 右栏。**

若作者要覆盖全部 7 步，就必须在开工前选乙或丙，并同步改本文 §1.2、V5、图 3、图 4 与验收范围。标 **待作者裁决**。

### 1.3 术语表（与代码逐字一致，不许翻译）

| 术语 | 含义 | 不许写成 |
|---|---|---|
| 章细纲(待定位) | 窗口里有可进入条目，但还没有候选细纲 | 细纲待定位、待定位细纲 |
| 章细纲(待确认) | 有候选细纲，未确认 | 细纲待确认 |
| 写作备料 | 已确认细纲，材料包未齐备 | 备料中 |
| 写稿 | 材料包段齐备，正在写正文 | 起草中 |
| 审核 | 有唯一待审稿 | 审读中、待审 |
| 改稿 | 有审核记录且证据未过期 | 修订 |

| 定稿准备与沉淀 | 润色已承接、待定稿包不完整 | 沉淀中 |
| 作者定稿裁决 | 待定稿包完整、等作者批准 | 待批准 |
| 定稿入档 | 待定稿包完整、裁决=已批准 | 入档中 |
| 完成 | 定稿章已在盘 | 已完成、已发布 |

## 2. 信息架构：书 → 卷 → 幕 → 章

### 2.1 四级层级，每层能看什么、能改什么

| 层 | 数据从哪来 | 能看 | 能改 | 本期在页面上 |
|---|---|---|---|---|
| **书** | `shelf`：`id`（`book:<书id>`）、`name`、`progress`（一行近况）、`error` | 书名、一行近况、是否有书 id 问题 | **不能改**。书级工件（契约/大纲/分卷）只能经对话里的工具写 | 左栏顶层（图 1） |
| **卷** | `/chapters` 的 `volume`；卷目录 `故事剧情/卷规划/卷NN/` | 卷号、本章在哪卷 | 卷纲/计划时间线/幕纲在书仓里是**可编辑真源**（作者手改产生 `fix:` 提交），但**不在整页里改**——点这些文件仍是右栏现状 | 左栏章树按卷分组；卷本身不是页面 |
| **幕** | 幕纲文件 `故事剧情/卷规划/卷NN/幕纲/幕NN-幕名.md` | 幕纲正文 | 经 `novel_confirm_volume_outline`（目标：幕纲） | **本期不显示、不分组**，原因见 2.2 |
| **章** | `/chapters` 的 `volume`+`chapter`+`title`+`status`+`finalized` | 章号、章名、建议环节、是否定稿 | 正文（草稿可编辑 / 定稿只读）；细纲、材料包、审核记录、待定稿包**不在页内改** | 整页的主语 |

**一条对称纪律**：页面上只有"章正文"这一样东西能直接改字。其余全部只读或跳回对话。理由不是保守，是这些工件的写入都带校验与提交语义（结构门槛、审批指纹、`design:`/`ch:` 提交），绕过去就等于绕过门禁。

### 2.2 幕层本期为什么不可用（一条硬事实）

幕是卷与章之间的剧情单元，幕纲里有 `## 章组排布` 段——但这段是**自由文本**，代码里只有段名常量（`packages/core/src/design/volume.ts` 的 `幕纲必备段`），**没有"哪几章属于哪一幕"的机器可读映射**。`/chapters` 也不返回幕归属。

所以：**本期左栏不按幕分组，也不显示"本幕第几章"。** 硬要显示，只能靠正则猜幕纲正文，那是拿不可靠的东西冒充事实。

要做幕层，前置条件是章↔幕的可读映射（一段结构化字段或一张映射表）。这条**不在本期**，也不该在这一页里偷偷解决。

### 2.3 三栏各管什么

| 栏 | 宽度 | 职责 | 一句话判据 |
|---|---|---|---|
| 左栏 | 200–240 | **这章的 7 个环节现在什么样** | 只由 `status` 和 `finalized` 决定 |
| 中栏 | 自适应，最宽 | **这章的文件正文** | 按 定稿 → 待审稿 → 确认细纲 取第一个存在的 |
| 右栏 | 260–320 | **有没有等作者的事** | 发现项 + 待你裁决，两块 |

左栏右侧的边线必须一直画到底；三栏各滚各的，整页不整体滚动。

### 3.0 符号约定

四态符号，全文统一：

| 符号 | 含义 | 出现条件 |

**顶部条（固定一行，不滚动）**

| 位 | 内容 | 规格 |

**中栏 · 文件正文**

- 标题行显示**文件名 + 角色标签 + 可编辑性**：`稿1.md  待审稿 · 可编辑`。

- 只读文件在标题行下方加一条说明带（见 图 8）。
- 空态见 图 11。

**右栏 · 这章怎么了**

- **审读发现项**：本期恒为「未接入」，`title` 注明原因，正文区不画假进度条、不画骨架屏。

- 两块之间一条分隔线。右栏不显示任何计数为 0 的指标。

**底部状态条**（可选，Dev 判断是否需要）

- 保存状态（`已保存` / `未保存改动 ●` / 错误原文）+ 字数。字数取当前 buffer 正文汉字数，**不是**契约篇幅的核对结果。不愿做就不做，不做不影响验收。

|---|---|

| 说明文案 | 「审核记录是机器态文件，客户端本期不解析它的结构。」一句，小字 |
| `title`（悬停） | 「审核记录 `草稿区/审核/卷NN-NNNN-章名.json` 由 `novel_record_review_findings` 写入，其结构与处置词表是核心侧契约；在客户端另解析一份等于造第二个真源。本期不新增读取接口。」 |

**本期形态（页面本身不变）**

│                │    本页只显示文件事实，不显示运行状态。    │                 │

**为什么页面不显示运行态**：这一页的 7 个环节全部由**文件事实**推出。子代理失败了，文件没变，事实就没变——页面显示的仍然是"审核"这一步，这是**对的**。运行状态（哪次调用失败、失败码是什么）在会话日志里，属于对话。

所以本期的规定是：

- 页面**不显示**子代理运行状态、不显示"失败"、不显示重试按钮。
- 失败由主控在对话里报（现有文案：「操作失败，请查看对话中的错误详情。」「操作已中断，请核对已有结果。」）。
- 中栏底部那行 `ⓘ` 是**静态说明**，恒定显示，不是失败时才出现——这样作者不会以为"页面没反应＝没失败"。

**下期候选（不是本期承诺）**：右栏加一块「最近一次操作」，取 `workflow` 接口的 `WorkflowView.calls`，显示 `state` / `summary`。前置条件是确认该接口的 `sessionId` 作用域在整页态下仍然可用（标 **待 Dev 会签**）。

```text

│ ← 返回书稿   卷01 · 0012 雨夜来客              当前环节 写稿 · 参考      [↻] │

│                │                                           │                 │
│ ✓ 细纲         ├───────────────────────────────────────────┤  未接入         │
│ ✓ 备料         │ ⚠ 文档已变化，请先核对磁盘版本            │                 │
│ ● 起草         │   [查看磁盘版本]  [用磁盘版本]  [保留我的] │ ─────────────── │
│ ○ 审读         ├───────────────────────────────────────────┤ 待你裁决        │
│ ○ 改稿         │                                           │                 │
│ ○ 润色         │  雨落在瓦上，声音像有人在数钱。            │ 暂无            │
│ ○ 定稿         │                                           │                 │
│                │  ← 作者改的字还在，没有被替换               │                 │
└────────────────┴───────────────────────────────────────────┴─────────────────┘
```

**保存失败按 code 分五种，各一套原文与动作**（全部沿用仓里已有文案，不改写）：

| 情形 | 显示原文 | 动作 |
|---|---|---|
| 磁盘已变（冲突） | 文档已变化，请先核对磁盘版本 | `[查看磁盘版本]` 打开当前磁盘正文做对照；`[用磁盘版本]` 丢弃本地改动；`[保留我的]` 手动再存一次（带新 hash） |
| 只读 | 定稿更正通过吃书补偿流程处理 / 过程工件由业务工具维护，只读 等 | 编辑区转只读，不提供重试 |
| 提交失败（保存成功、`ch:` 没成） | 正文已保存，但提交失败 | `[重试提交]`（现有 `retry-commit`）。**不能说"保存失败"**——正文已经在盘上了 |
| 通知失败（主控没收到） | 已保存，未通知到对话 | `[重试通知]`（现有 `notify`）。同样是"保存成功" |
| 网络/服务不可用 | 操作失败，请查看对话中的错误详情。 / 书房服务尚未就绪，请刷新后重试 | `[重试]` |

**三条硬规定**：

1. **永不静默覆盖。** 冲突时不自动用磁盘版本替换作者的改动，也不自动覆盖磁盘。两份文字都留着。
2. **两份文字都要能看。** `[查看磁盘版本]` 必须能看，不能只是一句"有冲突"。
3. **提交失败不是保存失败。** 文案上必须分开，否则作者会重存一遍正文（重存会再产生一次保存记录）。

**文件被外部改动（不是错误，但要提示）**：主控在对话里写了同一文件、或作者在别的编辑器里改了，中栏顶部显示一行「文件已在磁盘上变化，[重读]」。**有未保存改动时不自动重读**，等作者点。

## 4. 本章生产流程：每一步、在哪个界面、谁点确认

这一节回答的是"怎么做"，不是"怎么显示"。**每一行的"进入下一步"那一列是代码要照着实现的判据。**

### 4.1 七步总表

| # | 步骤 | 这一步作者做什么 | 这一步 AI 做什么 | 在哪个界面完成 | 结束标志（文件） | 进入下一步的条件 |
|---|---|---|---|---|---|---|
| 1 | **细纲** | 在对话里看呈报表（门槛核对、情节点概述、十查结论），表态同意或要求改 | 读窗口/卷纲/本幕幕纲 → `novel_new_outline_draft` 落候选 → 跑写前十查 → 呈确认 → `novel_confirm_outline` 落确认细纲，提交 `design(chNNNN):` | **对话**（页面只显示 `● 细纲`，无按钮） | `故事剧情/卷规划/卷NN/章细纲/NNNN-章名.md` 出现 | **【作者确认】**〔谈〕逐章呈确认；另有结构门槛〔码〕（九节非空、至少一个完整单元、来源引用合法、窗口有同名条目） |
| 2 | **备料** | 无动作，看就绪播报。十段材料不是开写门槛 | `材料备料.mjs` 预览 → `novel_assemble_materials` 落十段材料包 + `材料清单.json` | **对话** | `草稿区/材料包/卷NN-NNNN-章名/材料清单.json` 状态=段齐备 | **【自动】**细纲确认后备料自动接续 |
| 3 | **起草** | 收稿验收（只查不改）；欠产时三选（收下/退回细纲/弃章）；也可以直接在中栏改字 | 组装任务包（心智→目标→细纲→材料→文风→硬约束→写作卡）→ 派起草子代理 → 交整章新稿或**停笔报告** | **对话**派活；**章工作台中栏**读/改 | `草稿区/草稿/卷NN-NNNN-章名/稿N.md` 出现，`角色: 待审稿`、`选定: true` | **【自动】**接续审读。**要作者定的例外只有两个**：停笔报告（回细纲改纲）、欠产阶梯（三选） |
| 4 | **审读** | 处置发现项：默认处置口径下建议级由主控直接处置（汇总一行、作者可翻案）；高/硬伤级与创作取舍逐条呈报 | `确定性检查.mjs` → 派全量审读子代理（九维）→ `novel_record_review_findings` 按模块回写（零发现也回写，带审读指纹） | **对话**（页面右栏恒「未接入」） | `草稿区/审核/卷NN-NNNN-章名.json` 写入，`完成: true`，每条发现项有处置状态 | **【自动】**按处置路由判是否进改稿：语义层/细纲层/材料层/账本层有问题→改稿；全部处置且不再需要改稿→润色 |

### 4.2 审读 ⇄ 改稿 的循环出口（这一条最容易写错）

这个循环**不是一个需要作者点"结束"的循环**。出口是代码判的，三条同时成立才出：

```text
① 审核记录的「完成」= true
② 每条发现项都有处置状态（六值之一：已解决 / 已接受修改 / 作者保留 / 已驳回 / 无法判断 / 已转提案）
③ 审核证据对当前稿未过期
   —— 审核记录绑的是被审正文的哈希与审读指纹；改稿改了字，哈希就失配，证据立刻过期
```

对应的代码事实（`derive.ts` 第 6、7 行）：

- 「改稿」成立 = `有审核记录 && !审核证据过期`
- 「润色」成立 = `审核完成 && !润色已承接`

**所以循环的实际行为是**：

| 发生了什么 | 事实怎么变 | 页面怎么显示 |
|---|---|---|
| 审读完，发现项还有没处置的 | 「审核」成立，「改稿」成立（有记录、证据未过期） | 两张都亮不起来——`status` 取最后一个成立的行，显示「改稿」 |
| 改稿改了正文 | 新稿哈希 ≠ 审核记录的审稿哈希 → 证据过期 | `status` 退回「审核」；左栏回到审读是 ●。**这不是 bug，是设计要求** |
| 重审后又改，又过期 | 同上，循环 | 同上 |
| 改到不用再改 | 审核完成 + 处置齐 + 证据未过期 → 「润色」成立 | `status` = 润色，出循环 |
| 第 3 轮仍未解决 | 主控标「须作者决定」并附瓶颈诊断（建议，不是门禁） | 页面不变，作者在对话里定 |

**作者唯一要做的**：把发现项处置完。作者不点"结束循环"，页面也不提供这个按钮。

**润色是例外的一条**：润色会改字，会破坏"证据绑正文哈希"的前提，所以有 `novel_record_polish` 这个承接登记——登记之后，过期判定改按承接链认，不算过期（`scan.ts` 的 `carryoverApplicable`）。润色后**不重跑九维语义审读**，只做保真核对与两个确定性检查的复核。

### 4.3 一条必须钉死的：这页不是分步向导

**章工作台不提供"下一步"按钮。** 七个步骤的推进全部在对话里，页面只做三件事：

1. 显示这章走到哪（7 个环节）；
2. 让作者直接读/改正文；
3. 提示有没有等作者的事（待你裁决）。

写清这条，是因为最容易的误读是把它做成分步向导：每步一个按钮、点完自动进下一步。那样会立刻违反三条纪律——排细纲要读四份上游、确认要〔谈〕、入档要〔码〕审批，全都不能由一个按钮代劳。

| 保存冲突 | 按 `status` 点亮 | 文档已变化，请先核对磁盘版本 + 三动作（图 13） | 正常 | **是** |
| 提交/通知失败 | 按 `status` 点亮 | 正文已保存，但提交失败（或未通知到对话）+ 重试 | 正常 | **是** |
| 子代理失败 | 按 `status` 点亮（**不变**） | 正文照常 + 静态说明（图 12） | 正常 | 否 |
| 读取失败 | 骨架 → 局部报错 | 该区报错原文，不白屏 | 该区报错原文 | **是** |
| 旧键存量章 | 按 `status` 点亮 | 正常；顶部条 `章未定位 · 章名` | 正常 | 否 |

**一条总规矩**：空不等于错。没细纲、没章、没书、没候选都是合法状态，用引导语气；只有 IO 失败、格式异常、保存冲突、服务不可用才用错误样式。

### 6.3 已知限制（第一版接受，写进验收前提）

1. **千章书会卡。** `/chapters` 是对每章跑一次全量扫描，实测 1000 章约 21 秒、200 章约 2.9 秒。第一版接受"单卷 50 章内可用"，≥500 章的书允许明显等待。窗口化需要新接口，本期不做。
2. **整页态下右栏能力消失。** 宿主在整页态不给 on-screen 会话，右栏的文件预览与检索索引看不到。要看回对话。
3. **刷新回对话。** 宿主没有路由，页面位置只在内存里，不落 `localStorage`，不假装恢复。
4. **旧键存量章章号显示为 0。** 0.0.57 之前的草稿目录不带章号，顶部条只能显示「章未定位 · 章名」。进页与点亮不受影响。
5. **真机未验。** 第三方插件注册 `main` 槽在宿主里还没真机点过，验收前必须由作者或 Dev 点一遍。
6. **幕层不可用。** 章不挂幕，页面不显示"本幕第几章"。
7. **右栏两块都是占位。** 审读发现项恒「未接入」；待你裁决只有一行字和跳转。
8. **只覆盖后半程。** 细纲态、备料态本期进不了整页（§1.2.1 方案甲），7 个环节里可到达的是「起草 → 审读 → 改稿 → 润色 → 定稿」。前两步的入口仍是对话 + 右栏。

## 10. 演进方向（不是本期承诺）

章工作台跑顺之后，再评估要不要加外层：文库页 → 书房总览页 → 章工作台，三级下钻。那时候这一页**直接就是中层那一页**，不返工。

判断标准只有一条：作者是否真的需要"一次看多本书/多卷"。现在不需要——长篇连载的作者一天只在一本书、一章上。
