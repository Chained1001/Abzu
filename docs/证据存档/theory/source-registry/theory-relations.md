## Relation Model

Use these typed relations:

| relation | meaning | Skill consequence |
|---|---|---|
| dependency | B needs A's definitions, facts, or artifacts | run A and validate its output before B |
| hierarchy | theories operate at macro, meso, or micro levels | frame broadly, execute narrowly |
| complementarity | theories inspect different parts of one task | layer outputs with separate evidence |
| overlap | same target with different vocabulary or grain | use terminology bridge; avoid duplicate operations |
| competition | incompatible operation or success criterion | route by condition or ask user |
| critique | one limits another's assumptions | use as boundary or failure check |
| translation | partially corresponding concepts across disciplines/languages | mark loss; do not claim identity |
| method-to-theory | one item operationalizes or measures another | keep rationale and procedure distinct |
| sequential | B consumes A's artifact | encode order and gate |
| orthogonal | dimensions coexist but do not support each other | keep separate audits |
| background | context without executable authority | keep out of main workflow |
| replacement | one item supersedes another for this task | use stronger item; preserve historical retrieval |

## Conflict Handling

Classify conflict before resolution:

- definition conflict;
- scope or scale conflict;
- method conflict;
- value conflict;
- causal conflict;
- layer-ownership conflict;
- evidence-status conflict.

Resolve in this order:

1. user hard boundary and decision authority;
2. versioned story fact and knowledge boundary;
3. same-object, same-scale direct evidence;
4. layer ownership;
5. mature bounded theory;
6. conditional/provisional theory;
7. project rule;
8. AI proposal.

Do not merge a value conflict. Do not let language evidence rewrite story truth. Do not let post-release correlation become a causal writing rule.
