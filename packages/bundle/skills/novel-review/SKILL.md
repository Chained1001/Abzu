# 全面审读（Novel Review）

本技能是**编排手册**：怎么派发、怎么回写发现项、怎么处置。检查标准本体在包内 `agents/`（合并章程＋9 份单维底本），本技能不复述；主 Agent 收集聚合，绝不主观臆造结论。

## 底本与两种派发

| 派发方式 | 任务包里的底本 | 何时用 |
|---|---|---|
| **全量审读（默认）** | `agents/全量审读.md`（9 维合并章程） | 常规审读——**一次派发跑完 9 维**,文本只发一遍 |
| 定向加深 | `agents/<单维>审读.md`（章节结构审读／人物与关系审读／情节与因果审读／信息披露审读／线索与伏笔审读／节奏与张力审读／读者承诺审读／文风与表达审读／世界内合理性审读，文件名与回写用的模块名同名） | 某维度发现项密集、或作者点名深挖时 |

两个确定性模块（文本规范检查、设定与时序核对）由技能脚本完成：唯一待审稿就绪后运行 `node <resourceBase>/scripts/确定性检查.mjs --book <bookRoot> --卷 <卷> --章 <章> --章名 <章名>`——脚本只算不写，stdout 末尾给出「回写载荷」（逐确定性模块的发现项数组），你按模块名经 `novel_record_review_findings` 逐个回写落盘；再回写 9 维审读结果。

**字数以脚本为准**：两种输出模式都提供 `正文统计`，含稿件路径、版本、审稿哈希、审读指纹及统计口径。向审读者完整传递该对象；报告原样引用其中的 `汉字数`，若另报 `非空白字符数` 或 `字符数` 须明确口径。正文含章标题，不含 frontmatter 和草稿候选事实。缺统计、稿件不符或指纹不符时重新运行当前稿脚本；取得结果前只能写“字数未核验”，不得凭阅读感觉、行数、token 数或子代理估数补齐，不得据此宣称满足篇幅要求。换稿后旧统计作废。

**每次回写都带输入身份**：每个自动模块（包括零发现项）调用 `novel_record_review_findings` 时必须传 `审读指纹`。确定性模块原样使用该次脚本的回写载荷；语义模块使用派发时附给它、并随报告原样返回的指纹。缺失或与当前输入不一致均拒绝，不能在收到旧结果后补上最新指纹。

**输入已变的重跑**：换稿、细纲升版或材料包刷新后，按当前输入重跑确定性脚本与语义审读。新轮首个模块带当前指纹回写时重置旧轮次（旧完成态作废、旧发现项不保留，作者意见与已给处置按三元组沿用）；之后每个模块仍必须携带实际审读的同一指纹。只更新指纹而不重审正文和材料会伪造当前稿证据，禁止这样做。

需要审读材料交接时在同一命令后加 `--审读材料 true`，输出完整JSON：`审读指纹`、`正文统计`、`材料段`、`回写载荷`。它用与写稿/恢复相同的读取器验证已登记补充。把其中补充的来源、理由、性质与原文完整放入下方模板；不得只送清单或只修改指纹却漏掉正文。来源过期或附件损坏是备料待核对，不是空审成功；回《细纲备料》处理后重跑，并沿用本次输出的指纹回写。

## 标准流程

脚本的 `篇幅核对` 使用当前契约与实测正文汉字数，返回范围、来源和差额。偏短/偏长已经纳入“文本规范检查”普通发现项，沿用本流程逐模块回写和修改、作者保留等处置，不再创建重复发现项或额外篇幅审核节点。未配置、未确认不能报篇幅达标；配置错误按现有契约更新通道核对。若材料包内的旧篇幅说明与当前脚本不一致，沿用《细纲备料》刷新材料。幅度本身不决定故事质量，不自动裁剪、扩写或发起单独审批。契约「章节篇幅」含章型浮动条款时，审读按本章章型的浮动档区间判差额——过渡章对照过渡档区间、高潮章对照高潮档区间，容差带口径照作品契约章节篇幅节（单源），判定分段照本表（档区间内＝达标，容差带内＝呈作者裁量，超出＝欠产/超产发现项），章型未注明按主区间；脚本篇幅核对按全带（全档最小值～全档最大值）核对——core 契约解析器接受浮动行落地前脚本遇浮动行报「配置错误」，篇幅核对整节交人工按本章章型的档区间判。

**篇幅处置建议分级**（按差额取一档给建议，是建议口径不是门禁，与「幅度不决定质量」共存）：

- **欠字 → 先「回炉扩写」（显式档，一次为限）**：定向扩写重交——事件膨胀法判据单源在《正文起草》验收步（每拍给新信息、卫星事件不引新冲突），本节不重述；字数核对已在起草验收步前置，到审读侧仍欠的章按本档给建议；
- **回炉扩写后仍欠 → 先过第四形态「细纲没错只是写得薄：写足再交」**（零新卫星事件、纯信息加密补写一轮——细纲事件量足、执行未写足时走此档，处置枚举单源在《正文起草》验收步，本节引用不重述）→ 仍欠或细纲事件量本身不足再呈作者三选：收下（记 `作者保留`）／改卡重写（退回细纲——细纲事件量本身不足时才退）／弃章；
- **超字 → 一次净删**：保情节点/事实/因果/情绪兑现/钩；删重复解释/装饰排比/无功能微动作——一次净删优于多次零碎删改。

**发现项处置三列表**（信号→动作→停止条件；按信号选路、按停止条件判修完——停止条件是可检验状态，不写「改好为止」式空话；篇幅类发现项按上方「篇幅处置建议分级」走，停止条件口径同表＝差额落回本章章型档区间）：

| 信号（发现类型/严重度） | 动作（返回节点或主控动作） | 停止条件（修完的可检验状态） |
|---|---|---|
| 表达层：套话/重复表达/思维标记/排版类——语义与结构不动就能修 | 处置记 `已接受修改`、改动说明写『留润色』（纯处置批），由润色一并处理（0.0.54 润色后移） | 润色承接通过＝修完（`novel_record_polish` 登记成功）；两轮仍有残留＝升改稿 |
| 语义层：情节因果/人物行为/信息披露越界——润色够不着 | 改稿 | 按发现项编号逐条定位重审，原位不再命中＝修完；同条两轮改稿仍命中＝升细纲 |
| 细纲层：单元未兑现/事件量不足/信息预算错配——根因在细纲 | 细纲 | 新确认细纲后重跑本轮审读，原发现项不再命中＝修完；细纲修不动（设定或材料本身缺）＝升备料 |
| 材料层：设定缺条目/账本未登记/契约口径冲突（「材料完整性」报缺处） | 备料 | 补料刷新材料包后重审，各模块材料完整性＝完整＝修完；补料后冲突在已定稿真源＝升作者裁决 |
| 账本层：旧事实登记矛盾/线索状态错——审读不改账本 | 沉淀（账本更正） | 账本更正落账后重查该行，与新事实一致＝修完；牵动已定稿章＝吃书补偿呈报 |
| 硬伤涉设定取舍/吃书补偿/无法机械判（硬伤级） | 作者裁决（主控动作，非返回节点） | 落处置（下方步骤 6 六值之一，`无法判断` 不算）＝完成；作者未表态前该条停在「待处理」，不代答不推断 |

派发前核对各维度所需材料和正文分区。报告缺关键材料或指纹时，先补料重审，不将它作为零发现项回写完成；部分维度有完整依据时可先回写该维度。格式字段与模型执行说明留在任务资料区，不作为小说正文审读。

1. 读唯一待审稿：`草稿区/草稿/卷<NN>-<NNNN>-<章名>/` 下 `角色: 待审稿` 的那一稿；
2. **确定性检查**：运行技能脚本（只算不写），把「回写载荷」里每个确定性模块经 `novel_record_review_findings` 回写（零发现项也要回写以置完成态）；脚本失败时按失败分流处理（见《工作台总控》脚本失败分流表），属脚本缺陷则停下报作者；
3. **派发（默认全量）**：子代理（Subagent）隔离运行——按下面的派发模板组装，材料全部内联；
4. **回写**：子代理按维度分组返回发现项后，**按模块名逐个调 `novel_record_review_findings`**（卷/章/章名/模块名/审读指纹/该模块发现项数组）——一次全量报告要回写 9 次，每个模块一次（含零发现项的模块），按模块记完成态；每条发现项必须带 `发现项编号`，同一模块内唯一——改稿按编号定位逐条处置；发现项多时按模块分次回写，一次只传一个模块的数组；**严禁用通用写工具手写审核记录 JSON**；
5. 全部模块回写后，记录中的 `完成` 仅表示模块回写齐全；还须证据适用当前稿且所有发现项有效处置，才可宣布审核通过。分别呈报待回写模块和待处置项——**只跑不回写＝空审**，仍有待处置项也不能宣布通过；
6. 处置：**每条发现项都要给**，取值只用 `已解决`、`已接受修改`、`作者保留`、`已驳回`、`无法判断`、`已转提案` 六个（初始值 `待处理` 不算处置；`已转提案` 只用于影响真源、且已通过提案明确关联本章本发现项的条目——工具核对提案状态与关联身份，拒绝即按报错修正）；留一条「待处理」审核就判不完成，建议级也一样。带补丁的 `已接受修改` 在改稿节点经 `novel_apply_revision_batch` 落实；只记处置的条目（含上游范围的保留／驳回／已转提案）走同一工具的纯处置批，传编号与处置即可；硬伤未处置不得进入定稿准备。严重程度两轨词表不并轨：机器轨（确定性脚本回写载荷）用 `低`/`中`/`高`，模型轨（审读底本）用 `硬伤`/`建议`/`仅供参考`；两路发现项汇入同一审核记录时按映射对应读——低↔仅供参考、中↔建议、高↔硬伤，各自原词回写不改写。**审核完成后进入《精修润色》**（0.0.54 润色后移：表达层发现项留润色一并处理，润色改字后经 `novel_record_polish` 登记承接，不重跑审读脚本）。**默认处置口径（0.0.55）**——本书未另定口径时，机器轨「低/中」与模型轨「建议/仅供参考」级、且修改建议可机械执行的发现项，主控直接按建议处置（改稿轮落实或留润色），不逐条呈作者；在定稿呈报里列一行汇总（编号＋问题一句＋处置），作者可翻案（翻案走退回或编辑器手改）。「高/硬伤」级与涉创作取舍（走向、人设口径、删段超过两成）的仍逐条呈报。

- **没有书仓访问槽位**：一切材料内联，不给可供自行读写书仓的路径；来源标识、版本和正文位置保留，用于报告引用，不能代替原文；
- **分档参考区间动态摘录**：派发前从《定调设计》技能包 `references/参考标尺.md` 原样摘录相关分档行（含打破条件列）放进第二部分——审读子代理隔离运行不读书仓文件，数值不抄进底本：底本只定用法，参考标尺是唯一数值源，任务包带当次数值；
- **参考线速览表单源**：十份审读底本（全量审读＋九份单维底本）的参考线数值一律对照第二部分速览表——底本文件不内联数值，速览表随任务包带，数值修订只改本 SKILL 表；段末格言化参照数值照写作卡摘录行随包；
- 材料缺项照实留空并注明「该项未提供」，子 Agent 在「材料完整性」回报缺项——由主控补全原文后重审，不用可访问路径代替材料；
- 卷级体检：每章一次这样的派发，主 Agent 聚合，不把多章塞进一次派发；
- **定向加深派发**：同一模板，底本槽换单维底本、任务行注明「只审 X 维」。

## 重入（新一轮审读）

- 同一模块重复回写＝本轮结果**整批替换**；跨轮沿用按「模块名＋证据位置＋问题说明」三元组认亲——上一轮作者已给的处置自动保留，不被退回「待处理」；
- 正文改动后不再命中的发现项直接消失；新命中的为「待处理」；
- 完成态只看本轮：曾经失败又被摘掉的模块不会永久压住 `完成`，不必手改审核记录。

## 工件契约

| 工件 | 路径 | 属性 |
|---|---|---|
| 审核记录 | `草稿区/审核/卷<NN>-<NNNN>-<章名>.json` | 机器态 JSON，`schemaVersion: 1`;含 `完成`、`问题[]`、`模块`;`模块` 每项五个键 `完成`／`失败`／`跳过`／`待回写`／`理由`（后三个可缺） |

发现项字段以底本「发现项字段」表为准，其中 `处置状态` 七个取值是 `待处理`（初始）／`已接受修改`／`已解决`／`作者保留`／`已驳回`／`无法判断`／`已转提案`（须关联已通过提案）；按这些实际字段取值填写，不用「已确认」替代处置或完成状态。审核记录在草稿区，不入 git。

## 作者介入

- 作者能做什么：补自己的发现项；驳回子代理的某条发现项；
- 用哪个通道：作者补的发现项以模块名 `作者意见` 经 `novel_record_review_findings` 回写（该模块是作者亲自提出意见的通道，不参与自动审读、不卡模块完成态；无需自动审读指纹，跨稿保留，也不刷新旧自动证据）；驳回某条 → 该发现项处置记 `已驳回`；不得把自动审读结果改称作者意见来绕过指纹校验；
- 主 Agent 接到后：作者发现项原样回写，不代作者改写措辞；`生成模块: 作者手写/作者手改` 的稿，其发现项处置一律呈作者，不由你自行改动正文。

## Off-limits

- 审读子代理只读不写：绝不直接修改正文或真源文件；
- 参考事实来自已核对的真源与材料；待审稿的新内容和候选事实须标明性质，不冒充已入档事实；子代理失败只单点重试（全量派发失败重派全量；某维度质量存疑用定向加深复核）。
